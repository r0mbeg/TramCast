# Backend TramCast

Go-приложение TramCast. Запущенная основа — сервер Gin, конфигурация из окружения, логирование через `slog` и пул PostgreSQL. Готовы чтение справочников, их импорт из XLSX и снимка OpenStreetMap, раздача сборки фронтенда, gRPC-клиент Python-сервиса, регистрация версий прогноза и очередь расчётов с фоновым обработчиком и транзакционной публикацией; HTTP API прогнозов добавляется следующим этапом.

Готовы SQL-миграции, 41 именованный запрос, сгенерированные пакеты sqlc/gRPC и модуль Go 1.26.8. `cmd/tramcast/main.go` собирает конфигурацию, логгер, пул, обработчики фич, обработчик очереди и HTTP-сервер. Из сервисов прогнозов реализованы регистрация и активация версии и [очередь прогнозов](#очередь-прогнозов): приём, захват, аренда, вызов ML, публикация, повторы и восстановление. Задания пока ставит команда `enqueue-prediction-jobs`; HTTP-маршруты прогнозов не реализованы.

## Запуск

В Docker весь проект запускается из корня командой `docker compose up --build -d --wait` после настройки `.env`. Очищенная книга справочников и снимок OSM входят в образ. Compose собирает Go и фронтенд, дожидается PostgreSQL, применяет миграции и загружает справочники в пустую БД перед запуском HTTP. Инструкция — в [документации разработки](../docs/development.md#запуск-приложения-в-docker).

Из корня проекта после настройки `.env` и запуска PostgreSQL:

```text
make run-backend
```

Напрямую из `backend`: `go run ./cmd/tramcast -env-file ../.env`. Без `-env-file` приложение читает только окружение процесса. Подробные настройки и команды БД — в [инструкции разработки](../docs/development.md).

Пул проверяется через `Ping` с таймаутом до запуска HTTP. При ошибке приложение завершается с ненулевым кодом. По SIGINT/SIGTERM сервер прекращает приём соединений и ждёт активные запросы до `HTTP_SHUTDOWN_TIMEOUT`; одновременно обработчик очереди перестаёт захватывать задания и даёт текущему вызову ML до `PREDICTION_JOB_SHUTDOWN_TIMEOUT` ([остановка](#жизненный-цикл-и-остановка)). Когда оба завершились, закрываются gRPC-клиент и пул. Ошибка привязки HTTP-порта также завершает приложение вместе с обработчиком.

| Маршрут | Назначение |
| --- | --- |
| `GET/HEAD /healthz` | HTTP работает: `200` |
| `GET/HEAD /readyz` | PostgreSQL отвечает на `Ping`: `200`, при ошибке или таймауте — `503` |
| `GET /api/routes` | `{"routes": [...]}` — маршруты по номеру; `name` может быть `null` |
| `GET /api/routes/geometry` | GeoJSON `FeatureCollection`: `LineString` на каждый вариант движения, координаты `[lon, lat]` по порядку остановок; свойство `source` — `workbook` или `osm` |
| `GET /api/routes/{route_id}/stops` | `{"route_id", "patterns": [...]}` — варианты движения и остановки по порядку; `400 invalid_route_id`, `404 route_not_found` |
| `GET /api/stops` | `{"stops": [...]}` — весь справочник остановок |
| Остальные GET/HEAD | Файлы из `WEB_DIR`; при переходе в браузере пути без расширения получают `index.html`. `/api/...`, отсутствующие файлы и страницы без файла для JSON-клиента (`Accept: application/json` без `text/html`) — `404` |

Readiness проверяет подключение, а применение миграций остаётся отдельным шагом. Логи запросов содержат сгенерированный `request_id`, метод, путь, статус и длительность. Параметры URL, заголовки и тела запросов не записываются; клиент получает request ID в `X-Request-ID`.

Ошибки API имеют вид `{"error": "<код>"}`. Обработчик передаёт внутреннюю ошибку через `core_http_server.WriteInternalError`: клиент получает `500 internal_server_error`, а текст ошибки попадает в строку лога запроса уровня ERROR.

Проверки из корня проекта: `go -C backend test ./...`, `go -C backend build ./...` и `make tidy-backend-check`. Тесты проверяют конфигурацию, логирование, совместимость пула с sqlc, диагностические маршруты, обработку panic, остановку активных запросов, сервис и обработчики справочников, раздачу статики, чтение и проверку книги справочников и снимка OSM (тесты читают снимок из `data/osm/` по относительному пути), объединение источников и транзакцию импорта на заглушке.

Для прогнозов проверяются московское время и выравнивание по часу, настройки ML и очереди, gRPC-клиент на `bufconn` (форма запроса, отказ до отправки, проверки ответа, классификация статусов, deadline), а также разбор метаданных ML, проверка, регистрация, активация и сверка версии на заглушках. Очередь проверяется на заглушках транзакций: порядок запросов приёма, захвата и публикации, откат при каждой ошибке, потеря владения, неизвестный исход commit, запись ошибки и задержки повторов, пакеты восстановления, перевод точек в московские дату и час. Worker проверяется на заглушках очереди и ML внутри `testing/synctest`: продление аренды, её потеря и поздний ответ, коды ошибок, шлюз ML и остановка. PostgreSQL и Python-сервис для этих тестов не требуются.

Интеграционные тесты пропускаются без переменных окружения. Тест клиента против запущенного replay 030 требует `TRAMCAST_TEST_ML_ADDR` ([запуск](../docs/development.md#версия-прогноза)). Тесты очереди и worker на PostgreSQL требуют `TRAMCAST_TEST_DATABASE_URL` — строку подключения к отдельной тестовой базе ([запуск](../docs/development.md#тесты-очереди-на-postgresql)). Вспомогательный пакет `core_postgres_testdb` создаёт для каждого теста схему `tramcast_test_<hex>`, задаёт её в `search_path` пула, применяет секции `Up` всех миграций по порядку имён и удаляет схему после теста; строка подключения и ошибки её разбора в лог не попадают. Сценарии: параллельный приём одной пары создаёт одно задание; при лимите 3 из 10 параллельных маршрутов принимаются ровно 3; параллельные обработчики захватывают разные задания, заблокированная строка пропускается без ожидания; истечение аренды, восстановление с сохранением номера попытки; публикация устаревшей попытки отклоняется без строк; полная публикация — 1 464 строки вместе с `succeeded`; ошибка копирования откатывает всё, задание остаётся `running`; повтор и окончательная ошибка; исчерпанные попытки; worker с заглушкой ML для 10 маршрутов — 14 640 строк и все задания `succeeded`, в том числе при расчёте дольше аренды; после активации новой версии worker сначала проверяет её в ML: задание ждёт в `queued` без попыток, пока ML её не обслуживает, затем публикуется с первой попытки; остановка во время вызова ничего не записывает, задание возвращает восстановление.

## Импорт справочников

Для автоматического первого запуска есть флаг `-if-empty`: транзакция с уровнем `READ COMMITTED` получает общую блокировку импорта, затем отдельным запросом проверяет `routes`, `stops` и `routes_stops`. Если хотя бы одна таблица непустая, команда успешно завершается с сообщением о пропуске, не открывая источники и не расходуя identity. Для пустого каталога чтение, проверка и запись выполняются под той же блокировкой; ошибка откатывает транзакцию. Два параллельных первых запуска не выполняют импорт дважды. Частично заполненная БД также пропускается: для восстановления или обновления нужен обычный явный импорт. В Compose этот режим включён у `catalog-init`.

```text
make import-catalog-dry-run
make import-catalog
```

Команда `cmd/import-catalog` читает очищенную книгу по пути `CATALOG_FILE` (по умолчанию `./data/catalog/catalog.xlsx`) и снимок OpenStreetMap маршрутов 17, 25, 26, 28, 50 по пути `CATALOG_OSM_FILE` (по умолчанию `./data/osm/tram_routes.json`). Оба файла хранятся в Git и включаются в образ приложения. При явном `-env-file` относительные пути, включая значения по умолчанию и переопределения окружением, считаются от папки этого файла; без флага — от рабочего каталога. Абсолютные пути сохраняются. Обе переменные должны быть непустыми: импорт заменяет всю географию и без снимка очистил бы позиции маршрутов OSM. Основной сервер загружает ту же конфигурацию, но файлы не открывает.

Флаг `-env-file` задаёт файл окружения; `-file` и `-osm-file` заменяют пути книги и снимка для разового запуска, причём относительные пути в этих двух флагах считаются от рабочего каталога процесса. `-dry-run` выполняет импорт и откатывает транзакцию. Позиционные аргументы не принимаются: путь без `-file` завершает команду с кодом 2, иначе флаги после него, включая `-dry-run`, были бы молча пропущены. Напрямую из `backend`: `go run ./cmd/import-catalog -env-file ../.env`. Происхождение снимка, дата данных, лицензия ODbL 1.0 и порядок обновления описаны в [README снимка](../data/osm/README.md).

Фича `catalog` устроена по общей схеме: команда → `catalog/service` → хранилища. `catalog/repository/xlsx` открывает книгу через excelize с исходными значениями ячеек, находит листы `Маршруты GTFS_ROUTES`, `Остановки GTFS_STOPS`, `Порядок_остановок GTFS_TRIPS_ST` и колонки по именам в первых двух строках. `catalog/repository/osm` (`catalog_osm_repository`) открывает файл снимка по переданному пути и декодирует ответ Overpass (`Decode`) в типизированную модель с `int64` ID, тоже без смысловых проверок. Сервис проверяет всю книгу и весь снимок до записи, включая пустые обязательные листы, и при любой проблеме любого источника выводит общий список без изменения БД: для книги — «лист, строка, описание», для OSM с relation и номером участника. Затем объединяет источники с приоритетом книги: маршрут с листа маршрутов книги берётся из книги, его данные OSM пропускаются с предупреждением. Каталог заменяется одной транзакцией; запись идёт через небольшие интерфейсы запросов, поэтому вся логика транзакции покрыта юнит-тестами на заглушке в памяти; общие правила импорта закреплены в [контракте](../AGENTS.md#справочники).

Команда пишет в лог абсолютные пути книги и снимка (`file`, `osm_file`) при старте и итог в конце: число маршрутов, остановок и позиций книги, дата снимка OSM (`timestamp_osm_base`) и число записанных из него маршрутов, остановок и позиций, созданные маршруты без географии, изменённые флаги прогноза, очищенные позиции и удалённые остановки. Пропущенные в пользу книги маршруты OSM видны в предупреждениях. Повторный запуск на тех же книге и снимке сохраняет ID и данные. Каждый импорт, в том числе пробный, расходует значения identity (`INSERT … ON CONFLICT` вычисляет следующий ID до проверки конфликта), поэтому новые строки могут получать ID с пропусками. Пропуск через `-if-empty` значения identity не расходует.

## Версии прогноза

Команда `cmd/register-forecast-version` записывает в `forecast_versions` комплект артефактов, который обслуживает запущенный Python-сервис, и по флагу делает версию активной. Она работает на хосте с Go и в образ приложения пока не входит. Здесь описаны флаги и правила; требования к окружению, получение метаданных и команды для cmd, PowerShell и Git Bash — в [инструкции разработки](../docs/development.md#версия-прогноза).

| Флаг | Цель Make | Назначение |
| --- | --- | --- |
| `-env-file` | `ENV_FILE`, по умолчанию `../.env` от `backend` | Файл окружения: подключение к PostgreSQL, `ML_GRPC_ADDR` и `ML_GRPC_TIMEOUT` |
| `-metadata` | `METADATA` от корня репозитория или абсолютный путь | Обязательный путь к JSON-метаданным. Относительный путь считается от рабочего каталога процесса, как `-file` импорта |
| `-activate` | `ACTIVATE=1` | После регистрации сделать версию активной |
| `-dry-run` | `DRY_RUN=1` | Выполнить все проверки, включая проверку ML, и найти уже зарегистрированную версию без записи; активация пропускается |
| `-verify` | `VERIFY=0` передаёт `-verify=false` | Включён по умолчанию: перед записью вызвать `Predict` для маршрута 5. При `-verify=false` gRPC-клиент не создаётся |
| `-allow-replay` | `ALLOW_REPLAY=1` | Разрешить метаданные replay; без флага они отклоняются |

Без `METADATA` цель Make завершается ошибкой. Неверные флаги, позиционные аргументы и отсутствие `-metadata` — код 2, остальные ошибки — код 1. Через `go run` и Make код 2 виден только в строке `exit status 2`: сам `go run` завершается с кодом 1, а Make при любой ошибке рецепта — с кодом 2, поэтому различать ошибки можно по логу или при запуске собранного бинарника.

Порядок шагов: разбор метаданных → их проверка и запрет replay без `-allow-replay`, ещё до подключения к PostgreSQL → покрытие маршрутов по БД → проверка ML → регистрация → активация. Ошибка до регистрации, в том числе неудачная проверка ML, не меняет БД. `-dry-run` ничего не записывает и никогда не активирует.

- **Метаданные.** JSON из `service.py --describe` (`make ml-describe`) или манифест replay `ml/bundles/030/forecast_bundle.json`: `timezone`, `route_numbers`, `history_end`, `forecast_from`, `forecast_to`, `model_version`, `dataset_version`; время в RFC 3339. Остальные ключи игнорируются, replay распознаётся по наличию `serving_mode` или `prediction_file`. UTF-8 BOM удаляется, файл в UTF-16 отклоняется с подсказкой.
- **Проверка метаданных.** Зона `Europe/Moscow`; непустые ID без пробелов по краям; все три границы заданы, `history_end <= forecast_from < forecast_to`; `forecast_from` и `forecast_to` — на целых московских часах; горизонт не длиннее `forecasts_predictor_grpc.MaxHours` (1 464 часа) — общего с клиентом лимита одного вызова Python. БД для этой проверки не нужна.
- **Покрытие маршрутов.** `route_numbers` включает каждый маршрут БД с `forecast_enabled`. Если таких маршрутов нет, справочники ещё не импортированы: команда завершается ошибкой, а не регистрирует версию без проверки покрытия.
- **Проверка ML.** `Predict` для маршрута 5 на весь горизонт `[forecast_from, forecast_to)` с ожидаемыми ID; маршрут 5 должен входить в `route_numbers`. По контракту ML это структурный ноль: рецепт отвечает без запуска модели и GPU, replay — чтением сохранённого результата. Совпадение версий и полная сетка подтверждают, что запущенный процесс обслуживает именно этот комплект на весь период; расчёт остальных маршрутов так не проверяется. Ошибка клиента, например `ml_version_mismatch` или `ml_unavailable`, останавливает команду до записи. Без проверки (`VERIFY=0` в Make, `-verify=false` в `go run`) версию можно зарегистрировать заранее, но активировать её стоит повторным запуском с проверкой. Worker запущенного backend замечает смену активной версии перед следующим захватом и снова проверяет ML [шлюзом очереди](#очередь-прогнозов): пока ML её не обслуживает, задания не захватываются. Смену комплекта ML без смены версии шлюз не замечает: первое захваченное после неё задание активной версии завершится неповторяемой ошибкой `ml_version_mismatch`.
- **Повторный запуск.** Уникальный ключ `forecast_versions_artifacts_key` по `(model_version, dataset_version, history_end, forecast_from, forecast_to)`: те же метаданные возвращают прежнюю версию с её ID, а не копию. Другой период или новый ID модели — новая версия. ID новой записи — UUID v4 из `crypto/rand`.
- **Активация.** Отдельная транзакция после регистрации, порядок — в [границах транзакций](#границы-транзакций). Уже активная версия не меняется. При ошибке активации версия остаётся зарегистрированной и неактивной; повторный запуск с `-activate` безопасен.
- **Replay.** Replay 030 имеет собственный `model_version` `tabpfn030-zhores8477154-replay` и нужен для разработки и проверки интеграции. Его регистрируют только с `-allow-replay` и никогда не выдают за рабочую GPU-версию: для демонстрации активной должна быть версия из `make ml-describe`.

В итоге команда пишет в лог ID версии, создана ли она, результат активации, ID модели и данных и период. Логика находится в `forecasts/service` (`forecasts_service`): разбор метаданных и их проверка без БД (`CheckSpec`), а после подключения — `Service.Apply`, который выполняет покрытие маршрутов, сверку через интерфейс `Predictor` (его реализует клиент `forecasts_predictor_grpc`), регистрацию и активацию через небольшие интерфейсы sqlc.

## Очередь прогнозов

Задание — пара `(forecast_version_id, route_id)` на весь горизонт версии. Жизненный цикл задания в PostgreSQL ведёт `forecasts_service.Queue`, фоновый обработчик `forecasts_worker` работает в процессе `cmd/tramcast`. HTTP API, создающего задания по запросу пользователя, ещё нет: сейчас задания ставит команда [`enqueue-prediction-jobs`](#постановка-заданий). Параметры — `PREDICTION_JOB_*` ([таблица](../docs/development.md#конфигурация-backend)), порядок SQL — в [границах транзакций](#границы-транзакций). Каждый шаг — короткая транзакция `READ COMMITTED`; сетевых вызовов внутри транзакций нет.

- **Приём (`Admit`).** Сначала в транзакции `READ ONLY` проверяются версия (`ErrVersionNotFound`) и маршрут (`ErrRouteNotFound`, `ErrForecastDisabled`): SQL их не проверяет, и отсутствие строки проявилось бы нарушением внешнего ключа под блокировкой очереди. Затем транзакция приёма: блокировка таблицы заданий первым запросом → существующее задание пары возвращается в любом статусе, даже при полной очереди → если `queued + running` по всем версиям не меньше `PREDICTION_JOB_QUEUE_CAPACITY`, откат и `ErrQueueFull` (в будущем HTTP — `503`) → вставка с UUID из Go. Повторный приём возвращает прежнее задание; `failed` не перезапускается.
- **Захват (`Claim`).** Одна транзакция: `ClaimNextPredictionJob` переводит готовое к запуску задание в `running`, увеличивает `attempt_count` и выдаёт аренду `PREDICTION_JOB_LEASE_DURATION`; затем читаются закреплённая версия задания (не активная) и маршрут. Ошибка чтения откатывает захват, попытка не расходуется. Полученный `attempt_count` — токен владения для всех последующих записей этой попытки.
- **Вызов ML.** Запрос — номер маршрута и весь горизонт закреплённой версии с её ID модели и данных; клиент отклоняет ответ другого комплекта (`ml_version_mismatch`) и неточную сетку. Контекст вызова не зависит от HTTP, deadline — `ML_GRPC_TIMEOUT`. Если прогноз маршрута отключили после приёма, задание завершается кодом `route_not_enabled` без вызова ML.
- **Аренда.** Пока идёт вызов, отдельная горутина каждую треть срока аренды вызывает `RenewLease` с собственным тайм-аутом. Ноль изменённых строк — `ErrLeaseLost`: вызов отменяется, результат не записывается. Ошибку БД worker повторяет, пока с последнего успешного продления не пройдёт срок аренды минус интервал продления, после чего тоже считает аренду потерянной. Перед публикацией или записью ошибки продление останавливается и дожидается завершения: иначе продление, ждущее за блокировкой публикации, увидело бы уже завершённое задание.
- **Публикация (`Publish`).** До `BEGIN` точки переводятся в московские дату и час (`pgtype.Date` — полночь UTC этой даты); версия и маршрут берутся из задания, число точек должно равняться числу часов версии. Транзакция: `LockPredictionJobForPublication` с номером попытки (нет строки — `ErrLeaseLost`, ничего не записано) → сверка версии и маршрута заблокированной строки с заданием → `CopyValidationPredictions` в той же транзакции с проверкой числа строк → `CompletePredictionJob` ровно с одной изменённой строкой → commit. Нарушение ключа или CHECK при копировании (SQLSTATE `23505`, `23514`) — `ErrPublicationConflict`; любая ошибка откатывает все строки. Если исход commit неизвестен, задание перечитывается с отдельным тайм-аутом 5 с: `succeeded` с этой попыткой — успех, `running` с ней — обычная ошибка публикации (`publication_failed`), иначе `ErrLeaseLost`.
- **Ошибки (`FailAttempt`).** `FinishPredictionJobWithError` записывает код в `last_error_code`, а текст ошибки, не длиннее 1 000 символов, без NUL и с корректным UTF-8, — в `last_error_message`; оба поля остаются внутренними. Повторяемая ошибка при оставшихся попытках возвращает задание в `queued` с отсрочкой `PREDICTION_JOB_RETRY_DELAY × 4^(n−1)` после попытки n, не больше 1 ч; прочие ошибки и последняя попытка дают `failed`. При значениях по умолчанию (3 попытки, 30 с) повторы идут через 30 с и через 2 мин, третья неудача окончательна. Потеря владения — `ErrLeaseLost`, запись не выполняется.

| `last_error_code` | Источник | Повтор |
| --- | --- | --- |
| `ml_unavailable`, `ml_deadline_exceeded` | Клиент gRPC, [таблица статусов](#grpc-контракт) | Да |
| Остальные `ml_*` | Клиент gRPC: `ml_invalid_request`, `ml_invalid_response`, `ml_version_mismatch`, `ml_cancelled` при действующем владении и статусы сервера | Нет |
| `route_not_enabled` | Прогноз маршрута отключён после приёма задания | Нет |
| `publication_conflict` | Публикация нарушила ключ или CHECK таблицы прогнозов | Нет |
| `publication_failed` | Другая ошибка публикации, в том числе БД | Да |
| `internal_error` | Ошибка вызова ML без классификации клиента | Нет |
| `lease_expired` | Восстановление истёкшей аренды | Да, пока есть попытки |
| `attempt_limit_exceeded` | Задание в очереди без оставшихся попыток, например после уменьшения лимита | Нет |

- **Восстановление (`Recover`).** При старте worker и затем каждые полсрока аренды `RecoverExpiredPredictionJobs` возвращает `running` с истёкшей арендой в `queued` с базовой задержкой `PREDICTION_JOB_RETRY_DELAY` либо завершает его `failed`, если попытки исчерпаны; затем `FailExhaustedQueuedPredictionJobs` закрывает задания в очереди без оставшихся попыток. Пакеты по 100 строк фиксируются по отдельности и повторяются, пока пакет не окажется неполным. Номер попытки при восстановлении не меняется, его увеличит следующий захват, поэтому поздний ответ прежней попытки отклоняется при публикации. Восстановление работает только с БД и не зависит от шлюза ML.
- **Шлюз ML.** Общий для всех циклов захвата и закрыт при старте. Пока он закрыт, worker читает активную версию и вызывает `Predict` для маршрута 5 на весь её горизонт с тайм-аутом 10 с — тот же структурный ноль, что в проверке `register-forecast-version`. Успех открывает шлюз и запоминает ID проверенной версии, в лог пишется `ML server ready` с ID модели и данных. Отсутствие активной версии или любая ошибка проверки оставляет шлюз закрытым с повтором через `max(PREDICTION_JOB_POLL_INTERVAL, 15 с)`; в лог попадает только смена состояния. Перед каждым захватом worker читает активную версию: если она сменилась, шлюз закрывается и проверка повторяется. Шлюз также закрывается после ошибки задания `ml_unavailable` или `ml_deadline_exceeded` и после `ml_version_mismatch` у задания активной версии. Несовпадение версий у задания неактивной версии — неповторяемая ошибка только этого задания, шлюз остаётся открытым. Пока шлюз закрыт, задания не захватываются и попытки не расходуются. Остановка ML при открытом шлюзе стоит не больше одной попытки одного задания на цикл захвата: задание возвращается в очередь как повторяемое, и шлюз закрывается. Смену комплекта ML без смены версии шлюз не замечает ([ограничения](#ограничения-очереди)).

### Жизненный цикл и остановка

При `PREDICTION_JOB_WORKER_ENABLED=true` (по умолчанию) `cmd/tramcast` создаёт gRPC-клиент по `ML_GRPC_ADDR` и `ML_GRPC_TIMEOUT`, очередь и worker и запускает его рядом с HTTP-сервером. При `false` в лог пишется `prediction job worker disabled`, задания остаются в очереди. `Run` запускает цикл восстановления и `PREDICTION_JOB_WORKERS` циклов захвата и возвращается только после завершения всех горутин; затем в лог пишется `prediction job worker stopped`. Пустая очередь или ошибка БД при захвате — пауза `PREDICTION_JOB_POLL_INTERVAL`. Лог задания содержит `job_id`, номер попытки, `forecast_version_id`, `route_number`, длительность, код ошибки и итоговый статус.

По сигналу остановки worker сразу прекращает захват. Текущему вызову ML даётся `PREDICTION_JOB_SHUTDOWN_TIMEOUT` (от 0 до 20 с): быстрый ответ из кэша или replay ещё публикуется, долгий расчёт отменяется, и Python прерывает вычисление. Если исход commit публикации неизвестен, перечитывание задания добавляет до 5 с. После отмены из-за остановки или потери аренды worker ничего не записывает: задание остаётся `running` до истечения аренды, затем восстановление возвращает его в очередь. Прерванная попытка при этом расходуется; после исчерпания попыток восстановление завершает задание `failed` с `lease_expired`. Ожидание HTTP-запросов и вызова ML идёт параллельно. Предел 20 с вместе с перечитыванием оставляет worker запас до `stop_grace_period: 30s` сервиса `backend` в Compose; `HTTP_SHUTDOWN_TIMEOUT` тоже держите заметно меньше 30 с.

На Windows консольному процессу после `taskkill` без `/F` или закрытия окна консоли даётся около 5 с, затем он завершается принудительно. Поэтому для backend на хосте держите `PREDICTION_JOB_SHUTDOWN_TIMEOUT` небольшим или останавливайте его через Ctrl+C. Принудительное завершение не оставляет частичной публикации: незавершённая транзакция откатывается, а задание вернёт восстановление после истечения аренды.

### Ограничения очереди

- `failed` окончателен: `UNIQUE (forecast_version_id, route_id)` действует во всех статусах, а запроса сброса нет. Повторная постановка возвращает то же задание; пересчитать пару можно только в другой версии прогноза, то есть с другими артефактами или периодом.
- `ml_unavailable` включает и занятость Python: он строит один ответ за раз, поэтому одновременный вызов — healthcheck `ml/compose.yaml`, проверка `register-forecast-version` или второй backend — может отнять попытку. По этой же причине по умолчанию работает один цикл захвата.
- Смену комплекта ML без смены версии — пересборку ML, другой режим или поколение рецепта — открытый шлюз не замечает: первое захваченное задание активной версии окончательно завершается `ml_version_mismatch`, и только затем шлюз закрывается. После такой смены перезапустите backend либо зарегистрируйте и активируйте версию нового комплекта до постановки заданий.
- Восстановление применяет лимит попыток и задержку процесса, который его выполняет. Все процессы с общей БД, включая контейнер backend, должны использовать одинаковые `PREDICTION_JOB_MAX_ATTEMPTS` и `PREDICTION_JOB_RETRY_DELAY`. Compose передаёт их контейнеру из `.env`, поэтому backend на хосте с тем же `.env` применяет те же значения; не переопределяйте их окружением только одного процесса.
- Compose пока не передаёт контейнеру backend `ML_GRPC_*` и остальные `PREDICTION_JOB_*`: для них действуют значения по умолчанию, и ML ищется по `127.0.0.1:50051` внутри своего контейнера. Проверка шлюза не проходит, и контейнер заданий не захватывает; расчёт выполняет backend на хосте ([порядок](../docs/development.md#предварительный-расчёт)).

### Постановка заданий

Команда `cmd/enqueue-prediction-jobs` ставит задания версии для всех маршрутов с `forecast_enabled` — предварительный расчёт до появления HTTP API. Сама она ML не вызывает: расчёт выполняет worker запущенного backend. Как и регистрация версии, команда работает на хосте с Go и в образ не входит. Цель Make — `make prediction-jobs-enqueue`, её переменные приведены в таблице.

| Флаг | Цель Make | Назначение |
| --- | --- | --- |
| `-env-file` | `ENV_FILE`, по умолчанию `../.env` от `backend` | Файл окружения: подключение к PostgreSQL и `PREDICTION_JOB_QUEUE_CAPACITY` |
| `-version` | `VERSION=<uuid>` | UUID версии прогноза. По умолчанию активная; если её нет или версия не найдена, команда завершается ошибкой. Для неактивной версии команда предупреждает: шлюз worker открывается, только когда ML обслуживает активную версию, поэтому задание другой версии получит `ml_version_mismatch` и завершится `failed` |
| `-dry-run` | `DRY_RUN=1` | Ничего не записывать: для каждого маршрута показать существующее задание или его отсутствие |
| `-wait` | `WAIT=1` | После постановки опрашивать задания каждые 2 с, пока все не станут `succeeded` или `failed`, и вывести итог. Ctrl+C прекращает только ожидание: задания остаются в очереди |

Маршруты обрабатываются по возрастанию номера через `Queue.Admit`; для каждого в лог пишутся `route_number`, `job_id`, `status`, `attempt_count`, `created` и `last_error_code`, в конце — итог по статусам. Без маршрутов с прогнозом, то есть до импорта справочников, команда завершается ошибкой. Повторный запуск возвращает прежние задания и ничего не создаёт заново. Если очередь заполнена, команда сообщает об этом, продолжает с остальными маршрутами и в конце завершается с кодом 1. С `-wait` код 1 означает также, что хотя бы одно задание завершилось `failed` или ожидание прервано Ctrl+C. Позиционные аргументы и неверные флаги, включая `-version` не в формате UUID, — код 2; как виден код через `go run` и Make, описано у [регистрации версии](#версии-прогноза). Порядок запуска вместе с backend — в [инструкции разработки](../docs/development.md#предварительный-расчёт).

## Миграции

Миграция [20260926140649_init_schema.sql](migrations/20260926140649_init_schema.sql) описывает шесть таблиц: `routes`, `stops`, `routes_stops`, `forecast_versions`, `validation_predictions`, `prediction_jobs`.

Секция `Up` создаёт таблицы, ключи, ограничения и индексы. Секция `Down` удаляет таблицы в обратном порядке зависимостей. Начальные данные не добавляются. Межстрочные правила — полная сетка прогноза, неизменяемость версии и проверка текущей попытки — реализуются в Go и транзакциях.

Миграция [20260927135806_forecast_versions_artifacts_key.sql](migrations/20260927135806_forecast_versions_artifacts_key.sql) добавляет в `forecast_versions` одноимённый уникальный ключ `(model_version, dataset_version, history_end, forecast_from, forecast_to)`, `Down` удаляет его. На этом ключе основана повторяемая регистрация версии: без применённой миграции `CreateForecastVersion` завершается ошибкой.

Проверка структуры миграций из корня TramCast:

```powershell
Set-Location backend
goose -dir migrations validate
```

Если терминал уже открыт в `backend`, выполните только вторую команду. `validate` проверяет разбор файлов goose. SQL применения и отката начальной схемы также проверен на отдельной PostgreSQL 18.1, `Up` и `Down` второй миграции — на отдельной базе PostgreSQL 18.1.

Поля и ограничения определены в SQL-миграциях; общие правила версий и публикации — в [контракте проекта](../AGENTS.md#прогнозы-и-очередь). Для следующих изменений создавайте новую SQL-миграцию через `goose -dir migrations create <name> sql` и заполняйте её вручную.

Имена пакетов повторяют путь через `_`, как в Задачнике: `core_config`, `core_http_server`, `core_domain`, `routes_service`, `routes_transport_http`, `routes_sqlc`, `forecasts_service`, `forecasts_predictor_grpc`, `forecasts_worker`, `core_postgres_testdb`. При импорте псевдоним совпадает с именем пакета. Сгенерированный gRPC-пакет `forecastv1` сохраняет имя из контракта. Сервис фичи размещается в её подкаталоге `service/`. Во всех фичах обработчик вызывает сервис, а сервис — хранилище: sqlc в `routes`, `stops` и `forecasts`, `fs.FS` в `web`, книга XLSX, снимок OSM и sqlc в `catalog`. Клиент ML — не хранилище, а вычислительная зависимость: через интерфейс `Predictor` его вызывают сверка версий в `forecasts_service` и worker очереди для расчёта. Worker — такая же точка входа, как HTTP-обработчик: состояние заданий он меняет только через `forecasts_service.Queue`. Обработчик не обращается к хранилищу напрямую. Каталоги `ports/in`, `ports/out`, `adapters/in` и `adapters/out` для начального MVP не создаются.

Sqlc уже генерирует выполнение SQL-запросов. Транзакции импорта, версий и очереди, включая публикацию всех точек вместе с переводом задания в `succeeded`, собираются в сервисах фич из методов sqlc, привязанных к транзакции. Дополнительный рукописный код в `repository/postgres` нужен только там, где он выполняет отдельную задачу; обёртка над каждым методом sqlc сама по себе не требуется. Небольшие интерфейсы можно объявлять рядом с использующим их сервисом по мере необходимости.

Sqlc не создаёт пул и не управляет его жизненным циклом. `core_postgres.NewPool` возвращает `*pgxpool.Pool`, который подходит для `routes_sqlc.New(pool)`, `stops_sqlc.New(pool)`, `forecasts_sqlc.New(pool)` и `catalog_sqlc.New(pool)` из сгенерированных пакетов. Для транзакции используется `queries.WithTx(tx)` или `New(tx)`; пакеты разных фич могут работать в одной транзакции, как при импорте. Доменные типы нужны для правил и поведения приложения, а HTTP DTO — для публичного формата API; они добавляются тогда, когда отличаются от моделей хранения.

## Схема БД и генерация

Источник правды для схемы — последовательность файлов в `migrations`. Goose применяет их к БД; sqlc читает их как описание схемы вместе с файлами запросов.

В [sqlc.yaml](sqlc.yaml) настроены общие миграции и отдельные пакеты `routes_sqlc`, `stops_sqlc`, `forecasts_sqlc`, `catalog_sqlc`. Для каждого пакета выбраны `pgx/v5`, JSON-теги, интерфейс запросов и исключение неиспользуемых моделей. JSON-теги не превращают структуры БД в публичные DTO.

Из корня проекта: `make sqlc-compile` проверяет запросы, `make sqlc-generate` генерирует Go-код внутри фич. Без Make из `backend` можно выполнить `sqlc compile` и `sqlc generate`. Генерация не меняет БД; миграции применяются отдельно через `make migrate-up`.

| Фича | Файлы запросов | Назначение |
| --- | --- | --- |
| routes | [routes.sql](internal/features/routes/repository/postgres/queries/routes.sql), [route_stops.sql](internal/features/routes/repository/postgres/queries/route_stops.sql) | Чтение и импорт маршрутов, варианты и упорядоченные остановки, геометрия всех вариантов для карты |
| stops | [stops.sql](internal/features/stops/repository/postgres/queries/stops.sql) | Чтение и импорт остановок |
| forecasts | [versions.sql](internal/features/forecasts/repository/postgres/queries/versions.sql), [predictions.sql](internal/features/forecasts/repository/postgres/queries/predictions.sql), [jobs.sql](internal/features/forecasts/repository/postgres/queries/jobs.sql) | Версии, включая поиск по артефактам и периоду, почасовые значения и жизненный цикл очереди |
| catalog | [catalog.sql](internal/features/catalog/repository/postgres/queries/catalog.sql) | Advisory-блокировка импорта и удаление остановок, которых нет ни в книге, ни в снимке OSM и на которые нет ссылок |

Доменные Go-структуры не изменяют схему БД. Изменения уже применённой схемы оформляются новой миграцией с последующим обновлением запросов и генерацией.

## Границы транзакций

Запросы составляют сценарии для Go через `Queries.WithTx(tx)` с уровнем `READ COMMITTED`. Импорт, регистрация и активация версий и все шаги очереди (`forecasts_service.Queue`) реализованы. Любая ошибка, неожиданный результат или число изменённых строк требует отката. Сетевой вызов Python выполняется между короткими транзакциями.

- **Обычный импорт справочников:** книга и снимок OSM читаются, проверяются целиком и объединяются до `BEGIN`. Затем одна транзакция над объединённым каталогом: `LockCatalogImport` → для всех маршрутов книги и OSM по возрастанию номера `GetRouteBySourceID` и `GetRouteByNumber` (проверка конфликтов идентичности по состоянию до записи) → `UpsertRoute` для каждого из них → `EnsureRoute` для целевых маршрутов, которых нет ни в одном источнике → `ListRoutes` → `SetRouteForecastEnabled` там, где флаг отличается от целевого списка (ровно одна изменённая строка) → `UpsertStop` для остановок обоих источников по возрастанию ID источника → для каждого маршрута БД `GetRouteForUpdate` → `DeleteRouteStops` → `InsertRouteStop` → `DeleteUnusedStopsNotInCatalog` с объединённым списком ID остановок → commit, а в режиме `-dry-run` — rollback. `UpsertRoute` сохраняет внутренний ID и прежние метаданные при NULL во входе. Для `-if-empty` порядок отличается: `BEGIN` → `LockCatalogImport` → `CatalogHasData`; только для пустого каталога источники читаются и импортируются внутри той же транзакции.
- **Регистрация версии:** покрытие маршрутов (`ListRoutes`) заранее читается в транзакции `READ ONLY`. Затем короткая транзакция `READ COMMITTED`: `CreateForecastVersion` с `ON CONFLICT ON CONSTRAINT forecast_versions_artifacts_key DO NOTHING` → при `pgx.ErrNoRows`, то есть если версия с теми же артефактами и периодом уже есть, отдельный запрос `GetForecastVersionByArtifacts` со свежим снимком, а не SELECT в том же выражении → commit. В `-dry-run` выполняется только `GetForecastVersionByArtifacts` в транзакции `READ ONLY`, которая откатывается.
- **Активная версия:** `LockForecastVersionsForActivation` → `GetForecastVersion` → `DeactivateForecastVersions` → `ActivateForecastVersion` → commit. Если версия не найдена, откатить транзакцию, сохранив прежнюю активную версию; уже активная версия — rollback без записи. Блокировка таблицы сериализует переключения и ненадолго задерживает параллельную регистрацию.
- **Приём задания:** до транзакции приёма в транзакции `READ ONLY` проверить `GetForecastVersion` и `GetRouteByID` с `forecast_enabled`. Затем `LockPredictionJobAdmission` → `GetPredictionJobByRouteAndVersion` (найденное задание возвращается в любом статусе) → `CountPendingPredictionJobs` → сравнить с `PREDICTION_JOB_QUEUE_CAPACITY` → `CreatePredictionJob` → commit. Лимит учитывает `queued` и `running`; существующие задания доступны и при заполненной очереди. Блокировку таблицы брать до любых блокировок её строк. Она временно задерживает изменения очереди, поэтому транзакция должна быть короткой.
- **Конфликт вставки:** `CreatePredictionJob` возвращает `pgx.ErrNoRows` при существующей паре «версия + маршрут». Читать её нужно следующим SQL-запросом `GetPredictionJobByRouteAndVersion`, а не через SELECT в том же CTE: следующий запрос получает свежий снимок.
- **Обработчик:** `ClaimNextPredictionJob` → `GetForecastVersion` закреплённой версии → `GetRouteByID` → commit до RPC; ошибка чтения откатывает захват. Каждое продление аренды (`RenewPredictionJobLease`) и завершение ошибки (`FinishPredictionJobWithError`) — отдельная короткая транзакция с полученным `attempt_count` в `attempt_number`. Ноль изменённых строк или `pgx.ErrNoRows` означает потерю владения; старый обработчик прекращает запись.
- **Публикация:** сверить версии модели/данных ответа с закреплённой версией прогноза и проверить точную полную сетку; маршрут и служебные ID взять из контекста вызова Go, точки перевести в московские дату и час до `BEGIN`. Начать транзакцию → `LockPredictionJobForPublication` → сопоставить пакет с версией/маршрутом заблокированного задания → `CopyValidationPredictions` → проверить число вставленных точек → `CompletePredictionJob` с ровно одной изменённой строкой → commit. После захвата блокировки срок аренды повторно не проверяется: блокировка защищает публикацию до commit. Отдельно вызывать `CompletePredictionJob` нельзя. При неизвестном исходе commit — `GetPredictionJob` отдельным запросом.
- **Восстановление:** при старте worker и каждые полсрока аренды пакетами по 100 строк `RecoverExpiredPredictionJobs`, затем `FailExhaustedQueuedPredictionJobs`, каждый пакет — отдельной транзакцией. Второй запрос закрывает исчерпанные задания после уменьшения лимита попыток. Конфигурация Go проверяет лимиты попыток и аренды и неотрицательную задержку: SQL принимает неположительные значения за «нечего захватывать» или потерю владения. Для ошибки попытки Go передаёт задержку с учётом номера попытки; `RecoverExpiredPredictionJobs` принимает одну задержку на пакет, поэтому восстановление использует базовую.

`ListValidationPredictions` читает `[from, to)` по локальным парам дата/час. Go проверяет границы внутри версии, выравнивание и полноту сетки; нулевые значения сохраняются. Запросов изменения опубликованного прогноза и параметров версии нет.

Для SQL очереди проверены `sqlc compile`, генерация в отдельном временном каталоге, 20 проверок сценариев на PostgreSQL 18.1 и параллельные сеансы: пропуск заблокированного задания, истечение аренды во время ожидания блокировки и публикация под блокировкой одновременно с восстановлением. Go-очередь и worker покрыты юнит-тестами на заглушках. Интеграционные тесты ([сценарии](#запуск)) запускаются только с `TRAMCAST_TEST_DATABASE_URL` и прошли на отдельной PostgreSQL 18.1 с `-race`: параллельный приём и лимит очереди, захват с `SKIP LOCKED`, истечение аренды и восстановление, отказ устаревшей попытке, атомарная публикация 1 464 строк, откат при конфликтах, задержки повторов 30 с и 2 мин, восстановление пакетами, worker целиком с заглушкой ML, включая расчёт дольше аренды и проверку новой активной версии перед захватом её заданий.

Предварительный расчёт целиком проверен на временной PostgreSQL 18.1 с replay 030 и backend на хосте Windows: 10 заданий `succeeded` с первой попытки, 14 640 строк совпали с `ml/bundles/030/forecast.csv` построчно, повторная постановка вернула те же задания. После активации другой версии при остановленном ML шлюз закрылся до первого захвата: все 10 её заданий остались в `queued` без попыток, пока ML был недоступен и пока он обслуживал другой комплект (`ml_version_mismatch` пробы). После возврата активности версии 030 шлюз открылся, а задания неактивной версии завершились окончательно с `ml_version_mismatch`, не затронув строки 030. Остановка ML без работы в очереди не вызвала ни захватов, ни ошибок. Остановка по Ctrl+C завершилась с кодом 0 записями `prediction job worker stopped` и `application stopped`; ранее проверена и остановка через `taskkill` без `/F`.

Для версий на отдельной базе PostgreSQL 18.1 после `Up`, `Down` и повторного `Up` новой миграции SQL-запросами проверены: путь `ON CONFLICT` — тот же момент, записанный в UTC, попадает в ограничение, строка остаётся одна; две параллельные регистрации — одна строка, вторая ждёт commit первой и затем находит её отдельным запросом; две параллельные активации — сериализуются, активна ровно одна версия, а активация без снятия прежней падает на `forecast_versions_one_active_idx`. Команда целиком проверена на временном контейнере PostgreSQL 18.1 с запущенным replay 030: отказ без `-allow-replay` и ошибки метаданных до подключения к базе, пробный запуск без записи, регистрация, повторы без дублей, активация и переключение версий (активна ровно одна), восемь одновременных регистраций и десять одновременных активаций, несовпадение ID (`ml_version_mismatch`), недоступный ML (`ml_unavailable`), пустой каталог, UTF-16 и BOM, ошибка активации после регистрации (версия остаётся зарегистрированной и неактивной); через Make из PowerShell — те же основные сценарии.

## gRPC-контракт

Общий [контракт `ForecastService.Predict`](../proto/README.md) хранится в корневом `proto/`. Сгенерированные сообщения и gRPC-интерфейсы Go размещаются в `internal/gen/tramcast/forecast/v1`, а клиент, преобразование типов и проверка ответа — в `internal/features/forecasts/predictor/grpc`. Команды генерации приведены рядом с контрактом.

Go передаёт только номер маршрута и границы периода; часовой пояс фиксирован как `Europe/Moscow`. Python возвращает почасовые точки и версии фактически использованных модели и данных. `job_id`, `forecast_version_id` и `attempt_number` остаются в контексте обработчика Go. При несовпадении версий артефактов с ожидаемыми результат не сохраняется, задание завершается неповторяемой ошибкой.

Клиент `forecasts_predictor_grpc` используют команда регистрации версии и обработчик очереди. `New(addr, timeout)` создаёт соединение без TLS для loopback или внутренней сети и отключает повторы gRPC: бюджет попыток принадлежит очереди PostgreSQL. Соединение открывается при первом вызове, поэтому недоступный сервер проявляется как `ml_unavailable`. Пауза между попытками переподключения ограничена 10 с вместо 120 с по умолчанию в gRPC, поэтому после перезапуска ML вызовы снова доходят до него в пределах примерно 10 с; тайм-аут одной попытки соединения остаётся стандартным, 20 с. Параметры, переданные вызывающим кодом, имеют приоритет. Каждый `Predict` получает собственный deadline `timeout` (в команде — `ML_GRPC_TIMEOUT`) поверх контекста вызывающего кода.

- **До отправки:** положительный номер маршрута, заданные ожидаемые версии, `From < To`, обе границы на целых московских часах, от 1 до `MaxHours` (1 464) часов. Иначе — `ml_invalid_request`, сервер не вызывается.
- **Ответ:** обе версии непустые, без пробелов по краям и точно совпадают с ожидаемыми `ModelVersion` и `DatasetVersion` запроса; только затем проверяются точки: их число равно числу часов, у точки `i` `hour_start` ровно `From + i` часов без наносекунд, `boardings` присутствует и неотрицателен. Несовпадение версий — `ml_version_mismatch`, остальные нарушения — `ml_invalid_response`; ответ отклоняется целиком. Точки возвращаются с `HourStart` в `core_domain.Moscow`.
- **Ошибки:** все ошибки `Predict` имеют тип `*Error` с кодом для `last_error_code`, признаком повтора и исходной ошибкой для логов. Решения не зависят от текста сообщения сервера; `status.Code` через `Unwrap` возвращает исходный статус gRPC.

| Статус gRPC | Код | Повтор |
| --- | --- | --- |
| `UNAVAILABLE` | `ml_unavailable` | да |
| `DEADLINE_EXCEEDED` | `ml_deadline_exceeded` | да |
| `CANCELLED` | `ml_cancelled` | нет; после отмены из-за остановки Go или потери аренды обработчик очереди ничего не записывает |
| `INVALID_ARGUMENT` / `NOT_FOUND` / `FAILED_PRECONDITION` / `RESOURCE_EXHAUSTED` | `ml_invalid_argument` / `ml_not_found` / `ml_failed_precondition` / `ml_resource_exhausted` | нет |
| Остальные статусы | `ml_internal` | нет |

Против запущенного replay 030 клиент проверен интеграционным тестом: маршрут 1 на весь горизонт — 1 464 часа с суммой 1 103 274, маршрут 5 — нули.

## Локальная инфраструктура

PostgreSQL и команды запуска описаны в [инструкции разработки](../docs/development.md). Секреты задаются в корневом `.env`; файлы БД — в `out/pgdata` и исключены из Git.

Исходники фронтенда лежат в соседнем каталоге `TramCast/frontend`. Go раздаёт готовую сборку с диска по пути из `WEB_DIR`; директория `backend/web` и встраивание сборки через `go:embed` не нужны. `go:embed` в backend не используется: снимок OSM команда импорта тоже читает с диска, по пути из `CATALOG_OSM_FILE`.
