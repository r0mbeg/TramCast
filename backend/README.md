# Backend TramCast

Go-приложение TramCast. Запущенная основа — сервер Gin, конфигурация из окружения, логирование через `slog` и пул PostgreSQL. Готовы чтение справочников, их импорт из XLSX и снимка OpenStreetMap, раздача сборки фронтенда; API прогнозов и обработка заданий добавляются следующим этапом.

Готовы первая SQL-миграция, 40 именованных запросов, сгенерированные пакеты sqlc/gRPC и модуль Go 1.26.8. `cmd/tramcast/main.go` собирает конфигурацию, логгер, пул, обработчики фич и HTTP-сервер. Транзакционные сервисы прогнозов пока не реализованы.

## Запуск

В Docker весь проект запускается из корня командой `docker compose up --build -d --wait` после настройки `.env`. Очищенная книга справочников и снимок OSM входят в образ. Compose собирает Go и фронтенд, дожидается PostgreSQL, применяет миграции и загружает справочники в пустую БД перед запуском HTTP. Инструкция — в [документации разработки](../docs/development.md#запуск-приложения-в-docker).

Из корня проекта после настройки `.env` и запуска PostgreSQL:

```text
make run-backend
```

Напрямую из `backend`: `go run ./cmd/tramcast -env-file ../.env`. Без `-env-file` приложение читает только окружение процесса. Подробные настройки и команды БД — в [инструкции разработки](../docs/development.md).

Пул проверяется через `Ping` с таймаутом до запуска HTTP. При ошибке приложение завершается с ненулевым кодом. По SIGINT/SIGTERM сервер прекращает приём соединений и ждёт активные запросы до `HTTP_SHUTDOWN_TIMEOUT`, затем закрывается пул. Ошибка привязки HTTP-порта также завершает приложение.

| Маршрут | Назначение |
| --- | --- |
| `GET/HEAD /healthz` | HTTP работает: `200` |
| `GET/HEAD /readyz` | PostgreSQL отвечает на `Ping`: `200`, при ошибке или таймауте — `503` |
| `GET /api/routes` | `{"routes": [...]}` — маршруты по номеру; `name` может быть `null` |
| `GET /api/routes/geometry` | GeoJSON `FeatureCollection`: `LineString` на каждый вариант движения, координаты `[lon, lat]` по порядку остановок; свойство `source` — `workbook` или `osm` |
| `GET /api/routes/{route_id}/stops` | `{"route_id", "patterns": [...]}` — варианты движения и остановки по порядку; `400 invalid_route_id`, `404 route_not_found` |
| `GET /api/stops` | `{"stops": [...]}` — весь справочник остановок |
| Остальные GET/HEAD | Файлы из `WEB_DIR`; при переходе в браузере пути без расширения получают `index.html`. `/api/...`, отсутствующие файлы и страницы без файла для JSON-клиента (`Accept: application/json` без `text/html`) — `404` |

Readiness проверяет подключение, а применение миграций остаётся отдельным шагом. Логи запросов содержат сгенерированный `request_id`, метод, путь, статус и длительность. Параметры URL, заголовки и тела запросов не записываются; клиент получает request ID в `X-Request-ID`.

Ошибки API имеют вид `{"error": "<код>"}`. Обработчик передаёт внутреннюю ошибку через `core_http_server.WriteInternalError`: клиент получает `500 internal_server_error`, а текст ошибки попадает в строку лога запроса уровня ERROR.

Проверки из корня проекта: `go -C backend test ./...`, `go -C backend build ./...` и `make tidy-backend-check`. Тесты проверяют конфигурацию, логирование, совместимость пула с sqlc, диагностические маршруты, обработку panic, остановку активных запросов, сервис и обработчики справочников, раздачу статики, чтение и проверку книги справочников и снимка OSM (тесты читают снимок из `data/osm/` по относительному пути), объединение источников и транзакцию импорта на заглушке. PostgreSQL для этих тестов не требуется.

## Импорт справочников

Для автоматического первого запуска есть флаг `-if-empty`: транзакция с уровнем `READ COMMITTED` получает общую блокировку импорта, затем отдельным запросом проверяет `routes`, `stops` и `routes_stops`. Если хотя бы одна таблица непустая, команда успешно завершается с сообщением о пропуске, не открывая источники и не расходуя identity. Для пустого каталога чтение, проверка и запись выполняются под той же блокировкой; ошибка откатывает транзакцию. Два параллельных первых запуска не выполняют импорт дважды. Частично заполненная БД также пропускается: для восстановления или обновления нужен обычный явный импорт. В Compose этот режим включён у `catalog-init`.

```text
make import-catalog-dry-run
make import-catalog
```

Команда `cmd/import-catalog` читает очищенную книгу по пути `CATALOG_FILE` (по умолчанию `./data/catalog/catalog.xlsx`) и снимок OpenStreetMap маршрутов 17, 25, 26, 28, 50 по пути `CATALOG_OSM_FILE` (по умолчанию `./data/osm/tram_routes.json`). Оба файла хранятся в Git и включаются в образ приложения. При явном `-env-file` относительные пути, включая значения по умолчанию и переопределения окружением, считаются от папки этого файла; без флага — от рабочего каталога. Абсолютные пути сохраняются. Обе переменные должны быть непустыми: импорт заменяет всю географию и без снимка очистил бы позиции маршрутов OSM. Основной сервер загружает ту же конфигурацию, но файлы не открывает.

Флаг `-env-file` задаёт файл окружения; `-file` и `-osm-file` заменяют пути книги и снимка для разового запуска, причём относительные пути в этих двух флагах считаются от рабочего каталога процесса. `-dry-run` выполняет импорт и откатывает транзакцию. Позиционные аргументы не принимаются: путь без `-file` завершает команду с кодом 2, иначе флаги после него, включая `-dry-run`, были бы молча пропущены. Напрямую из `backend`: `go run ./cmd/import-catalog -env-file ../.env`. Происхождение снимка, дата данных, лицензия ODbL 1.0 и порядок обновления описаны в [README снимка](../data/osm/README.md).

Фича `catalog` устроена по общей схеме: команда → `catalog/service` → хранилища. `catalog/repository/xlsx` открывает книгу через excelize с исходными значениями ячеек, находит листы `Маршруты GTFS_ROUTES`, `Остановки GTFS_STOPS`, `Порядок_остановок GTFS_TRIPS_ST` и колонки по именам в первых двух строках. `catalog/repository/osm` (`catalog_osm_repository`) открывает файл снимка по переданному пути и декодирует ответ Overpass (`Decode`) в типизированную модель с `int64` ID, тоже без смысловых проверок. Сервис проверяет всю книгу и весь снимок до записи, включая пустые обязательные листы, и при любой проблеме любого источника выводит общий список без изменения БД: для книги — «лист, строка, описание», для OSM с relation и номером участника. Затем объединяет источники с приоритетом книги: маршрут с листа маршрутов книги берётся из книги, его данные OSM пропускаются с предупреждением. Каталог заменяется одной транзакцией; запись идёт через небольшие интерфейсы запросов, поэтому вся логика транзакции покрыта юнит-тестами на заглушке в памяти; общие правила импорта закреплены в [контракте](../AGENTS.md#справочники).

Команда пишет в лог абсолютные пути книги и снимка (`file`, `osm_file`) при старте и итог в конце: число маршрутов, остановок и позиций книги, дата снимка OSM (`timestamp_osm_base`) и число записанных из него маршрутов, остановок и позиций, созданные маршруты без географии, изменённые флаги прогноза, очищенные позиции и удалённые остановки. Пропущенные в пользу книги маршруты OSM видны в предупреждениях. Повторный запуск на тех же книге и снимке сохраняет ID и данные. Каждый импорт, в том числе пробный, расходует значения identity (`INSERT … ON CONFLICT` вычисляет следующий ID до проверки конфликта), поэтому новые строки могут получать ID с пропусками. Пропуск через `-if-empty` значения identity не расходует.

## Первая миграция

Миграция [20260926140649_init_schema.sql](migrations/20260926140649_init_schema.sql) описывает шесть таблиц: `routes`, `stops`, `routes_stops`, `forecast_versions`, `validation_predictions`, `prediction_jobs`.

Секция `Up` создаёт таблицы, ключи, ограничения и индексы. Секция `Down` удаляет таблицы в обратном порядке зависимостей. Начальные данные не добавляются. Межстрочные правила — полная сетка прогноза, неизменяемость версии и проверка текущей попытки — реализуются в Go и транзакциях.

Проверка структуры миграции из корня TramCast:

```powershell
Set-Location backend
goose -dir migrations validate
```

Если терминал уже открыт в `backend`, выполните только вторую команду. `validate` проверяет разбор файлов goose. SQL применения и отката также проверен на отдельной PostgreSQL 18.1.

Поля и ограничения определены в SQL-миграциях; общие правила версий и публикации — в [контракте проекта](../AGENTS.md#прогнозы-и-очередь--контракт-будущей-реализации). Для следующих изменений создавайте новую SQL-миграцию через `goose -dir migrations create <name> sql` и заполняйте её вручную.

Имена пакетов повторяют путь через `_`, как в Задачнике: `core_config`, `core_http_server`, `core_domain`, `routes_service`, `routes_transport_http`, `routes_sqlc`. При импорте псевдоним совпадает с именем пакета. Сгенерированный gRPC-пакет `forecastv1` сохраняет имя из контракта. Сервис фичи размещается в её подкаталоге `service/`. Во всех фичах обработчик вызывает сервис, а сервис — хранилище: sqlc в `routes`, `stops`, `forecasts`, `fs.FS` в `web`, книга XLSX, снимок OSM и sqlc в `catalog`. Обработчик не обращается к хранилищу напрямую. Каталоги `ports/in`, `ports/out`, `adapters/in` и `adapters/out` для начального MVP не создаются.

Sqlc уже генерирует выполнение SQL-запросов. Дополнительный рукописный код в `repository/postgres` нужен там, где он выполняет отдельную задачу: преобразование модели, обработку ошибок или транзакцию публикации всех точек вместе с переводом задания в `succeeded`. Обёртка над каждым методом sqlc сама по себе не требуется. Небольшие интерфейсы можно объявлять рядом с использующим их сервисом по мере необходимости.

Sqlc не создаёт пул и не управляет его жизненным циклом. `core_postgres.NewPool` возвращает `*pgxpool.Pool`, который подходит для `routes_sqlc.New(pool)`, `stops_sqlc.New(pool)`, `forecasts_sqlc.New(pool)` и `catalog_sqlc.New(pool)` из сгенерированных пакетов. Для транзакции используется `queries.WithTx(tx)` или `New(tx)`; пакеты разных фич могут работать в одной транзакции, как при импорте. Доменные типы нужны для правил и поведения приложения, а HTTP DTO — для публичного формата API; они добавляются тогда, когда отличаются от моделей хранения.

## Схема БД и генерация

Источник правды для схемы — последовательность файлов в `migrations`. Goose применяет их к БД; sqlc читает их как описание схемы вместе с файлами запросов.

В [sqlc.yaml](sqlc.yaml) настроены общие миграции и отдельные пакеты `routes_sqlc`, `stops_sqlc`, `forecasts_sqlc`, `catalog_sqlc`. Для каждого пакета выбраны `pgx/v5`, JSON-теги, интерфейс запросов и исключение неиспользуемых моделей. JSON-теги не превращают структуры БД в публичные DTO.

Из корня проекта: `make sqlc-compile` проверяет запросы, `make sqlc-generate` генерирует Go-код внутри фич. Без Make из `backend` можно выполнить `sqlc compile` и `sqlc generate`. Генерация не меняет БД; миграции применяются отдельно через `make migrate-up`.

| Фича | Файлы запросов | Назначение |
| --- | --- | --- |
| routes | [routes.sql](internal/features/routes/repository/postgres/queries/routes.sql), [route_stops.sql](internal/features/routes/repository/postgres/queries/route_stops.sql) | Чтение и импорт маршрутов, варианты и упорядоченные остановки, геометрия всех вариантов для карты |
| stops | [stops.sql](internal/features/stops/repository/postgres/queries/stops.sql) | Чтение и импорт остановок |
| forecasts | [versions.sql](internal/features/forecasts/repository/postgres/queries/versions.sql), [predictions.sql](internal/features/forecasts/repository/postgres/queries/predictions.sql), [jobs.sql](internal/features/forecasts/repository/postgres/queries/jobs.sql) | Версии, почасовые значения и жизненный цикл очереди |
| catalog | [catalog.sql](internal/features/catalog/repository/postgres/queries/catalog.sql) | Advisory-блокировка импорта и удаление остановок, которых нет ни в книге, ни в снимке OSM и на которые нет ссылок |

Доменные Go-структуры не изменяют схему БД. Изменения уже применённой схемы оформляются новой миграцией с последующим обновлением запросов и генерацией.

## Границы транзакций

Обновление истории ML выполняется отдельным офлайн-пайплайном. Его запуск,
передача пакета и согласование версий описаны в
[инструкции интеграции ML](../ml/docs/INTEGRATION.md#как-подключить-обновление-данных).
RPC `Predict` получает прогноз из закреплённого комплекта; он не запускает
подготовку данных. Автоматический запуск builder и регистрация его версии в Go
пока не реализованы.

Запросы составляют сценарии для Go через `Queries.WithTx(tx)` с уровнем `READ COMMITTED`. Импорт реализован; сервисы версий, очереди и публикации ещё предстоит собрать из готовых SQL-запросов. Любая ошибка, неожиданный результат или число изменённых строк требует отката. Сетевой вызов Python должен выполняться между короткими транзакциями.

- **Обычный импорт справочников:** книга и снимок OSM читаются, проверяются целиком и объединяются до `BEGIN`. Затем одна транзакция над объединённым каталогом: `LockCatalogImport` → для всех маршрутов книги и OSM по возрастанию номера `GetRouteBySourceID` и `GetRouteByNumber` (проверка конфликтов идентичности по состоянию до записи) → `UpsertRoute` для каждого из них → `EnsureRoute` для целевых маршрутов, которых нет ни в одном источнике → `ListRoutes` → `SetRouteForecastEnabled` там, где флаг отличается от целевого списка (ровно одна изменённая строка) → `UpsertStop` для остановок обоих источников по возрастанию ID источника → для каждого маршрута БД `GetRouteForUpdate` → `DeleteRouteStops` → `InsertRouteStop` → `DeleteUnusedStopsNotInCatalog` с объединённым списком ID остановок → commit, а в режиме `-dry-run` — rollback. `UpsertRoute` сохраняет внутренний ID и прежние метаданные при NULL во входе. Для `-if-empty` порядок отличается: `BEGIN` → `LockCatalogImport` → `CatalogHasData`; только для пустого каталога источники читаются и импортируются внутри той же транзакции.
- **Активная версия:** `LockForecastVersionsForActivation` → проверить существование выбранной версии → `DeactivateForecastVersions` → `ActivateForecastVersion` → commit. Если версия не найдена, откатить транзакцию, сохранив прежнюю активную версию.
- **Приём задания:** сначала можно прочитать существующее задание без блокировки. Для нового: `LockPredictionJobAdmission` → повторно проверить существование → `CountPendingPredictionJobs` → сравнить с лимитом → `CreatePredictionJob` → commit. Лимит учитывает `queued` и `running`; существующие задания доступны и при заполненной очереди. Блокировку таблицы брать до любых блокировок её строк. Она временно задерживает изменения очереди, поэтому транзакция должна быть короткой.
- **Конфликт вставки:** `CreatePredictionJob` возвращает `pgx.ErrNoRows` при существующей паре «версия + маршрут». Читать её нужно следующим SQL-запросом `GetPredictionJobByRouteAndVersion`, а не через SELECT в том же CTE: следующий запрос получает свежий снимок.
- **Обработчик:** `ClaimNextPredictionJob` атомарно захватывает задание; commit до RPC. Каждое продление аренды и завершение ошибки передаёт полученный `attempt_count` как `attempt_number`. Ноль изменённых строк или `pgx.ErrNoRows` означает потерю владения; старый обработчик прекращает запись.
- **Публикация:** сверить версии модели/данных ответа с закреплённой версией прогноза и проверить точную полную сетку; маршрут и служебные ID взять из контекста вызова Go. Начать транзакцию → `LockPredictionJobForPublication` → сопоставить пакет с версией/маршрутом заблокированного задания → `CopyValidationPredictions` → проверить число вставленных точек → `CompletePredictionJob` с ровно одной изменённой строкой → commit. После захвата блокировки срок аренды повторно не проверяется: блокировка защищает публикацию до commit. Отдельно вызывать `CompletePredictionJob` нельзя.
- **Восстановление:** периодически выполнять ограниченными пакетами `RecoverExpiredPredictionJobs` и `FailExhaustedQueuedPredictionJobs`. Второй запрос закрывает исчерпанные задания после уменьшения лимита попыток. При реализации worker добавить в конфигурацию Go положительные лимиты попыток, аренды и размера пакета, неотрицательную задержку; задержку повторов вычислять с учётом номера попытки.

`ListValidationPredictions` читает `[from, to)` по локальным парам дата/час. Go проверяет границы внутри версии, выравнивание и полноту сетки; нулевые значения сохраняются. Запросов изменения опубликованного прогноза и параметров версии нет.

Проверены `sqlc compile`, генерация в отдельном временном каталоге, 20 проверок сценариев на PostgreSQL 18.1 и параллельные сеансы: пропуск заблокированного задания, истечение аренды во время ожидания блокировки и публикация под блокировкой одновременно с восстановлением. Исполняемый Go-сервис и вызов Python этими проверками не покрыты.

## gRPC-контракт

Общий [контракт `ForecastService.Predict`](../proto/README.md) хранится в корневом `proto/`. Сгенерированные сообщения и gRPC-интерфейсы Go размещаются в `internal/gen/tramcast/forecast/v1`, а клиент, преобразование типов и проверка ответа — в `internal/features/forecasts/predictor/grpc`. Команды генерации приведены рядом с контрактом; реализация клиента появится при подключении ML-сервиса.

Go передаёт только номер маршрута и границы периода; часовой пояс фиксирован как `Europe/Moscow`. Python возвращает почасовые точки и версии фактически использованных модели и данных. `job_id`, `forecast_version_id` и `attempt_number` остаются в контексте обработчика Go. При несовпадении версий артефактов с ожидаемыми результат не сохраняется, задание завершается неповторяемой ошибкой.

## Локальная инфраструктура

PostgreSQL и команды запуска описаны в [инструкции разработки](../docs/development.md). Секреты задаются в корневом `.env`; файлы БД — в `out/pgdata` и исключены из Git.

Исходники фронтенда лежат в соседнем каталоге `TramCast/frontend`. Go раздаёт готовую сборку с диска по пути из `WEB_DIR`; директория `backend/web` и встраивание сборки через `go:embed` не нужны. `go:embed` в backend не используется: снимок OSM команда импорта тоже читает с диска, по пути из `CATALOG_OSM_FILE`.
