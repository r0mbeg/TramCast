# Backend TramCast

Go-приложение TramCast. Запущенная основа — сервер Gin, конфигурация из окружения, логирование через `slog` и пул PostgreSQL. Готовы чтение справочников и раздача сборки фронтенда; API прогнозов и обработка заданий добавляются следующим этапом.

Готовы первая SQL-миграция, 36 именованных запросов, сгенерированные пакеты sqlc/gRPC и модуль Go 1.26.8. `cmd/tramcast/main.go` собирает конфигурацию, логгер, пул, обработчики фич и HTTP-сервер. Транзакционные сервисы прогнозов пока не реализованы.

## Запуск

Из корня проекта после настройки `.env` и запуска PostgreSQL:

```text
make run-backend
```

Напрямую из `backend`: `go run ./cmd/tramcast -env-file ../.env`. Без `-env-file` приложение читает только окружение процесса. Подробные настройки и команды БД — в [инструкции разработки](../docs/development.md).

Пул проверяется через `Ping` с таймаутом до запуска HTTP. При ошибке приложение завершается с ненулевым кодом. По SIGINT/SIGTERM сервер прекращает приём соединений и ждёт активные запросы до `HTTP_SHUTDOWN_TIMEOUT`, затем закрывается пул. Ошибка привязки HTTP-порта также завершает приложение.

| Маршрут | Назначение |
| --- | --- |
| `GET/HEAD /healthz` | HTTP работает: `200` |
| `GET/HEAD /readyz` | PostgreSQL отвечает на `Ping`: `200`, при ошибке или таймауте — `503` |
| `GET /api/routes` | `{"routes": [...]}` — маршруты по номеру; `name` может быть `null` |
| `GET /api/routes/{route_id}/stops` | `{"route_id", "patterns": [...]}` — варианты движения и остановки по порядку; `400 invalid_route_id`, `404 route_not_found` |
| `GET /api/stops` | `{"stops": [...]}` — весь справочник остановок |
| Остальные GET/HEAD | Файлы из `WEB_DIR`; при переходе в браузере пути без расширения получают `index.html`. `/api/...`, отсутствующие файлы и страницы без файла для JSON-клиента (`Accept: application/json` без `text/html`) — `404` |

Readiness проверяет подключение, а применение миграций остаётся отдельным шагом. Логи запросов содержат сгенерированный `request_id`, метод, путь, статус и длительность. Параметры URL, заголовки и тела запросов не записываются; клиент получает request ID в `X-Request-ID`.

Ошибки API имеют вид `{"error": "<код>"}`. Обработчик передаёт внутреннюю ошибку через `core_http_server.WriteInternalError`: клиент получает `500 internal_server_error`, а текст ошибки попадает в строку лога запроса уровня ERROR.

Проверки из корня проекта: `go -C backend test ./...`, `go -C backend build ./...` и `make tidy-backend-check`. Тесты проверяют конфигурацию, логирование, совместимость пула с sqlc, диагностические маршруты, обработку panic, остановку активных запросов, сервис и обработчики справочников и раздачу статики. PostgreSQL для этих тестов не требуется.

## Первая миграция

Миграция [20260926140649_init_schema.sql](migrations/20260926140649_init_schema.sql) описывает шесть таблиц: `routes`, `stops`, `routes_stops`, `forecast_versions`, `validation_predictions`, `prediction_jobs`.

Секция `Up` создаёт таблицы, ключи, ограничения и индексы. Секция `Down` удаляет таблицы в обратном порядке зависимостей. Начальные данные не добавляются. Межстрочные правила — полная сетка прогноза, неизменяемость версии и проверка текущей попытки — реализуются в Go и транзакциях.

Проверка структуры миграции из корня TramCast:

```powershell
Set-Location backend
goose -dir migrations validate
```

Если терминал уже открыт в `backend`, выполните только вторую команду. `validate` проверяет разбор файлов goose. SQL применения и отката также проверен на отдельной PostgreSQL 18.1.

Подробные поля и правила описаны в [контракте проекта](../AGENTS.md#предметная-область). Для следующих изменений создавайте новую SQL-миграцию через `goose -dir migrations create <name> sql` и заполняйте её вручную.

| Каталог | Назначение |
| --- | --- |
| `cmd/tramcast` | `main.go`: конфигурация → slog → pgxpool → обработчики фич → HTTP; завершение по сигналу. |
| `internal/core/config` | Чтение окружения и явного dotenv-файла, проверка обязательных значений и лимитов. |
| `internal/core/logger` | Создание `*slog.Logger` с уровнем и форматом text/json, вывод в stdout. |
| `internal/core/domain` | Пока без типов. Общие бизнес-типы появятся при необходимости; структуры sqlc здесь не дублируются. |
| `internal/core/repository/postgres` | Создание и проверка обычного `*pgxpool.Pool`; запросы конкретных фич располагаются у фич. |
| `internal/core/transport/http` | Gin, middleware, диагностические маршруты, формат ошибок, таймауты и завершение HTTP-сервера. |
| `internal/features/routes` | Операции над маршрутами и порядком остановок, включая таблицу `routes_stops`. Сервис проверяет маршрут и группирует остановки по вариантам. |
| `internal/features/stops` | Операции над справочником остановок. Сервис пока передаёт чтение списка в sqlc; логика появится здесь же. |
| `internal/features/forecasts` | Версии, почасовые значения и задания расчёта; обращение к модели. |
| `internal/features/web` | Раздача сборки из `WEB_DIR`. Сервис поверх `fs.FS` выбирает файл, `index.html` для клиентских маршрутов, тип, кеширование и ETag по содержимому для файлов вне `assets/`; обработчик пишет ответ через `http.ServeContent`. |
| `service` внутри фичи | Сценарии и правила фичи; зависит от небольшого интерфейса хранилища (sqlc `*Queries` или `fs.FS`). |
| `transport/http` внутри фичи | REST-обработчики и DTO этой фичи. |
| `repository/postgres/queries` внутри фичи | Написанные вручную именованные SQL-запросы. |
| `repository/postgres/sqlc` внутри фичи | Сгенерированные Go-структуры и методы для `pgx/v5`; вручную не редактируются. |
| `forecasts/predictor/grpc` | Клиент Python-сервиса и преобразование Protobuf-сообщений. |
| `forecasts/worker` | Фоновый цикл обработки заданий в том же Go-процессе. |

Имена пакетов повторяют путь через `_`, как в Задачнике: `core_config`, `core_http_server`, `routes_service`, `routes_transport_http`, `routes_sqlc`. При импорте псевдоним совпадает с именем пакета. Сгенерированный gRPC-пакет `forecastv1` сохраняет имя из контракта. Сервис фичи размещается в её подкаталоге `service/`. Во всех фичах обработчик вызывает сервис, а сервис — хранилище: sqlc в `routes`, `stops`, `forecasts` и `fs.FS` в `web`. Обработчик не обращается к хранилищу напрямую. Каталоги `ports/in`, `ports/out`, `adapters/in` и `adapters/out` для начального MVP не создаются.

Sqlc уже генерирует выполнение SQL-запросов. Дополнительный рукописный код в `repository/postgres` нужен там, где он выполняет отдельную задачу: преобразование модели, обработку ошибок или транзакцию публикации всех точек вместе с переводом задания в `succeeded`. Обёртка над каждым методом sqlc сама по себе не требуется. Небольшие интерфейсы можно объявлять рядом с использующим их сервисом по мере необходимости.

Sqlc не создаёт пул и не управляет его жизненным циклом. `core_postgres.NewPool` возвращает `*pgxpool.Pool`, который подходит для `routes_sqlc.New(pool)`, `stops_sqlc.New(pool)` и `forecasts_sqlc.New(pool)` из сгенерированных пакетов. Для транзакции используется `queries.WithTx(tx)`. Доменные типы нужны для правил и поведения приложения, а HTTP DTO — для публичного формата API; они добавляются тогда, когда отличаются от моделей хранения.

## Схема БД и генерация

Источник правды для схемы — последовательность файлов в `migrations`. Goose применяет их к БД; sqlc читает их как описание схемы вместе с файлами запросов.

В [sqlc.yaml](sqlc.yaml) настроены общие миграции и отдельные пакеты `routes_sqlc`, `stops_sqlc`, `forecasts_sqlc`. Для каждого пакета выбраны `pgx/v5`, JSON-теги, интерфейс запросов и исключение неиспользуемых моделей. JSON-теги не превращают структуры БД в публичные DTO.

Из корня проекта: `make sqlc-compile` проверяет запросы, `make sqlc-generate` генерирует Go-код внутри фич. Без Make из `backend` можно выполнить `sqlc compile` и `sqlc generate`. Генерация не меняет БД; миграции применяются отдельно через `make migrate-up`.

| Фича | Файлы запросов | Назначение |
| --- | --- | --- |
| routes | [routes.sql](internal/features/routes/repository/postgres/queries/routes.sql), [route_stops.sql](internal/features/routes/repository/postgres/queries/route_stops.sql) | Чтение и импорт маршрутов, варианты и упорядоченные остановки |
| stops | [stops.sql](internal/features/stops/repository/postgres/queries/stops.sql) | Чтение и импорт остановок |
| forecasts | [versions.sql](internal/features/forecasts/repository/postgres/queries/versions.sql), [predictions.sql](internal/features/forecasts/repository/postgres/queries/predictions.sql), [jobs.sql](internal/features/forecasts/repository/postgres/queries/jobs.sql) | Версии, почасовые значения и жизненный цикл очереди |

Доменные Go-структуры не изменяют схему БД. Изменения уже применённой схемы оформляются новой миграцией с последующим обновлением запросов и генерацией.

## Границы транзакций

Запросы составляют сценарии, которые Go выполняет через `Queries.WithTx(tx)` с уровнем `READ COMMITTED`. Любая ошибка, неожиданный результат или число изменённых строк требует отката. Сетевой вызов Python выполняется между короткими транзакциями.

- **Импорт:** прочитать и проверить XLSX до записи; `EnsureRoute` создаёт маршрут без географии, затем отдельный `GetRouteByNumber` читает его. `UpsertRoute` сохраняет внутренний ID, номер, доступность прогноза и прежние метаданные при NULL во входе. `UpsertStop` обновляет остановку по ID источника. Для замены позиций: `GetRouteForUpdate` → `DeleteRouteStops` → `InsertRouteStop` для всего проверенного списка. При импорте нескольких маршрутов блокировать их в одном порядке. Импортёр пока не реализован.
- **Активная версия:** `LockForecastVersionsForActivation` → проверить существование выбранной версии → `DeactivateForecastVersions` → `ActivateForecastVersion` → commit. Если версия не найдена, откатить транзакцию, сохранив прежнюю активную версию.
- **Приём задания:** сначала можно прочитать существующее задание без блокировки. Для нового: `LockPredictionJobAdmission` → повторно проверить существование → `CountPendingPredictionJobs` → сравнить с лимитом → `CreatePredictionJob` → commit. Лимит учитывает `queued` и `running`; существующие задания доступны и при заполненной очереди. Блокировку таблицы брать до любых блокировок её строк. Она временно задерживает изменения очереди, поэтому транзакция должна быть короткой.
- **Конфликт вставки:** `CreatePredictionJob` возвращает `pgx.ErrNoRows` при существующей паре «версия + маршрут». Читать её нужно следующим SQL-запросом `GetPredictionJobByRouteAndVersion`, а не через SELECT в том же CTE: следующий запрос получает свежий снимок.
- **Обработчик:** `ClaimNextPredictionJob` атомарно захватывает задание; commit до RPC. Каждое продление аренды и завершение ошибки передаёт полученный `attempt_count` как `attempt_number`. Ноль изменённых строк или `pgx.ErrNoRows` означает потерю владения; старый обработчик прекращает запись.
- **Публикация:** сверить версии модели/данных ответа с закреплённой версией прогноза и проверить точную полную сетку; маршрут и служебные ID взять из контекста вызова Go. Начать транзакцию → `LockPredictionJobForPublication` → сопоставить пакет с версией/маршрутом заблокированного задания → `CopyValidationPredictions` → проверить число вставленных точек → `CompletePredictionJob` с ровно одной изменённой строкой → commit. После захвата блокировки срок аренды повторно не проверяется: блокировка защищает публикацию до commit. Отдельно вызывать `CompletePredictionJob` нельзя.
- **Восстановление:** периодически выполнять ограниченными пакетами `RecoverExpiredPredictionJobs` и `FailExhaustedQueuedPredictionJobs`. Второй запрос закрывает исчерпанные задания после уменьшения лимита попыток. Конфигурация Go проверяет положительные лимиты попыток, аренды и размера пакета, неотрицательную задержку; задержка повторов вычисляется Go с учётом номера попытки.

`ListValidationPredictions` читает `[from, to)` по локальным парам дата/час. Go проверяет границы внутри версии, выравнивание и полноту сетки; нулевые значения сохраняются. Запросов изменения опубликованного прогноза и параметров версии нет.

Проверены `sqlc compile`, генерация в отдельном временном каталоге, 20 проверок сценариев на PostgreSQL 18.1 и параллельные сеансы: пропуск заблокированного задания, истечение аренды во время ожидания блокировки и публикация под блокировкой одновременно с восстановлением. Исполняемый Go-сервис и вызов Python этими проверками не покрыты.

## gRPC-контракт

Общий [контракт `ForecastService.Predict`](../proto/README.md) хранится в корневом `proto/`. Сгенерированные сообщения и gRPC-интерфейсы Go размещаются в `internal/gen/tramcast/forecast/v1`, а клиент, преобразование типов и проверка ответа — в `internal/features/forecasts/predictor/grpc`. Команды генерации приведены рядом с контрактом; реализация клиента появится при подключении ML-сервиса.

Go передаёт только номер маршрута и границы периода; часовой пояс фиксирован как `Europe/Moscow`. Python возвращает почасовые точки и версии фактически использованных модели и данных. `job_id`, `forecast_version_id` и `attempt_number` остаются в контексте обработчика Go. При несовпадении версий артефактов с ожидаемыми результат не сохраняется, задание завершается неповторяемой ошибкой.

## Локальная инфраструктура

PostgreSQL и команды запуска описаны в [инструкции разработки](../docs/development.md). Секреты задаются в корневом `.env`; файлы БД — в `out/pgdata` и исключены из Git.

Фронтенд планируется в соседнем каталоге `TramCast/frontend`. Go будет раздавать готовую сборку с диска; путь задаётся конфигурацией. Директория `backend/web` и встраивание через `go:embed` для этого не нужны.
