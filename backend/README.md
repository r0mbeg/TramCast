# Backend TramCast

Базовый каркас Go-приложения: REST API, раздача готового фронтенда с диска, очередь расчётов в PostgreSQL и gRPC-клиент Python-сервиса.

Сейчас созданы только каталоги с `.gitkeep`. Go-код, `go.mod`, миграции, SQL-запросы и `sqlc.yaml` ещё предстоит написать. Создание заготовки SQL-миграции через goose не требует Go-модуля или подключения к БД.

## Первая миграция

Из корня TramCast перейдите в `backend` и создайте заготовку:

```powershell
Set-Location backend
goose -dir migrations create init_schema sql
```

Если терминал уже открыт в `backend`, выполните только вторую команду. Файл появится в `backend/migrations` с временной меткой в имени. Команда создаёт заготовку; описание таблиц, ключей и индексов нужно заполнить в секции `-- +goose Up`, обратные действия — в `-- +goose Down`.

Согласованные шесть таблиц описаны в [контракте проекта](../AGENTS.md#предметная-область). Первую миграцию пользователь создаёт самостоятельно; в каркасе нет SQL-файлов.

## Каталоги

```text
backend/
├── cmd/tramcast/                         # Будущая точка входа
├── migrations/                           # SQL-миграции goose
├── internal/
│   ├── core/
│   │   ├── config/                       # Настройки приложения
│   │   ├── domain/                       # Рукописные модели приложения
│   │   ├── logger/                       # Настройка логирования
│   │   ├── repository/postgres/          # Подключение и пул pgx
│   │   └── transport/http/               # Сервер, общие HTTP-обработчики
│   └── features/
│       ├── routes/
│       │   ├── transport/http/
│       │   └── repository/postgres/
│       │       ├── queries/
│       │       └── sqlc/
│       ├── stops/
│       │   ├── transport/http/
│       │   └── repository/postgres/
│       │       ├── queries/
│       │       └── sqlc/
│       └── forecasts/
│           ├── transport/http/
│           ├── repository/postgres/
│           │   ├── queries/
│           │   └── sqlc/
│           ├── predictor/grpc/
│           └── worker/
└── README.md
```

| Каталог | Что в нём появится |
| --- | --- |
| `cmd/tramcast` | `main.go`: сборка зависимостей, запуск HTTP-сервера и фоновой обработки, завершение приложения. |
| `internal/core/domain` | Модели для логики приложения: маршрут, остановка, версия прогноза, прогноз и задание. Они не генерируются sqlc. |
| `internal/core/repository/postgres` | Общий пул соединений pgx; запросы конкретных фич располагаются у фич. |
| `internal/features/routes` | Операции над маршрутами и порядком остановок, включая таблицу `routes_stops`. |
| `internal/features/stops` | Операции над справочником остановок. |
| `internal/features/forecasts` | Версии, почасовые значения и задания расчёта; обращение к модели. |
| `transport/http` внутри фичи | REST-обработчики и DTO этой фичи. |
| `repository/postgres/queries` внутри фичи | Написанные вручную именованные SQL-запросы. |
| `repository/postgres/sqlc` внутри фичи | Сгенерированные Go-структуры и методы для `pgx/v5`; вручную не редактируются. |
| `forecasts/predictor/grpc` | Клиент Python-сервиса и преобразование Protobuf-сообщений. |
| `forecasts/worker` | Фоновый цикл обработки заданий в том же Go-процессе. |

Сервисные файлы, например `service.go` и файлы отдельных операций, появятся непосредственно в каталогах фич. Каталоги `ports/in`, `ports/out`, `adapters/in` и `adapters/out` для начального MVP не создаются.

Sqlc уже генерирует выполнение SQL-запросов. Дополнительный рукописный код в `repository/postgres` нужен там, где он выполняет отдельную задачу: преобразование модели, обработку ошибок или транзакцию публикации всех точек вместе с переводом задания в `succeeded`. Обёртка над каждым методом sqlc сама по себе не требуется. Небольшие интерфейсы можно объявлять рядом с использующим их сервисом по мере необходимости.

## Схема БД и генерация

Источник правды для схемы — последовательность файлов в `migrations`. Goose применяет их к БД; sqlc читает их как описание схемы вместе с файлами запросов.

После заполнения миграции и запросов:

1. Создать `backend/sqlc.yaml`: общий `schema: migrations`, отдельные блоки `routes`, `stops` и `forecasts`.
2. В каждом блоке указать каталог `queries` соответствующей фичи и выходной каталог `sqlc`, выбрать `sql_package: pgx/v5`.
3. Выполнить генерацию из `backend` командой `sqlc generate`.
4. Применять миграции командой `goose up` с настроенными параметрами подключения; при развёртывании это отдельный автоматический шаг до запуска новой версии backend.

Доменные Go-структуры не изменяют схему БД. Изменения уже применённой схемы оформляются новой миграцией с последующим обновлением запросов и генерацией.

Фронтенд планируется в соседнем каталоге `TramCast/frontend`. Go будет раздавать готовую сборку с диска; путь задаётся конфигурацией. Директория `backend/web` и встраивание через `go:embed` для этого не нужны.
