# TramCast — правила разработки

## Правила работы

- Перед написанием кода представляй пользователю подробный план действий.
- Не создавай коммит без явной просьбы. После изменений предлагай одно краткое сообщение в стиле истории Git: `feat(scope): ...`, `fix(scope): ...`, `docs: ...`.
- Текущие указания пользователя имеют приоритет над прежними решениями. Обновляй затронутые правила и статус вместе с реализацией.
- Перед изменениями проверяй файлы. Различай работающие возможности, согласованный план и измеренные результаты; не выдавай целевые метрики за достигнутые.
- Держи этот файл кратким: общие правила и обязательные договорённости. Детали реализации, команды и схемы не дублируй; используй документы ниже. README оставляй обзорным.
- Проверяй изменённое поведение подходящими проверками; в итоговом ответе указывай результат и оставшиеся ограничения.
- При работе с кодом обязательно используй `ponytail:ponytail` в режиме full, если пользователь не выбрал другой режим; перед первым применением прочитай доступный `SKILL.md`.
- Сначала изучи код и вызывающие места, переиспользуй существующее решение, стандартную библиотеку и платформу. Не добавляй инфраструктуру на будущее; сохраняй валидацию, обработку ошибок и безопасность. Нетривиальная логика требует запускаемой проверки; осознанные ограничения отмечай `ponytail:` с условием пересмотра.

**Реализовано:** Go/Gin-сервер с конфигурацией, slog, pgxpool, `/healthz`, `/readyz` и корректной остановкой; API справочников и GeoJSON; раздача фронтенда; транзакционный импорт XLSX + OSM с `-dry-run` и `-if-empty`; Docker-сборка и первый запуск с миграциями и импортом. Есть схема шести таблиц, SQL/sqlc и Protobuf со сгенерированным Go-кодом. Go-клиент `Predict` проверяет запрос и ответ и классифицирует ошибки; команда `register-forecast-version` регистрирует и активирует версию прогноза по метаданным ML со сверкой через `Predict`. Есть очередь `prediction_jobs` с [фоновым обработчиком](backend/README.md#очередь-прогнозов) и командой постановки `enqueue-prediction-jobs`. [HTTP API прогнозов](backend/README.md#http-api-прогнозов) отдаёт активную версию, ставит задания по запросу и читает готовые срезы и статус задания.

**Интерфейс:** React/TypeScript/Vite, TanStack Query, MapLibre и ECharts. Справочники, карта и прогнозы читаются из API: страница закрепляет активную версию на сессию, ставит задания по маршрутам и опрашивает их. День, неделя, месяц и сравнение в панелях уже есть; панели маршрутов и нижнюю можно скрыть. Выгрузка не подключена.

**ML:** основной локальный режим Python gRPC — CPU CatBoost, дистиллированный из 030; подготовленные признаки закреплены; два поставочных чекпоинта входят в Git (`ml/models/`). TabPFN 030, replay 030 и Chronos 002 сохранены для явного выбора. SQLite кэширует полный результат; новое поколение меняет версию. Удалённый GPU-сервис на RTX 2080 Ti 11 ГБ этим переключением не обновлён: [эксплуатация](ml/docs/GPU_SERVER.md), [поставка CPU](ml/docs/HANDOFF.md). Runtime не импортирует лабораторный код. [Измерения и ограничения](ml/docs/VALIDATION.md).

**Обновление ML-данных:** [офлайн-пайплайн](ml/docs/PREPARATION.md) пересобирает семейство 030 на обновлённой истории с января 2025 для следующих 61 суток. Требует покрытия календарями, погодой и сведениями о движении; выпускает отдельный комплект без автоматического включения и оценки качества. Исходная конкурсная поставка ноября–декабря сохраняется.

**Ещё предстоит:** подключение контейнера backend к ML (сейчас задания, в том числе поставленные из интерфейса, рассчитывает backend на хосте), конкурсная выгрузка из приложения, OpenAPI, аутентификация и rate limit клиента.

**Остановочное исследование:** по отдельному поручению пользователя в [ml/lab/stop_forecast](ml/lab/stop_forecast/README.md) проверяется цель маршрут × направление/вариант × позиция остановки × дата × час. Нужны реальные остановочные наблюдения и независимый эталон; маршрутные суммы и география их не заменяют. Аудит и баланс непривязанных событий реализованы, кандидат пилота — №12; проверяемый остановочный прогноз заблокирован отсутствием подтверждённой разметки. По уточнению пользователя отдельно разрешены модели обучения по агрегатам и байесовские сценарии, в том числе независимо от 030; их маршрутные метрики не доказывают остановочную точность. Доступные источники ограничены имеющимися файлами и интернетом: дополнительных выгрузок от организаторов пока нет; ожидание их получения не является рабочим планом. Рецепт 030 и прежние исследования сохраняются; интеграция Go/UI не входит в эту работу.

## Архитектура и код

Для первой остановочной функции пользователь согласовал **расчётное энтропийное распределение** маршрутного прогноза с явной маркировкой допущений. Отсутствие независимых остановочных наблюдений ограничивает заявления о точности, но не блокирует сценарный выпуск. Подготовлен и проверен [локальный пакет №12 на 61 день](ml/lab/stop_forecast/APP_PACKAGE.md); интеграция Go/UI и публикация не выполнялись. [Условия выпуска и границы ответственности](ml/lab/stop_forecast/APP_ESTIMATE_DECISION.md).

По следующему поручению подготовлен [сценарный выпуск всех 10 целевых маршрутов](ml/lab/stop_forecast/NETWORK_PACKAGE.md): 604 позиции, prior с признаками близости метро, 884 256 почасовых оценок с сохранением итогов 030. Для маршрутов без исходных B/F-долей применяется отдельный географический сценарий. Пакет №12 сохранён как контроль; интеграция остаётся задачей другого разработчика. Код, компактные входы и выпуск передаются через GitHub без ZIP.

Остановочный расчёт затем перенесён в Python runtime: `PredictStops` распределяет фактический результат общего маршрутного вычислителя/кэша по закреплённым профилям без зависимости от lab. Общий protobuf расширен добавочным методом, Python-генерация и Docker обновлены; Go-генерация, хранилище и UI остаются отдельной работой. [Контракт и подробная инструкция backend](ml/docs/STOPS_INTEGRATION.md). Локальная реализация проверена, удалённая служба не обновлялась, сценарный статус не меняется.

- Целевая схема MVP: браузер → один Go-сервис → PostgreSQL и Python по unary gRPC. Только Go пишет в прикладную БД и управляет очередью; Python работает с фиксированным комплектом артефактов без доступа к БД. Подготовка данных и обучение выполняются отдельно от пользовательских запросов.
- Go-модуль — `backend/`; фичи — `routes`, `stops`, `forecasts`, `web`, `catalog`. Цепочка: обработчик → `service/` → хранилище. HTTP/DTO — `transport/http`, SQL — `repository/postgres/queries`. Дополнительная иерархия `ports/adapters` не нужна.
- Имена пакетов и их импортных псевдонимов строятся через `_`: `core_config`, `core_postgres`, `routes_service`, `routes_transport_http`, `routes_sqlc`. Исключение — сгенерированный `forecastv1`.
- Сервис объявляет небольшой интерфейс нужных методов sqlc; его реализует `*Queries`. Для `web` хранилище — `fs.FS`, для `catalog` также читатели XLSX/OSM. Не добавляй обёртки и копии моделей ради слоёв. Общие бизнес-правила — `internal/core/domain`; сейчас там идентификаторы источников с префиксом `osm:` и московское время прогнозов (`Europe/Moscow`, выравнивание по целому часу).
- Источник схемы — [миграции](backend/migrations), доступа к БД — SQL и [sqlc.yaml](backend/sqlc.yaml) с `pgx/v5`. Применённую схему меняй новой миграцией. `sqlc generate` генерирует код, `goose up` отдельно меняет БД. Сгенерированные sqlc/Protobuf-файлы вручную не редактируй.
- Protobuf-исходник — `proto/`; Go-результат — `backend/internal/gen`, Python — `ml/runtime/generated`. Сохраняй совместимость номеров полей по правилам контракта.
- Исходники UI — `frontend/`, сборка — `frontend/dist`, которую Go читает с диска по `WEB_DIR`. В Git хранятся исходники и lock-файл; `dist` не коммитится. Node нужен для сборки.
- Сохраняй правила `web`: путь не выходит за `WEB_DIR`; SPA fallback только для путей без расширения, исключая `/api/...` и JSON-клиентов; отсутствующий файл с расширением — `404`. Vite `assets/*` неизменяемы; остальное — `no-cache` и ETag по содержимому. `http.ServeContent` обеспечивает `HEAD`, `304`, `Range`.
- Не добавляй в MVP Redis, отдельный брокер, PostGIS, партиционирование или аналитическую БД без новой потребности. Координаты — обычные поля PostgreSQL, GeoJSON формирует Go.

### Очистка истории

- Сохраняй `validation_result == 1`; обычная оплата и пересадка учитываются одинаково. Фильтруй raw **до агрегации** по `tran_date_time`: московские `[00:00, 01:00)` и `[05:30, 24:00)`. Час 0 относится к текущей календарной дате; часы 1–4 в прогнозе — структурные нули.
- Час 5 содержит только события с 05:30. Из готовых labels выделить полчаса нельзя: не дели значение пополам и не обнуляй весь час. До пересчёта из raw исключай этот час из обучения/оценки как неподтверждённый; его прогноз всё равно обязателен, при необходимости с описанным резервным методом.
- Отсутствие строки не доказывает нулевой спрос. Различай наблюдения, частичные счётчики, пропуски, структурные нули и восстановленные оценки. Восстановления храни отдельно, не превращай в факты и не используй как эталон оценки.
- `crd_hashcode` не идентифицирует человека надёжно: не считай по нему уникальных пассажиров и не удаляй успешные события только из-за совпадения хеша. Технические дубли проверяй отдельно.
- Исходные Excel/CSV сохраняй неизменными с контрольными суммами. `test_submission.csv` — шаблон, не наблюдения; примеры валидаций за 2026 год не добавляй к истории 2025 года.
- Сырые данные, очищенная история, признаки, маски качества и модели — файловые ML-артефакты вне прикладной БД. Сырые датасеты, прочие веса моделей, кэш, секреты и исходная книга справочников остаются вне Git. По решению пользователя два закреплённых чекпоинта `ml/models/dense-student-v3.cbm` и `ml/models/tabpfn-v2-regressor.ckpt` хранятся в Git с SHA256 из рецептов и лицензией TabPFN. По решению пользователя исторические отчёты, небольшие агрегаты, посылки и подготовленные входы рецепта 030 хранятся в Git; исторические протоколы не переписываются под новые пути.

### Обучение и проверка модели

- Начни с baseline `маршрут × день недели × час`; сравни с CatBoost или другим подходом на календарных, исторических и внешних признаках. Прямой и рекурсивный прогноз допустимы; оценивай весь 61-дневный горизонт, а не только ближайший день.
- Основная проверка: обучение на январе–августе → непрерывный прогноз сентября–октября. Не подставляй известные целевые факты этих месяцев в лаги последующих шагов. Преобразования и восстановление обучаются на тренировочной части; при возможности добавляй временные разбиения.
- Сравнивай модели на одинаковых очищенных наблюдениях и маске покрытия; показывай MAE, WAPE, срезы по маршрутам, часам и дальности. `WAPE = Σ|y − ŷ| / Σy`, `score = max(0, 1 − WAPE)`; при нулевой сумме фактов WAPE не определена, используй MAE. Локальные метрики и официальный score различаются; `0.88` не порог остановки.
- Внешние календарь, погода, расписания, трафик и события разрешены, включая ретроспективные сведения: собственного конкурсного запрета на них не вводим. Фиксируй URL, покрытие, дату получения/публикации, снимок или checksum и способ применения. Фактические будущие внешние наблюдения отличай от доступных прогнозов и сценариев; скрытых целевых фактов это не создаёт.
- После выбора модели переобучи её на январе–октябре. Артефакты фиксируют данные, признаки, параметры, seed, метрики и fallback. `dataset_version` охватывает все влияющие снимки, включая inference; содержимое под прежним ID не меняется. Собственные прогнозы не сдвигают `history_end`.
- Python проверяет конечность выхода, ограничивает снизу нулём, округляет half-up один раз и проверяет диапазон `int64`. Go повторно не округляет. Качество и submission проверяй после округления и применения структурных нулей.

## Справочники

- Источники запуска — [очищенная книга](data/catalog/catalog.xlsx) с листами `Маршруты GTFS_ROUTES`, `Остановки GTFS_STOPS`, `Порядок_остановок GTFS_TRIPS_ST` и [снимок OSM](data/osm/README.md) для 17, 25, 26, 28, 50. Они хранятся в Git и входят в образ. Оригинальная книга содержит персональные/служебные данные и метаданные автора; её не коммитят. В очищенной копии сохраняются значения и типы только трёх листов, без остальных листов и исходных метаданных.
- Импортируй все маршруты книги; она имеет приоритет над OSM по номеру. Целевые маршруты без обоих источников создаются без географии. `forecast_enabled` включён ровно у десяти целевых номеров и не обозначает готовность прогноза.
- Оба источника составляют полный снимок географии и проверяются целиком до записи. Обычный импорт читает их до транзакции; запись под общей advisory-блокировкой сохраняет внутренние ID, заменяет позиции, удаляет неиспользуемые остановки и откатывается целиком при ошибке. Конфликт исходного ID между номерами маршрутов требует разбора, а не автоматической перенумерации. Подробности — [импорт](backend/README.md#импорт-справочников), правила проверки — [catalog/service](backend/internal/features/catalog/service).
- `-if-empty` при `READ COMMITTED` сначала берёт блокировку импорта, затем отдельным запросом проверяет три таблицы справочников. Любая строка означает пропуск без чтения источников и изменения identity; иначе чтение, проверка и импорт идут под той же блокировкой. Частичный каталог не восстанавливается автоматически. Для обновления нужен явный импорт; `-dry-run` откатывает строки, но обычный пробный импорт может расходовать identity.
- Внутренний `route_id`, номер маршрута и ID источника различаются. HTTP использует внутренний ID, Python — номер. ID OSM имеют префикс `osm:`; остановки разных источников не склеиваются по имени или координатам. Позиции читаются по `stop_sequence` внутри `(route_id, pattern_key)`; повтор остановки допустим, обратное направление не получается разворотом прямого.
- Геометрия — схема между остановками, не рельсы: GeoJSON `[longitude, latitude]`, отдельная линия на вариант, источник `workbook`/`osm`, видимый в легенде и подсказке карты. Отсутствие географии не исключает прогноз. Соответствие географии всей истории 2025 года не подтверждено.
- OSM хранится без метаданных правок; обновляется вручную с проверкой по его README. Сохраняй лицензию ODbL и атрибуцию «© участники OpenStreetMap» для карты и производных данных.

## Прогнозы и очередь

Схема: `routes`, `stops`, `routes_stops`, `forecast_versions`, `validation_predictions`, `prediction_jobs`. Поля и ограничения — в [миграциях](backend/migrations); порядок SQL — в [границах транзакций](backend/README.md#границы-транзакций). Дополнительные таблицы истории, пользователей, импорта и ML-артефактов не входят в MVP.

- Одна задача — `(forecast_version_id, route_id)` на **весь горизонт версии**; пользователь читает любой непрерывный подынтервал внутри него. Конкурентные и пересекающиеся запросы получают ту же задачу во всех статусах.
- Параметры версии и опубликованные точки неизменяемы; меняется только `is_active`. Активная версия максимум одна, переключение транзакционное. Выбранный ID фиксируется в начале запроса и сохраняется при polling/чтении, даже если активная версия сменилась. Отсутствие активной версии и готовность её данных проверяет Go. Версию регистрируют по метаданным развёрнутого ML после сверки `Predict`; те же артефакты и период возвращают прежнюю запись. Replay — отдельная версия для разработки, регистрируется только по явному разрешению и никогда не выдаётся за рабочую GPU-версию.
- Ноль — готовое значение, отсутствие строки — отсутствие результата. Проверяй точные часы, а не только число строк. Пропуск у `succeeded` — ошибка целостности; нельзя незаметно дополнять старую версию новым расчётом.
- Захват задания — короткая транзакция с `FOR UPDATE SKIP LOCKED`, `running`, увеличением `attempt_count` и арендой. RPC идёт после commit с отдельным deadline, не зависящим от HTTP. Продление аренды и ошибки требуют текущих `id + attempt_count + running` и действующей аренды; потерявший владение обработчик прекращает записи.
- Go сверяет модель/данные ответа с версией, присутствие значений, диапазон и полную часовую сетку. При публикации блокирует задание и проверяет попытку/аренду; все точки и `succeeded` записываются одной транзакцией. `CompletePredictionJob` отдельно не вызывается. Блокировка защищает публикацию до commit; при неизвестном исходе commit сначала перечитай состояние.
- Временные ошибки дают отложенный повтор в пределах лимита; прочие — `failed`. Восстановление обрабатывает истёкшие аренды и исчерпанные попытки; поздний ответ старой попытки отклоняется. Polling не перезапускает `failed`, `succeeded` терминален. Повторный inference возможен, частичная публикация недопустима. После отмены из-за остановки Go или потери аренды обработчик ничего не пишет, задание возвращает восстановление. Захват открывает успешный `Predict` маршрута 5 активной версии; проверка повторяется при смене активной версии и после недоступности или тайм-аута ML либо несовпадения версий у задания активной версии. Смену комплекта ML без новой версии шлюз замечает только по неповторяемой ошибке первого задания, поэтому после неё перезапусти backend или активируй новую версию до постановки заданий.
- Ограничивай `queued + running`, число обработчиков, попытки и задержки. Приём нового задания и проверка лимита согласованы одной транзакцией; существующие задания доступны при полной очереди. Переполнение очереди — `503` с временем повтора. Rate limit клиента (`429`) отложен до аутентификации: без неё клиент различим только по IP, а пара «версия + маршрут» и ёмкость очереди уже ограничивают работу ML. Redis и gRPC retries/hedging не заменяют очередь PostgreSQL.
- SQLite внутри ML — удаляемый локальный кэш полного подготовленного горизонта, не очередь и не хранилище опубликованных прогнозов. Промах вызывает модель один раз под блокировкой; ошибки и отмена не сохраняют частичный ответ. Один процесс закреплён за неизменяемым рецептом; смена входов, весов, среды, параметров или ручного поколения создаёт новые ID, которые Go должен согласовать. Подробности — [интеграция ML](ml/docs/INTEGRATION.md).
- [Контракт gRPC](proto/README.md) обязателен: Python возвращает фактические версии фиксированного комплекта и полную сетку; несовпадение версий — неповторяемая ошибка. `optional boardings` проверяется на присутствие: отсутствующее поле отличается от нуля. Старую версию нельзя пересчитывать новым комплектом артефактов.

### HTTP прогнозов

Маршруты реализованы; полный список кодов и порядок проверок — в [backend/README.md](backend/README.md#http-api-прогнозов). Пути — `/api` без версии; DTO отделены от моделей БД. Списки передаются именованными полями, пустые — `[]`, отсутствующие значения — `null`, нулевой `boardings` не пропускается. Ошибка — `{"error":"<код>"}`, внутренние подробности остаются в логах с `request_id`.

| Метод и путь | Поведение |
| --- | --- |
| `GET /api/forecast-versions/active` | Активная версия, горизонт, зона и ID модели/данных |
| `POST /api/predictions/query` | `route_id`, `from`, `to`, необязательный `forecast_version_id`; `200` с полным срезом либо `202` с новым/существующим заданием |
| `GET /api/prediction-jobs/{job_id}` | Статус, версия и маршрут; чтение не запускает работу |
| `GET /api/predictions` | Готовый срез по обязательным версии, маршруту, `from`, `to`; иначе `409 prediction_not_ready`, без создания задания |

Ответ `200`: `forecast_version_id`, `route_id`, `timezone`, `from`, `to`, `points` с `date`, `weekday` (1–7, пн–вс), `hour`, `boardings`, по времени. Ответ `202`: `job_id`, версия, маршрут, `status` (`queued`/`running`) и интервал опроса. Терминальный `failed` при повторном query — `409 prediction_failed` с `job_id`; `succeeded` возвращает данные.

Неизвестный маршрут/версия — `404`; некорректный, слишком большой или выходящий за горизонт интервал — `400`; прогноз отключён — `422`; активная версия не настроена — `503`. Для неактивной версии новое задание не создаётся — `409 forecast_version_inactive`: worker считает только активную, и задание навсегда завершилось бы `failed`; готовые данные и существующие задания неактивной версии доступны. Тело query — только `application/json` (иначе `415`), чтобы чужой сайт не ставил задания простой формой. Попытки, аренда и `last_error_*` наружу не отдаются. Клиент после успеха читает ту же версию. Дневные и месячные суммы получаются из её опубликованных часов.

## Интерфейс и эксплуатация

- Следуй [PRODUCT.md](PRODUCT.md): настольный тёмный интерфейс, читаемость и доступность, легенда, сохранение маршрута/даты/версии. День показывается по часам, неделя и месяц — по дням с переходом к часам; переключение не обучает модель. Сравнение в панелях сохраняется, общая шкала используется по умолчанию; цвет не единственный носитель состояния.
- Различай ноль, отсутствие прогноза с причиной, очередь, расчёт, ошибку, replay и fallback. Показывай версию, границу истории и горизонт; для unary RPC не обещай процент прогресса. Скрытие панелей — настройка браузера, не часть URL. История с качеством данных, внешние ряды и мобильная адаптация — расширения.
- До публичного развёртывания требуется Basic Auth поверх HTTPS для UI/API; сейчас её нет. Python gRPC доступен только Go во внутренней сети. Платёжные идентификаторы и секреты не попадают в пользовательский API и логи.
- Постоянные данные PostgreSQL — `out/pgdata`; остановка окружения их сохраняет. `/readyz` проверяет Ping БД, не наличие миграций. Worker логирует `job_id`, попытку, версию, маршрут, длительность и код ошибки; сохраняй эти поля. Целевой p95 чтения до 500 мс ещё не подтверждён измерениями.

## Запуск и проверки

- Полный запуск после настройки `.env`: `make app-up` или `docker compose up --build -d --wait`. Docker собирает фронтенд и Go; порядок: PostgreSQL healthy → миграции → `catalog-init -if-empty` → backend. Ошибка подготовки блокирует запуск нового backend. Отдельная сборка — `make app-build`. CPU-сервис ML находится в профиле `ml` и запускается явно с весами из репозитория; обычный запуск приложения не требует NVIDIA.
- В [.env.example](.env.example) используются `WEB_DIR=./frontend/dist`, `CATALOG_FILE=./data/catalog/catalog.xlsx`, `CATALOG_OSM_FILE=./data/osm/tram_routes.json`. Относительные env-пути, включая defaults и process overrides, считаются от папки явного `-env-file`, без него — от рабочего каталога. Флаги импортёра `-file`/`-osm-file` считаются от рабочего каталога. Окружение процесса приоритетнее dotenv.
- Compose задаёт абсолютные пути внутри образа; хостовый mount книги и `CATALOG_HOST_FILE` не нужны. В build context допускается только очищенная XLSX; `dataset/`, другие книги и секретные `.env` исключаются. Мигратор собирается отдельно для amd64/arm64 с проверкой SHA-256; глобальный `ARG TARGETARCH` не добавляй — он ломал определение архитектуры на старом frontend Docker.
- Go: `go -C backend test ./...`, `go -C backend build ./...`; после изменения зависимостей — `make tidy-backend`, проверка — `make tidy-backend-check`. Фронтенд: `make frontend-test`, `make frontend-build`. SQL: `make sqlc-compile`, `make sqlc-generate`, `make migrate-validate`; Protobuf: `make proto-generate-go`.
- Для изменений миграций, импорта и очереди используй отдельную тестовую БД. Проверяй первый/повторный и конкурентный импорт, rollback; для очереди — полную сетку, одновременные запросы, истечение аренды, поздние ответы и атомарную публикацию. Интеграционные тесты очереди запускаются только с `TRAMCAST_TEST_DATABASE_URL` одноразовой PostgreSQL. Команды и подробности — в [инструкции разработки](docs/development.md).

- ML передаётся через GitHub без отдельного архива. Самостоятельный `ml/compose.yaml` содержит профили `gpu` и `replay`; [инструкция запуска](ml/docs/HANDOFF.md), обёртки — цели `make ml-*` с `ML_MODE` ([описание](docs/development.md#ml-сервис-в-docker)). `.gitattributes` сохраняет байты `ml/recipes/`, `ml/bundles/` и `ml/runtime/*.py`: от них зависят проверки SHA-256 и `model_version`. Быстрые проверки: `make test-ml-service PYTHON=<абсолютный путь>`. Новую историю и входы готовят в полигоне вне RPC; текущий runtime не пересобирает всю цепочку из raw и не получает внешние данные из интернета.
