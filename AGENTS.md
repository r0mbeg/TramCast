# Разработка прогноза пассажиропотока трамваев

## Цель и источники требований

Построить воспроизводимую ML-модель числа посадок на уровне `маршрут × дата × час` и подготовить `submission.csv` на ноябрь–декабрь 2025 года. Сначала обеспечить корректность данных, временную валидацию и базовый прогноз, затем улучшать качество.

Источники: `dataset/README.md` задаёт контракт датасета и submission; `ИИ-прогноз загрузки трамвайных маршрутов.pdf` описывает продукт и критерии хакатона. При расхождениях явно фиксировать их: фактическое содержимое файлов проверять, требования не заменять предположениями.

Посадки не равны числу пассажиров одновременно в салоне или проценту заполненности. В данных нет подтверждённой информации о высадках и загрузке каждого рейса; не выдавать прогноз посадок за эти показатели.

## Что проверено в исходных данных

Первичное исследование выполнено 26.09.2026. Полностью проверены обе таблицы labels и шаблон submission; прочитаны листы XLSX и все 6 страниц PDF. У сырых CSV исследованы заголовки, первые 10 000 строк каждого файла и последние записи. Полная сверка сырых событий с labels ещё не выполнена; статистику выборки нельзя выдавать за статистику всего файла.

В обеих таблицах labels присутствуют только маршруты `1, 7, 11, 12, 17, 25, 26, 28, 50`. README называет маршрут 5 редким, но в labels его нет вообще; в шаблоне его прогноз равен нулю. Это не доказывает отсутствие маршрута 5 в сырых событиях. Для маршрута 50 отсутствует весь день 21.09.2025; остальные восемь представленных маршрутов имеют записи на каждый из 304 дней.

Справочник `dataset/spravochniki/Хакатон_справочники_трамвай_10_маршрутов.xlsx` (фактическое имя может содержать составной Unicode-символ й) содержит маршруты `1, 2, 3, 4, 5, 6, 7, 10, 11, 12`. Пересечение с обязательной сеткой прогноза: `{1, 5, 7, 11, 12}`. Есть листы маршрутов, остановок, порядка остановок, наряда, расписания и порядка с координатами. Большинство листов имеют строку пояснений перед машинными заголовками; лист с координатами начинается сразу с заголовков.

Справочник содержит версии с `actual_date` в ноябре–декабре 2025, а наряд — данные февраля 2026. `Хакатон_пример_валидаций.xlsx` содержит 20 иллюстративных записей, включая даты 2026 года. Не добавлять эти примеры в историю обучения и не использовать поздние версии справочников как заранее известные признаки.

## Контракт подготовки данных

- Исходные файлы в `dataset/` и `dataset.zip` не изменять. Производные таблицы и модели хранить отдельно; не добавлять многогигабайтные данные в Git.
- CSV читать с `sep=';'`, UTF-8. Для первого baseline использовать готовые labels; не перечитывать сырые 10 GiB в каждом эксперименте. Для аудита читать только нужные столбцы порциями.
- Цель: количество строк с `validation_result == 1` по номеру из `ngpt_route` и календарному часу `tran_date_time`. Не фильтровать дополнительно по `tran_type_id == 52` без доказанной необходимости: такого ограничения нет в определении цели.
- Не использовать `input_date_time` для времени события: README предупреждает о битых датах. `begin_date_time` не заменяет timestamp валидации. `pass_route` не является источником номера маршрута; `place_id` — площадка/депо, не остановка.
- Рабочее допущение: timestamps заданы по московскому местному времени. Подтвердить при аудите; не сдвигать на три часа без основания. Идентификаторы, включая хеши карт, не трактовать как количественные признаки.
- Назначать период по timestamp, а не имени файла. Для обучения на январе–августе оставлять `[2025-01-01, 2025-09-01)`, для проверки сентября–октября — `[2025-09-01, 2025-11-01)`. Перед финальным прогнозом исключить все события начиная с 01.11.2025, даже если они находятся в `test.csv`.
- При пересборке labels проверить пересечение файлов на границе и семантику идентификаторов транзакций. Не считать `tran_no` глобально уникальным без проверки и не удалять одинаковые строки вслепую. Сверять агрегаты по ключам с предоставленной разметкой, расхождения документировать.
- Явно восстанавливать полную сетку маршрутов, дат и часов. Отсутствующий ключ и подтверждённый ноль различать: сохранить признак наличия исходной строки, проверить сбои покрытия и день 21.09 для маршрута 50. Для baseline допустимо документированное допущение «нет записи в агрегате = 0»; не интерполировать фактическую цель молча и не считать метрику только по положительным часам.
- Маршрут 5 обязательно оставлять в сетке. До проверки сырых данных допустим нулевой fallback с явно указанным отсутствием обучающей истории; не обещать для него проверенную точность.
- Не привязывать посадки к остановкам по одному лишь `place_id`, порядку остановок или неполному расписанию. Геометрию справочника можно использовать для карты с указанием покрытия и версии; распределение спроса по остановкам без фактов — только явно обозначенный сценарий.

## Валидация и защита от утечки

1. Основная локальная проверка: обучиться на январе–августе и одним запуском из точки 31.08.2025 спрогнозировать все 61 сутки сентября–октября. `test.csv` и `labels_day_test.csv` здесь содержат факты для оценки, а не скрытый конкурсный тест.
2. Для устойчивости выбора сравнить модели на более ранних временных окнах, например обучение по июнь → июль–август. Если сентябрь–октябрь используется для подбора, честно называть его валидацией, а не независимой финальной оценкой. Случайное перемешивание train/validation запрещено.
3. После выбора подхода переобучить его на всей разрешённой истории января–октября; спрогнозировать ноябрь–декабрь из точки 31.10.2025. Скрытой разметки этих месяцев нет.
4. Любые средние, кодировки, нормализации, подбор коэффициентов и отбор признаков рассчитывать только на обучающей части каждого окна.
5. Лаги и скользящие средние строить отдельно по маршрутам и только из доступного прошлого. Для горизонта 61 день нельзя подставлять фактические посадки внутри прогнозируемого периода. Использовать признаки, известные на cutoff, либо явно воспроизводимую рекурсию по собственным прогнозам. Проверка должна повторять финальный режим инференса.
6. Будущие день недели и час известны заранее. Календарь праздников/переносов, ремонты и расписания использовать с источником и проверкой даты доступности. Фактическая погода будущего периода недопустима; прогноз погоды должен быть выпущен не позже cutoff, иначе использовать документированный сценарий или климатическую оценку.
7. Для каждого внешнего источника сохранять ссылку, способ получения, временное покрытие, дату доступности и результат сравнения модели с ним и без него. Не скачивать внешние данные без конкретной гипотезы улучшения.

## Метрика и порядок экспериментов

`WAPE = sum(abs(y - prediction)) / sum(y)`; `WAPE-score = max(0, 1 - WAPE)`.

Считать глобальную метрику на полной согласованной сетке. Не усреднять WAPE маршрутов или часов вместо основной формулы. При `sum(y) == 0` возвращать явно неопределённую метрику и отдельно абсолютную ошибку, не скрывать деление на ноль. Дополнительно показывать ошибки по маршрутам, месяцам, часам и суммарное смещение прогноза; маршрут 5 оценивать с учётом отсутствующей истории.

- Сначала воспроизводимый сезонный baseline: профиль `маршрут × день недели × час`, сравнение среднего/медианы и нескольких окон недавней истории на одинаковых временных разбиениях.
- Затем одна общая табличная ML-модель с маршрутом, календарными признаками и безопасными историческими агрегатами. Выбирать библиотеку по доступному окружению и измеримому улучшению, не создавать несколько стеков сразу.
- Тренд, праздники, внешние факторы и ансамбль добавлять по одному, фиксируя изменение WAPE-score. Десять месяцев истории не позволяют надёжно оценить полный годовой сезонный цикл; годовой прогноз обозначать как сценарный.
- Для каждого запуска сохранять границу истории, периоды оценки, признаки, параметры, seed, версии зависимостей, правило заполнения сетки, постобработку, метрику, время и расход памяти. Не создавать инфраструктуру экспериментов, если достаточно файла результатов.
- Около 0,48 — заявленный организаторами score примера на скрытом периоде; локальная оценка с ним напрямую несопоставима. Не заявлять итоговое конкурсное качество до фактической проверки организаторами.

## Формат результата и проверки

Итоговый `submission.csv`: UTF-8, разделитель `;`, без индекса, строго `route;date;hour;prediction`.

- Маршруты: `1, 5, 7, 11, 12, 17, 25, 26, 28, 50`.
- Даты: ежедневно с `2025-11-01` по `2025-12-31` включительно; часы: целые 0–23.
- Ровно 14 640 уникальных ключей; множество ключей должно совпадать с `dataset/test_submission.csv`. При использовании шаблона присоединять прогноз по ключам, а не по позиции строки.
- Предсказания конечные, числовые и неотрицательные; без NaN/inf. Правило обрезки и округления фиксировать и одинаково применять при оценке и экспорте. README допускает числа с последующим округлением, точное правило округления платформы не описано.
- Перед выдачей перечитать экспортированный CSV и повторить проверки схемы, ключей и значений. Значения `prediction` из шаблона не использовать как обучающие метки.

Нетривиальная логика должна иметь минимальные запускаемые проверки: агрегация успешных событий на границе периода, отсутствие утечки после cutoff, известный пример расчёта WAPE и контракт submission. Использовать один небольшой набор проверок, не строить отдельный фреймворк.

## Разработка и готовность к интеграции

Начинать с простого Python-пайплайна подготовки, обучения, временной оценки и пакетного прогноза. Переиспользовать существующий код и зависимости, когда они появятся. Новые библиотеки и усложнения добавлять только для решаемой задачи. Команды документировать после их реализации и проверки, не выдавать запланированные команды за работающие.

ML-результат готов, когда другой разработчик может воспроизвести оценку и submission по README, получить сохранённую модель/профили и схему признаков, увидеть ограничения и измеренные ресурсы. Дневной и месячный объём получать суммой почасовых прогнозов; поправочные коэффициенты сохранять отдельно от базового прогноза.

Полное решение хакатона шире текущего ML-этапа: PDF требует запускаемый backend + frontend через Docker/Docker Compose, REST/HTTP API, карту, экспорт и описание архитектуры. Указанный в PDF Java/Spring, React/TypeScript и Python ML — рекомендуемый стек; не разворачивать сервисы до отдельной задачи на их реализацию.

При дальнейшей продуктовой работе учитывать:

- Критерии основного этапа: качество 10 баллов, данные/применимость 8, архитектура/производительность 5, функциональность 4, бизнес-ценность 2. Веб-сервис — обязательный артефакт полного решения, хотя не нужен для первого ML-эксперимента.
- День обязателен; месяц и год упоминаются в критериях хотя бы качественно, при этом год в описании целей назван опциональным сценарием. Ограничения годового и остановочного прогнозов объяснять явно.
- Интерфейс должен позволять менять поправки на погоду/события/сезон и показывать их эффект без подмены исходного прогноза.
- В README полного решения нужны реальные замеры latency/RPS/CPU/RAM и условия тестирования. Ориентиры PDF: 2–4 vCPU, 2–4 ГБ RAM, сотни RPS и p95 менее 200–300 мс. Не выдавать эти ориентиры за измеренный результат.
- На сдачу нужны код и артефакты модели, инструкции, ссылки на внешние данные, запускаемый сервис, схема архитектуры, область применимости/адаптации, замеры и ограничения. PDF указывает 27 сентября, 23:59 МСК и лимиты 36 общих/24 успешных загрузок в день; актуальность сроков проверять на платформе перед сдачей.
