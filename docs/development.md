# Локальная разработка TramCast

Docker Compose собирает и запускает Go-backend с фронтендом, PostgreSQL, миграции и первичную загрузку справочников. Для разработки Go и Vite можно запускать локально. Python ML запускается отдельно по [инструкции](../ml/docs/HANDOFF.md); Redis и Caddy в текущем окружении не нужны.

## Настройка

Для контейнерного запуска нужен Docker с Compose v2 или новее и доступом в интернет для загрузки образов и зависимостей. Go, Node и Make на хосте не обязательны. Для локальной разработки нужны Go версии из `backend/go.mod` (1.26.8), Node.js 24 с npm 11 (проверено на Node 24.14.1); для SQL-генерации и создания миграций — `sqlc` и `goose`.

При первом запуске скопируйте `.env.example` в `.env` и задайте непустой пароль PostgreSQL. В PowerShell:

```powershell
Copy-Item .env.example .env
```

Существующий `.env` сохраняйте. Он исключён из Git. Compose сам читает этот файл; `make run-backend` передаёт его Go-приложению через `-env-file`. `PROJECT_ROOT` и отдельный экспорт переменных не требуются. При запуске из WSL инструменты Go/Make должны быть доступны в `PATH` этого окружения.

Очищенная книга `data/catalog/catalog.xlsx` находится в Git: в ней только маршруты, остановки и порядок остановок, без листа «Наряд» и исходных метаданных. Вместе со снимком OSM она включается в Docker-образ. Исходная книга из `dataset/` для запуска не нужна и остаётся вне Git. Для локального импорта есть одна настройка книги — `CATALOG_FILE=./data/catalog/catalog.xlsx`.

## Запуск приложения в Docker

Из корня проекта:

```text
docker compose up --build -d
```

Либо `make app-up`: он ждёт готовности backend и ML, затем выполняет цепочку версии прогноза на переднем плане и завершается с её кодом. `docker compose up --wait` для всего проекта не используйте: Compose считает ошибкой завершившийся разовый сервис `prediction-jobs-init`, от которого никто не зависит, даже при коде 0. Интерфейс доступен на `http://localhost:8080`; хостовый порт меняется через `HTTP_PORT`. Порт слушает `127.0.0.1`. Сборка выполняется внутри Docker: `npm ci` использует lock-файл, Go собирает сервер, импортёр, регистрацию версии и постановку заданий. Образ `tramcast-app:local` содержит эти четыре бинарника, весь `frontend/dist`, очищенную книгу справочников и снимок OSM. Node и Go SDK остаются в стадиях сборки. Приложение работает от непривилегированного пользователя UID/GID 10001. Образ `tramcast-ml-cpu:local` — CPU CatBoost из `ml/Dockerfile`; веса `ml/models/dense-student-v3.cbm` входят в Git и монтируются только для чтения, кэш хранится в томе `ml-cache`. GPU не нужна.

В Git хранятся исходники и lock-файл фронтенда; `frontend/dist` исключён из Git и собирается внутри Docker. При перезапуске контейнер отдаёт готовую статику. При повторной сборке Docker использует кеш: изменение Go не требует заново собирать неизменённый фронтенд.

Образ мигратора собирается отдельно из `docker/migrate.Dockerfile`: BuildKit автоматически выбирает бинарник Goose для `amd64` или `arm64`, скачивание проверяется по SHA-256. `TARGETARCH` не нужно задавать в `.env`. В Dockerfile указан `# syntax=docker/dockerfile:1`, чтобы использовать актуальный стабильный frontend сборщика независимо от встроенного в Docker. Глобальное `ARG TARGETARCH` не добавляется: на старых frontend оно могло затереть автоматически определённое значение и вызвать ошибку `failed to parse stage name "goose-"`.

Порядок запуска: PostgreSQL проходит healthcheck → `migrate` выполняет `goose up` → `catalog-init` выполняет `import-catalog -if-empty` → запускается backend. Ошибка миграции или импорта не позволяет запустить новый backend. `/readyz` проверяет доступность PostgreSQL; состояние схемы и успешность импорта проверяются отдельными шагами запуска.

Параллельно готовится прогноз: `ml` проходит healthcheck (gRPC-запрос маршрута 5, модель не запускается) → `ml-describe` сохраняет вывод `service.py --describe` в том `ml-cache` → после импорта справочников `forecast-version-init` выполняет `register-forecast-version -activate` по этим метаданным со сверкой через `Predict` → `prediction-jobs-init` ставит задания всех маршрутов активной версии → worker backend рассчитывает их через `ml:50051`. На CPU весь горизонт 10 маршрутов готов за несколько секунд. Повторный запуск возвращает ту же версию и те же задания, ничего не пересчитывая; новый комплект ML (другой `model_version`) регистрируется как новая версия и становится активным. Backend не ждёт ML: если ML не запустился, интерфейс работает, показывает «нет активной версии» и подхватит её после успешной регистрации. Каждый запуск делает активной версию CPU ML этого Compose: если вы вручную активировали другую версию, например GPU-версию с backend на хосте, повторите её активацию после запуска.

Первичный импорт проверяет `routes`, `stops` и `routes_stops` под транзакционной блокировкой. Если хотя бы в одной таблице есть запись, импорт пропускается без чтения источников и без изменения данных. Это защита существующей базы, а не проверка полноты справочника. Для обновления или восстановления частично заполненного каталога нужен явный импорт без `-if-empty`. Если все три таблицы пусты, оба источника проверяются и загружаются одной транзакцией. Ошибка откатывает загрузку; следующий запуск повторяет попытку. Файл-маркер и дополнительная таблица не используются.

В образ включаются только очищенная книга `/app/data/catalog/catalog.xlsx` и снимок OSM `/app/data/osm/tram_routes.json`. `catalog-init` использует эти пути без подключения файлов с хоста. `.dockerignore` исключает `dataset/` и остальные XLSX. Значение `CATALOG_FILE` в корневом `.env` задаёт источник локального импорта; Compose переопределяет его на путь внутри образа. Для обновления справочников в существующей БД пересоберите образ и явно повторите импорт: `-if-empty` не обновляет заполненный каталог.

```text
make app-build
make app-logs
docker compose ps --all
docker compose logs migrate catalog-init
```

`app-build` собирает образы приложения, мигратора и CPU ML, `app-logs` показывает логи backend, ML, цепочки версии, импорта и миграций. Цепочку версии можно повторить отдельно: `docker compose run --rm prediction-jobs-init`. Принудительный импорт и проверка без сохранения в контейнере (аргументы заменяют стандартный `-if-empty`):

```text
docker compose run --rm catalog-init -if-empty=false
docker compose run --rm catalog-init -dry-run
```

Без Make остановка выполняется через `docker compose --profile dev down`; `make app-down` также сохраняет данные PostgreSQL. Для обновления приложения повторите команду запуска с `--build`. `docker compose restart` перезапускает контейнеры, но не пересобирает образ и не выполняет заново всю цепочку подготовки. Если запущен контейнер backend, задайте локальному Go `HTTP_ADDR=127.0.0.1:8081` ([пример](#предварительный-расчёт)): на Windows привязка `:8080` проходит без ошибки, пока Docker публикует `127.0.0.1:8080`, и запросы к `localhost:8080` незаметно попадают в контейнер.

## Локальный запуск для разработки

Из корня проекта:

```text
make env-up
make migrate-up
make migrate-status
make import-catalog
make run-backend
```

Без Make те же действия:

```text
docker compose up -d --wait postgres env-port-forwarder
docker compose run --rm migrate up
docker compose run --rm migrate status
go -C backend run ./cmd/import-catalog -env-file ../.env
go -C backend run ./cmd/tramcast -env-file ../.env
```

`make import-catalog` загружает маршруты, остановки и порядок остановок из книги по пути `CATALOG_FILE` и из снимка OpenStreetMap по пути `CATALOG_OSM_FILE` для маршрутов 17, 25, 26, 28, 50, которых в книге нет. По умолчанию используются очищенная книга `data/catalog/catalog.xlsx` и снимок `data/osm/tram_routes.json` из репозитория. Для локального импорта можно задать другие пути в `.env`. Импорт нужен один раз на базу и повторяется при новой версии книги или снимка. `make import-catalog-dry-run` проверяет оба источника и показывает итог, откатывая изменения. При ошибках команда перечисляет их — в книге по листам и строкам, в снимке по relation и участникам — и ничего не записывает. После импорта обновите открытую страницу интерфейса: справочники кешируются в браузере до перезагрузки, перезапуск backend не нужен. Подробности — в [backend/README.md](../backend/README.md#импорт-справочников), порядок обновления снимка — в [его README](../data/osm/README.md).

| Контейнер | Назначение |
| --- | --- |
| `tramcast-postgres` | Отдельная PostgreSQL 18.1 для проекта; постоянные данные в `out/pgdata` |
| `tramcast-env-port-forwarder` | Необязательный доступ с хоста через `127.0.0.1:5433`; профиль `dev` |
| `migrate` (имя генерирует Compose) | Одноразовый запуск goose перед импортом; ручной `run --rm` удаляется после команды |
| `catalog-init` (имя генерирует Compose) | Одноразовая загрузка справочников в пустую БД |
| `backend` (имя генерирует Compose) | Go API и собранный фронтенд, хостовый HTTP-порт из `HTTP_PORT` |

`make env-up` поднимает PostgreSQL и локальный forwarder вместе. Для повторного открытия порта после `make env-port-close` используйте `make env-port-forward`. При явном запуске сервиса его Compose-профиль включается автоматически. Миграции обращаются к PostgreSQL по внутренней сети и не требуют проброса порта. PostgreSQL должен пройти healthcheck перед запуском зависимых сервисов.

Для клиента БД на хосте: адрес `127.0.0.1`, порт из `POSTGRES_FORWARD_PORT` (по умолчанию `5433`), пользователь и база из `.env`. Для контейнеров проекта адрес БД — `postgres:5432`. Пароль передаётся мигратору отдельной переменной окружения, а не аргументом командной строки.

У PostgreSQL нет опубликованных портов. Forwarder слушает только loopback, поэтому не открывает БД в локальную сеть. Сервис `backend` публикует HTTP-порт на loopback; Python gRPC доступен внутри сети Compose.

## Конфигурация backend

`-env-file` загружает только указанный файл. Уже установленные переменные окружения имеют приоритет, включая пустые значения: пустой обязательный параметр будет ошибкой. Относительные `WEB_DIR`, `CATALOG_FILE` и `CATALOG_OSM_FILE`, в том числе значения из окружения процесса и значения по умолчанию, разрешаются относительно папки этого env-файла. У стандартного `.env` это корень проекта, даже когда Go запущен из `backend/`. Без `-env-file` приложение читает окружение процесса и разрешает пути от текущего рабочего каталога. Абсолютные пути сохраняются. Сам путь к env-файлу в Make можно заменить: `make run-backend ENV_FILE=../.env.local`; этот аргумент считается относительно `backend`.

Если `.env` создан по старому шаблону, замените файловые настройки на `WEB_DIR=./frontend/dist`, `CATALOG_FILE=./data/catalog/catalog.xlsx`, `CATALOG_OSM_FILE=./data/osm/tram_routes.json`. Сохраните свои параметры БД и остальные настройки. Прежняя переменная `CATALOG_HOST_FILE` больше не используется и может быть удалена.

| Переменная | Значение по умолчанию / назначение |
| --- | --- |
| `HTTP_ADDR` | `:8080` |
| `HTTP_READ_HEADER_TIMEOUT` / `HTTP_READ_TIMEOUT` | `5s` / `15s` |
| `HTTP_WRITE_TIMEOUT` / `HTTP_IDLE_TIMEOUT` | `30s` / `60s` |
| `HTTP_SHUTDOWN_TIMEOUT` / `HTTP_PROBE_TIMEOUT` | `10s` / `2s` |
| `LOGGER_LEVEL` / `LOGGER_FORMAT` | `INFO` / `text`; формат также может быть `json` |
| `POSTGRES_HOST` / `POSTGRES_PORT` | `127.0.0.1` / `5433` для локального forwarder |
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | Обязательные значения из `.env` |
| `POSTGRES_SSLMODE` | `disable` для локальной PostgreSQL |
| `POSTGRES_MAX_CONNS` / `POSTGRES_MIN_CONNS` | `10` / `0` |
| `POSTGRES_CONNECT_TIMEOUT` / `POSTGRES_STARTUP_TIMEOUT` | `5s` / `10s` |
| `WEB_DIR` | `./frontend/dist`: сборка фронтенда; относительный путь разрешается от папки явного env-файла, а без него — от рабочего каталога процесса |
| `CATALOG_FILE` | `./data/catalog/catalog.xlsx`: очищенная книга для `make import-catalog`, хранится в Git; путь разрешается так же, как `WEB_DIR` |
| `CATALOG_OSM_FILE` | `./data/osm/tram_routes.json`: снимок OpenStreetMap для `make import-catalog`, хранится в Git; путь разрешается так же, как `WEB_DIR`. Пустое значение — ошибка: импорт без снимка очистил бы географию маршрутов 17, 25, 26, 28, 50 |
| `ML_GRPC_ADDR` | `127.0.0.1:50051`: адрес `host:port` Python gRPC-сервиса; порт числовой, от 1 до 65535 |
| `ML_GRPC_TIMEOUT` | `930s`: deadline одного вызова `Predict`. Больше лимита расчёта рецепта 030 (900 с), поэтому сервер первым сообщает о собственном тайм-ауте |
| `PREDICTION_JOB_WORKER_ENABLED` | `true`: запускать [обработчик очереди](../backend/README.md#очередь-прогнозов) в процессе backend; при `false` задания остаются в очереди |
| `PREDICTION_JOB_WORKERS` | `1`: число циклов захвата, от 1 до 16. Python строит один ответ за раз и отвечает «занят» (`ml_unavailable`) на параллельный вызов, поэтому больше одного обычно не нужно |
| `PREDICTION_JOB_QUEUE_CAPACITY` | `20`: предел `queued + running` по всем версиям, не меньше 1. Для предварительного расчёта нужно место под 10 маршрутов |
| `PREDICTION_JOB_MAX_ATTEMPTS` | `3`: захватов одного задания, включая повторы, от 1 до 100 |
| `PREDICTION_JOB_LEASE_DURATION` | `60s`: аренда захваченного задания, целые секунды от 3 с до 1 ч. Продлевается каждую треть срока, восстановление истёкших аренд запускается каждые полсрока |
| `PREDICTION_JOB_RETRY_DELAY` | `30s`: базовая задержка повтора, целые секунды от 0 до 1 ч. После неудачной попытки n — `RETRY_DELAY × 4^(n−1)`, не больше 1 ч; при значениях по умолчанию 30 с, затем 2 мин. Восстановление истёкшей аренды ждёт базовую задержку |
| `PREDICTION_JOB_POLL_INTERVAL` | `2s`: пауза после пустого захвата или ошибки БД, положительная |
| `PREDICTION_JOB_SHUTDOWN_TIMEOUT` | `5s`: сколько текущий вызов ML может завершаться после сигнала остановки, от 0 до 20 с; перечитывание задания после неизвестного исхода commit добавляет до 5 с. HTTP и обработчик останавливаются параллельно и должны уложиться в `stop_grace_period: 30s` Compose. На Windows-хосте держите значение небольшим ([остановка](#предварительный-расчёт)) |

`PREDICTION_JOB_*` проверяются всегда, даже при выключенном обработчике: лимит очереди нужен и приёму заданий. Если изменили `POSTGRES_FORWARD_PORT`, задайте такое же значение `POSTGRES_PORT` для локального backend. Compose переопределяет адрес БД на `postgres:5432`, HTTP-адрес на `:8080`, `WEB_DIR` на `/app/frontend/dist` и пути источников на контейнерные; хостовые пути локальной разработки внутрь не передаются. Compose передаёт контейнерам все `PREDICTION_JOB_*` и `ML_GRPC_TIMEOUT` из `.env`, а адрес ML задаёт сам: `ml:50051`, сервис того же Compose. `ML_GRPC_ADDR` из `.env` относится только к Go на хосте. Конфигурация проверяется до подключения; ошибки не выводят пароль или содержимое dotenv-файла.

После запуска доступны `http://localhost:8080/healthz` и `http://localhost:8080/readyz`. Первый маршрут проверяет HTTP, второй — доступность БД с ограничением времени. Справочники читаются через `/api/routes`, `/api/routes/geometry` (схемы маршрутов в GeoJSON для карты), `/api/routes/{route_id}/stops` и `/api/stops`; при локальном запуске до импорта списки пустые; Compose выполняет первичный импорт автоматически. Прогнозы отдаёт [HTTP API прогнозов](../backend/README.md#http-api-прогнозов). Без активной версии или доступного ML обработчик очереди не захватывает задания и сообщает об этом в лог без повторов на каждой проверке; HTTP при этом работает. Завершение — Ctrl+C; приложение ждёт активные запросы и текущий вызов ML до настроенных таймаутов, при включённом обработчике пишет в лог `prediction job worker stopped`, при чистом завершении — `application stopped`, после чего закрываются gRPC-клиент и пул.

Исходники фронтенда лежат в корневом `frontend/`, а Go отдаёт результат сборки из `WEB_DIR`. `make run-backend` передаёт корневой `.env`, поэтому значение `./frontend/dist` указывает на `TramCast/frontend/dist`. Абсолютный путь выводится в лог при старте. Если `index.html` нет, в логе будет предупреждение, а страницы вернут `404`; API при этом работает. Новая сборка подхватывается без перезапуска.

## Фронтенд

```text
make frontend-install
make frontend-build
make frontend-dev
make frontend-test
```

`frontend-install` ставит зависимости строго по `frontend/package-lock.json` (`npm ci`); повторяйте его после изменения lock-файла. `frontend-build` проверяет типы и собирает `frontend/dist`, который отдаёт Go из `WEB_DIR`: после сборки интерфейс открывается на `http://localhost:8080`. `frontend-dev` запускает Vite на `http://localhost:5173` с горячей перезагрузкой и проксирует `/api` на backend `127.0.0.1:8080`, поэтому backend должен быть запущен. `frontend-test` проверяет типы и запускает модульные тесты Vitest.

Интерфейс читает активную версию один раз за сессию и запрашивает весь её горизонт по каждому маршруту с прогнозом: `POST /api/predictions/query` ставит задание, если его нет, затем страница опрашивает задание с интервалом из ответа и после `succeeded` читает срез той же версии. Смена даты, часа и периода фильтрует уже полученные часы без запросов. Состояния «нет активной версии», «в очереди», «идёт расчёт», «очередь заполнена», «версия неактивна» и ошибка показаны раздельно; без активной версии страница проверяет её снова каждые 30 с. Для replay-версии (`model_version` с `replay`) строка контекста показывает чип «Replay · сохранённый результат». Панели «Маршруты» и нижнюю («Картина дня» или прогноз маршрута) скрывают язычки на их границе с картой; это настройка браузера в `localStorage`, не часть URL, а открытие маршрута снова показывает нижнюю панель. Для работы интерфейсу нужны backend и активная версия; в Docker задания считает backend в контейнере через CPU ML того же Compose. Подложка карты загружается с OpenFreeMap и требует интернета; при ошибке загрузки интерфейс сообщает, что подложка недоступна. Без импортированных справочников карта и список маршрутов пустые.

### ML-сервис в Docker

Цели `ml-*` оборачивают самостоятельную поставку `ml/compose.yaml` из [инструкции ML-команды](../ml/docs/HANDOFF.md): PostgreSQL, Go, локальный Python и корневой `.env` для них не нужны. Это отдельный Compose-проект `tramcast-ml` со своими томами весов и кэша. Он не связан с профилем `ml` корневого `docker-compose.yaml` и целью `prepare-ml-model` выше: веса одного способа другому не видны.

Этот раздел — самостоятельная поставка `ml/compose.yaml` для Go на хосте; приложению в Docker она не нужна, у него свой сервис `ml`. Самостоятельный CPU-режим запускается через `docker compose -f ml/compose.yaml up -d --build --wait ml-cpu`, как описано в [инструкции ML](../ml/docs/HANDOFF.md), и публикует порт на `127.0.0.1:50051`. Приведённые ниже Make-цели пока обслуживают только GPU и replay; перед их запуском остановите CPU-контейнер командой `docker compose -f ml/compose.yaml stop ml-cpu`.

Для этих Make-целей режим задаёт `ML_MODE`: `gpu` (по умолчанию) пересчитывает рецепт 030 на NVIDIA GPU, `replay` на CPU отдаёт сохранённый результат 030 под отдельными версиями и не вызывает модель. Из этих двух режимов без NVIDIA работает `replay`; основной CPU CatBoost запускается отдельной командой выше. Задайте его до первого `make ml-up`, иначе начнётся сборка GPU-образа на несколько гигабайт, которая затем остановится на резервировании видеокарты.

```text
make ml-start
make ml-check
make ml-describe
```

`ml-start` выполняет три шага HANDOFF: `ml-install` проверяет SHA256 закреплённых весов TabPFN в `ml/models/` (скачивает их только при отсутствии файла), `ml-up` запускает контейнер и ждёт healthcheck, `ml-warm` один раз рассчитывает полный прогноз (10 маршрутов × 1464 часа) в SQLite-кэш. Оба чекпоинта входят в Git; интернет требуется для сборки образов и восстановления отсутствующих GPU-весов; GPU-образ с PyTorch и CUDA весит несколько гигабайт. Обучения при этом нет: веса модели не меняются, исследования и подготовка входов остаются в `ml/lab/`. `ml-check` вызывает `Predict` встроенным клиентом для `ML_ROUTE` (по умолчанию 1) на весь ноябрь–декабрь и печатает число часов и сумму; `ml-describe` выводит JSON с ID модели и данных, периодом и маршрутами для [регистрации версии прогноза](#версия-прогноза). `ml-logs` выводит последние строки логов и следит за ними до Ctrl+C, `ml-down` останавливает оба режима и сохраняет веса и кэш.

Без GPU режим задаётся один раз на сессию PowerShell:

```powershell
$env:ML_MODE = "replay"
make ml-up
make ml-check
```

Ожидаемый ответ `replay` для маршрута 1 — 1 464 часа и сумма 1 103 274. `ml-up` сначала останавливает контейнер другого режима: оба публикуют один порт. `ml-warm`, `ml-describe` и `ml-start` работают только в `gpu`. Другой маршрут или период — `make ml-check ML_ROUTE=17 ML_FROM=2025-12-01T00:00:00+03:00`; занятый порт меняется через `ML_PORT=50052`.

Сервис слушает `127.0.0.1:50051` без TLS; метод — `tramcast.forecast.v1.ForecastService/Predict`. Reflection не включён, поэтому внешнему клиенту нужен контракт из `proto/`. Например, [grpcurl](https://github.com/fullstorydev/grpcurl) из корня репозитория в Git Bash:

```bash
grpcurl -plaintext -import-path proto -proto tramcast/forecast/v1/forecast.proto -d '{"route_number": 1, "forecast_from": "2025-10-31T21:00:00Z", "forecast_to": "2025-11-01T21:00:00Z"}' 127.0.0.1:50051 tramcast.forecast.v1.ForecastService/Predict
```

Windows PowerShell 5.1 убирает внутренние кавычки из аргументов программ, поэтому там JSON передаётся через стандартный ввод:

```powershell
'{"route_number": 1, "forecast_from": "2025-10-31T21:00:00Z", "forecast_to": "2025-11-01T21:00:00Z"}' | grpcurl -plaintext -import-path proto -proto tramcast/forecast/v1/forecast.proto -d '@' 127.0.0.1:50051 tramcast.forecast.v1.ForecastService/Predict
```

В JSON-ответе `boardings` приходит строкой, так как это `int64`. Postman и Insomnia принимают тот же `.proto` через импорт. Команды Go и `make run-backend` на хосте обращаются к `ML_GRPC_ADDR`, по умолчанию `127.0.0.1:50051`; при `ML_PORT=50052` задайте тот же порт в `ML_GRPC_ADDR`. Контейнер backend корневого Compose работает со своим CPU-сервисом `ml`, а не с этой поставкой: GPU и replay считает backend на хосте. Обработчик контейнера при этом не мешает: пока его CPU ML не обслуживает активную версию, шлюз закрыт и задания он не захватывает.

Подготовленные входы (`ml/recipes/`) и сохранённые результаты (`ml/bundles/`) сверяются по SHA256, а байты `model_030.py` и `constants.py` входят в `model_version`. `.gitattributes` запрещает Git менять в этих файлах переводы строк. В клоне, полученном до этого правила при `core.autocrlf=true`, режим `gpu` падает с `Input checksum mismatch`, а `replay` пишет в лог `Forecast checksum mismatch` и остаётся unhealthy. `git pull` такие файлы не исправляет, а `git status` может показывать их изменёнными, даже если правок нет.

Восстановление перезаписывает эти файлы из коммита. Сначала убедитесь, что первая команда ничего не выводит: она показывает только настоящие правки и не учитывает CRLF. Вторая команда рассчитана на cmd или Git Bash, где `&&` не даёт выполнить checkout после ошибки. Затем пересоберите образ, а в режиме `gpu` снова заполните кэш через `make ml-warm`.

```text
git diff --ignore-cr-at-eol --stat -- ml/recipes ml/bundles ml/runtime
git rm -r --cached -q -- ml/recipes ml/bundles ml/runtime/model_030.py ml/runtime/constants.py && git -c core.autocrlf=false checkout HEAD -- ml/recipes ml/bundles ml/runtime/model_030.py ml/runtime/constants.py
make ml-up
```

## Версия прогноза

Прогнозы Go привязаны к записи `forecast_versions` с ID модели и данных, которые обслуживает запущенный Python-сервис. Её записывает команда `register-forecast-version`; флаги, проверки, повторный запуск и правила replay описаны в [backend/README.md](../backend/README.md#версии-прогноза), здесь — порядок действий.

Команда запускается на хосте с Go. Нужны PostgreSQL с применёнными миграциями (`make migrate-up`) и импортированными справочниками (`make import-catalog`; в Docker их загружает `catalog-init`), доступная с хоста (`make env-up`, при уже запущенном приложении — `make env-port-forward`), и ML-сервер по адресу `ML_GRPC_ADDR`, если проверка не отключена через `VERIFY=0`. `METADATA` указывается от корня репозитория или абсолютным путём. `DRY_RUN=1` выполняет все проверки без записи.

Для разработки без GPU подходит replay 030; для него обязателен `ALLOW_REPLAY=1`.

```text
make ml-up ML_MODE=replay
make forecast-version-register METADATA=ml/bundles/030/forecast_bundle.json ALLOW_REPLAY=1 ACTIVATE=1
```

На GPU-хосте после `make ml-start` сохраните вывод `make ml-describe` в файл и зарегистрируйте версию по нему. В cmd:

```text
make ml-describe > out\ml-describe.json
```

В Git Bash — то же перенаправление с путём `out/ml-describe.json`. Windows PowerShell 5.1 при `>` пишет UTF-16, который команда отклоняет, поэтому там нужен `Out-File`; добавленный им UTF-8 BOM команда удаляет:

```powershell
make ml-describe | Out-File -Encoding utf8 out\ml-describe.json
```

Затем:

```text
make forecast-version-register METADATA=out/ml-describe.json ACTIVATE=1
```

Каталог `out/` должен существовать; JSON-файлы исключены из Git. ID модели зависит от весов, библиотек образа, устройства и поколения рецепта, поэтому после пересборки ML, смены `ML_CONFIG` или нового поколения через `--refresh` повторите `ml-describe` и регистрацию. Прежние версии и их прогнозы остаются в БД. Без Make из корня: `go -C backend run ./cmd/register-forecast-version -env-file ../.env -metadata ../out/ml-describe.json -activate`; здесь относительный `-metadata` считается от `backend`, а вместо `VERIFY=0` передаётся `-verify=false`.

Интеграционный тест Go-клиента вызывает запущенный replay: маршрут 1 на весь горизонт — 1 464 часа с суммой 1 103 274, маршрут 5 — нули; ожидаемые ID берутся из `ml/bundles/030/forecast_bundle.json`. PostgreSQL для него не нужна, без `TRAMCAST_TEST_ML_ADDR` тест пропускается. В Git Bash:

```bash
TRAMCAST_TEST_ML_ADDR=127.0.0.1:50051 go -C backend test -count=1 -run Replay ./internal/features/forecasts/predictor/grpc/
```

В PowerShell:

```powershell
$env:TRAMCAST_TEST_ML_ADDR = "127.0.0.1:50051"
go -C backend test -count=1 -run Replay ./internal/features/forecasts/predictor/grpc/
```

## Очередь прогнозов

Задания `prediction_jobs` рассчитывает обработчик внутри backend; его устройство, коды ошибок и повторы описаны в [backend/README.md](../backend/README.md#очередь-прогнозов). Задания ставят [HTTP API прогнозов](../backend/README.md#http-api-прогнозов) по запросу маршрута и команда `enqueue-prediction-jobs` для предварительного расчёта всех маршрутов версии. Считает их backend, чей ML обслуживает активную версию: в Docker — backend в контейнере через CPU ML того же Compose, для GPU и replay — backend на хосте.

### Предварительный расчёт

В Docker с CPU ML предварительный расчёт выполняется сам при каждом запуске ([порядок](#запуск-приложения-в-docker)). Ниже — ручной порядок для GPU-рецепта или replay с backend на хосте. После него версия этого ML становится активной; следующий `make app-up` снова активирует CPU-версию Compose.

Нужны:

- PostgreSQL с миграциями и справочниками, доступная с хоста: `make env-up`, а при уже запущенном приложении в Docker — `make env-port-forward`;
- ML-сервер по адресу `ML_GRPC_ADDR`: `make ml-up ML_MODE=replay` для разработки или `make ml-start` на GPU-хосте (он же заполняет кэш через `ml-warm`);
- активная версия, которую обслуживает этот ML: [регистрация](#версия-прогноза) с `ACTIVATE=1`.

Запустите backend с обработчиком на хосте:

```text
make run-backend
```

Если запущен контейнер backend, задайте другой адрес через окружение процесса: оно приоритетнее `.env`. С адресом по умолчанию ошибки занятого порта не будет: на Windows привязка `:8080` проходит, пока Docker публикует `127.0.0.1:8080`, и запросы к `localhost:8080` попадают в контейнер. В PowerShell:

```powershell
$env:HTTP_ADDR = "127.0.0.1:8081"
make run-backend
```

Переменная действует до конца сессии PowerShell, сброс — `Remove-Item Env:HTTP_ADDR`. В Git Bash — `HTTP_ADDR=127.0.0.1:8081 make run-backend`. Когда шлюз откроется, в логе backend появится `ML server ready` с ID модели и данных активной версии. Затем во втором терминале:

```text
make prediction-jobs-enqueue DRY_RUN=1
make prediction-jobs-enqueue WAIT=1
```

Первая команда ничего не записывает и показывает задания маршрутов с прогнозом. Вторая ставит недостающие задания и ждёт, пока все станут `succeeded` или `failed`; Ctrl+C прекращает только ожидание. С `WAIT=1` команда завершается с ошибкой, если хотя бы одно задание стало `failed` или ожидание прервано. Без `WAIT=1` команда завершается сразу после постановки, а текущее состояние в любой момент показывает `DRY_RUN=1`. Другую версию задаёт `VERSION=<uuid>`, файл окружения — `ENV_FILE`, как у остальных целей. Без Make из корня: `go -C backend run ./cmd/enqueue-prediction-jobs -env-file ../.env -wait`. Флаги и коды завершения — в [backend/README.md](../backend/README.md#постановка-заданий).

После успешного расчёта у версии 10 заданий `succeeded`, а в `validation_predictions` — полная сетка 14 640 строк; с replay 030 это [проверено](../backend/README.md#границы-транзакций). На GPU первый маршрут с ненулевым прогнозом при пустом кэше запускает холодный расчёт всех десяти маршрутов, остальные читаются из кэша; маршрут 5 и replay отвечают без модели ([измерения](../ml/docs/VALIDATION.md)).

- **Контейнер backend** не мешает расчёту: его CPU ML не обслуживает версию GPU или replay, поэтому шлюз контейнера закрыт, и задания этой версии захватывает только backend на хосте. Истёкшие аренды восстанавливают оба процесса с `PREDICTION_JOB_MAX_ATTEMPTS` и `PREDICTION_JOB_RETRY_DELAY` из `.env`. Не переопределяйте их окружением только на хосте; изменив их в `.env`, повторите команду запуска приложения: `docker compose restart` новые значения не применяет.
- **ML недоступен:** при закрытом шлюзе задания ждут в `queued` и не расходуют попытки, пока проверка шлюза не пройдёт. Если ML остановился при открытом шлюзе, одно задание на цикл захвата (по умолчанию цикл один) получает `ml_unavailable` и возвращается в очередь с расходом попытки, после чего шлюз закрывается.
- **Смена версии или комплекта ML:** смену активной версии worker замечает перед следующим захватом и снова проверяет ML, поэтому новую версию можно активировать при запущенном backend. Узкое окно между этой проверкой и захватом остаётся: задание версии, активированной и поставленной в очередь именно в этот момент, может успеть попасть к ML; при обычном порядке «регистрация, затем постановка заданий» это практически исключено. Смену комплекта ML без новой версии (пересборка ML, другой `ML_MODE` или `ML_CONFIG`, новое поколение через `--refresh`) шлюз не замечает: первое задание активной версии окончательно завершится `ml_version_mismatch`. Поэтому после такой смены перезапустите backend или зарегистрируйте и активируйте версию нового комплекта до постановки заданий.
- **Остановка backend во время расчёта** через `PREDICTION_JOB_SHUTDOWN_TIMEOUT` отменяет вызов без записи результата. Задание остаётся `running` до истечения аренды (по умолчанию 60 с), затем восстановление возвращает его в очередь, и после перезапуска backend продолжит расчёт. Прерванная попытка расходуется. На Windows после `taskkill` без `/F` или закрытия окна консоли процессу даётся около 5 с, затем он завершается принудительно (Docker ждёт 30 с), поэтому на хосте держите `PREDICTION_JOB_SHUTDOWN_TIMEOUT` небольшим или останавливайте backend через Ctrl+C. Принудительное завершение откатывает незавершённую публикацию, задание вернёт восстановление.
- **`failed` окончателен:** повторная постановка возвращает то же задание, команды сброса нет. Причина — `last_error_code` в выводе команды и код ошибки в логе backend.

### Запросы к API прогнозов

`route_id` — внутренний ID из `GET /api/routes`, а не номер маршрута. В Git Bash:

```bash
curl -s http://localhost:8080/api/forecast-versions/active
```

```bash
curl -s -H 'Content-Type: application/json' -d '{"route_id":1,"from":"2025-11-01T00:00:00+03:00","to":"2025-11-02T00:00:00+03:00"}' http://localhost:8080/api/predictions/query
```

Ответ `202` содержит `job_id`; статус — `curl -s http://localhost:8080/api/prediction-jobs/<job_id>`. После `succeeded` тот же запрос вернёт `200` со срезом. В query-строке `GET /api/predictions` знак `+` смещения кодируется как `%2B`. В PowerShell 5.1 `curl` — псевдоним `Invoke-WebRequest`, поэтому используйте `curl.exe` или `Invoke-RestMethod`:

```powershell
Invoke-RestMethod -Method Post -ContentType application/json -Body '{"route_id":1,"from":"2025-11-01T00:00:00+03:00","to":"2025-11-02T00:00:00+03:00"}' http://localhost:8080/api/predictions/query
```

`Invoke-RestMethod` превращает ответы `4xx` и `5xx` в исключение; код ошибки из тела виден в его тексте.

### Тесты очереди на PostgreSQL

Интеграционные тесты очереди и worker работают с настоящей PostgreSQL и пропускаются без `TRAMCAST_TEST_DATABASE_URL`. Используйте отдельный одноразовый сервер, а не БД проекта в `tramcast-postgres`. Каждый тест создаёт собственную схему `tramcast_test_<hex>`, применяет в ней миграции и удаляет её после себя; строка подключения в вывод не попадает. Для такого сервера подходит тот же образ, что в Compose:

```text
docker run --rm -d --name tramcast-test-postgres -e POSTGRES_PASSWORD=test -p 127.0.0.1:55432:5432 postgres:18.1-bookworm
docker exec tramcast-test-postgres pg_isready -h 127.0.0.1 -U postgres
```

Повторяйте вторую команду, пока она не сообщит `accepting connections`. Затем в Git Bash:

```bash
TRAMCAST_TEST_DATABASE_URL='postgres://postgres:test@127.0.0.1:55432/postgres?sslmode=disable' go -C backend test -count=1 ./...
```

В PowerShell:

```powershell
$env:TRAMCAST_TEST_DATABASE_URL = "postgres://postgres:test@127.0.0.1:55432/postgres?sslmode=disable"
go -C backend test -count=1 ./...
Remove-Item Env:TRAMCAST_TEST_DATABASE_URL
```

`docker stop tramcast-test-postgres` останавливает сервер; из-за `--rm` контейнер удаляется вместе с данными. Сценарии тестов перечислены в [backend/README.md](../backend/README.md#запуск).
