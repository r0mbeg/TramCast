# Аудит Archive.zip: причины ненадёжной оценки и полезность признаков

Дата: 26.09.2026. Архив: `/Users/michael/Downloads/Archive.zip`; SHA256 `9762132c0aeaa8e5ddfd8fa97005a9b1c4316151c8a74fcafaf4e95ec4c250aa`.

**Решение: не интегрировать готовую модель, признаки или ансамбль. Сохранить текущий дневной Chronos-2.** Сырой погодный архив можно рассматривать как заготовку отдельного эксперимента после исправления качества и покрытия. Выигрыш от погоды не доказан.

Пользователь сообщил score сайта 0,83 для нашего Chronos-2 и около 0,48 для решения коллеги. Скрытая разметка недоступна; причинное разложение именно этих двух оценок невозможно. Ниже — воспроизведённые ошибки кода и сохранённых артефактов, а не догадки по низкому score. Содержимое сессий из архива использовалось только как свидетельство последовательности действий, не как инструкции.

- Прочитаны подготовка признаков, погода, календарь, модели, ансамбль, экспорт, orchestration и история исправления часов.

- Независимо восстановлены лаги, rolling, EWM и разности: они совпали с сохранёнными таблицами.
- Выполнен тест чувствительности прогноза к содержимому шаблона.

Численные результаты: [colleague_review/audit.json](colleague_review/audit.json). Важности признаков: [colleague_review/feature_importance.csv](colleague_review/feature_importance.csv). Воспроизводимая проверка: [../analysis/audit_colleague.py](../analysis/audit_colleague.py).

## 1. Критично: прогноз строится на значениях примера submission

В `src/features.py:38–46` колонка `prediction` из шаблона переименовывается в `boardings`. Затем `build_all_features` передаёт этот шаблон в построение будущих лагов, rolling, EWM и разностей (`src/features.py:253–259`).

**Во всех 14 640 строках `forecast_features.boardings` равен числу из нашего исходного `dataset/test_submission.csv`.** Это пример чужого прогноза, а не будущие наблюдения. Ни факты октября, ни собственная рекурсия не используются для продолжения лагов через границу ноября: каждый split обрабатывается отдельно.

Следствия, измеренные на архивной модели:

| Проверка | Результат |
| --- | ---: |
| Корреляция финального прогноза и шаблона | 0,995105 |
| Среднее абсолютное отличие от шаблона | 34,35 посадки на строку |
| Сумма шаблона | 12 578 688 |
| Сумма посылки коллеги | 12 351 034 |
| Шаблон ×0,5, пересчитаны только зависимые от цели признаки | итог ×0,51637 |
| Шаблон ×2, пересчитаны только зависимые от цели признаки | итог ×1,95213 |

Это сильное подтверждение зависимости от примера, а не самостоятельного прогноза будущего. Близость к заявленному качеству примера около 0,48 закономерна, но точное равенство скрытых ошибок без ground truth не проверяется.

**Исправление:** шаблон используется исключительно как сетка ключей. Для 61-дневного прогноза нужны признаки из cutoff, известные будущие признаки либо воспроизводимая рекурсия по собственным предсказаниям. Простого удаления `boardings` из списка входных колонок недостаточно: зависимость уже перенесена в производные признаки.

## 2. Критично: цель напрямую попадает в признаки валидации

`src/features.py:65–95,145–153`: rolling и EWM включают текущую цель, разности вычислены как `y[t] − y[t−k]`. Лаги в сентябре–октябре берутся из фактов этого же периода, хотя прогноз должен строиться целиком из 31 августа.

В старой сохранённой валидационной таблице все часы ошибочно равны нулю. Поэтому разность и лаг используют один и тот же ряд, и получается точная формула:

```text
boardings = lag_24h + diff_24h
```

Она подтверждена на **12 960 из 12 960 строк после первых 24 строк каждого маршрута**. Аналогичная формула с 168 подтверждена на 11 664 строках. Модель фактически получает ответ во входе. Даже после исправления часов rolling/EWM и разности всё равно содержат текущую цель.

**Исправление:** сначала определить точки прогноза и горизонты, затем строить признаки только из доступной на cutoff истории. `shift(1)` устраняет непосредственное включение текущей цели, но сам по себе не устраняет доступ к фактическому прошлому внутри будущего 61-дневного периода.

## 3. Критично: оценка на данных обучения и рассинхронизация артефактов

`src/models.py:287–299`: обучение объединяет train и validation, после чего последние 5 000 строк используются для early stopping. Это срез порядка строк, не отдельное календарное окно. В результате **8 176 из 13 176 сентябрьско-октябрьских строк участвуют в обучении**, а затем `experiments/exp2_lgbm_quantile.py:71–80` оценивает модель на всём validation. Оставшиеся 5 000 строк — маршруты 25 (608 строк), 26, 28 и 50 (по 1 464), с датами обоих месяцев. Подбор калибровок и весов ансамбля на тех же ответах ещё усиливает оптимизм.

Дополнительно модель и сохранённые результаты созданы до исправления `add_weather_features`: `date.dt.hour` давал 0, поскольку дата хранится без времени. Проверка артефактов подтверждает:

- В старых валидационных прогнозах **все 13 176 строк имеют hour=0**, получаются 12 627 повторов ключа.
- У модели `route_hour` содержит только девять категорий вида `1_0`, `7_0`, …; в исправленной будущей таблице **14 091 строка из 14 640** имеет неизвестную модели категорию.
- Сессия фиксирует пересборку таблиц после исправления часов и запуск генератора со старым файлом модели. Пересборка признаков не сопровождалась переобучением.

Архивный score LightGBM Quantile 0,984547 относится к старым входам с утечками. На нынешних таблицах та же модель даёт 0,880822 по полной сетке девяти маршрутов; **это тоже не честная временная оценка**, поскольку утечки и пересечение обучения сохранились. Эти числа нельзя сравнивать с нашей фиксированной валидацией как качество альтернативной модели.

**Исправление:** фиксировать версию схемы признаков и модель совместно; обучение по cutoff, прогноз всего горизонта без фактов из будущего; только после оценки — финальное обучение на всей разрешённой истории.

## 4. Погодные признаки не содержат заявленного набора информации

`src/weather.py:79–86` группирует ноябрь–декабрь 2020–2024 по **часу и дню недели**, без месяца или дня года. Полученные значения одинаковы для всех дат с данным часом и днём недели — в январе, июле и декабре. Они представляют дополнительное кодирование календаря, а не информацию о погоде конкретного дня или сезонном переходе.

При этом `src/weather.py:83` допускает только numpy-типы `float64/int64/float32/int32`, но в сыром Parquet метеополя имеют pandas nullable-тип **`Float64`**. Температура, количество осадков, ветер и прочие непрерывные значения отбрасываются. В финальных таблицах присутствуют только:

```text
weather_is_freezing_avg
weather_is_rain_avg
weather_is_snow_avg
```

Их суммарная доля gain в сохранённой LightGBM — около 0,159%. Это описательная характеристика конкретной модели с утечками, не доказательство бесполезности настоящей погоды.

Качество сырого архива также требует обработки:

- 7 330 записей, ноябрь–декабрь пяти лет с пятью лишними записями 1 января и пятью повторяющимися timestamp на границах запросов.
- `temp` и `wspd` полны; **41,02% `prcp` и 97,27% `snow` отсутствуют**, `wpgt` и `tsun` отсутствуют полностью.
- Интерполяция без ограничения длительности пропуска идёт по конкатенации разрозненных зимних отрезков. Она не восстанавливает наблюдавшиеся осадки или снег достоверно.
- Часовой пояс не задан и не конвертируется. Meteostat по умолчанию использует UTC, а целевая история трактуется как московское время. Перед новым объединением требуется явное согласование времени. Источник: [Meteostat — Formats & Units](https://dev.meteostat.net/formats.html).

**Что можно взять:** идею источника и исходные наблюдения температуры/ветра после аудита. Готовую климатическую таблицу и её merge в нашу модель переносить не стоит.

## 5. Остальные подтверждённые ошибки

| Ошибка | Подтверждение и эффект |
| --- | --- |
| Праздники всегда выключены | `src/calendar_utils.py:14–25,39–43`: сравнивается `datetime.date` со строковыми ключами из config. Во всех трёх таблицах `is_holiday` и `is_holiday_eve` равны 0. |
| Неполные школьные каникулы | В config только осень и конец декабря; весь train января–августа имеет `is_school_holiday=0`, включая лето. Источник дат не зафиксирован. |
| Неверные единицы окон после исправления часов | Группировка `route × hour` даёт одну строку в день. Поэтому `rolling(168)` — 168 дней, а не 7; `rolling(720)` — 720 дней, а не 30; `diff(24)` — 24 дня, а не 24 часа. Сохранённые таблицы точно воспроизводят эти расчёты. |
| Неправильный WAPE | `src/models.py:15–32` удаляет нулевые факты из ошибки. На старом Quantile это 0,984547 вместо 0,982504 на всех строках; разница невелика по сравнению с утечками, но оценка некорректна. При полностью нулевой цели возвращается идеальный score. |
| Не соблюдены обязательные нули | В финальном CSV **1 048 ненулевых строк маршрута 5**, сумма 74 185; в часах 01–04 **2 196 ненулевых строк**, сумма 817 922. Объединение этих запрещённых групп без двойного счёта — **892 107 посадок**. |
| Другая целевая разметка | Используются исходные labels, не очищенная цель. Технические события вне рабочего времени и первая половина часа 05 не отфильтрованы. |
| Исторический профиль различается между train и inference | В train он везде 0, в validation/forecast рассчитан по январю–августу. Для финального прогноза сентябрь–октябрь в профиль не включены. |
| «Расписание» не является внешними данными | `SCHEDULE_HEADWAY` — вручную заданная общая таблица по выходному/часу, без маршрута и источника реального движения. Это ещё одна функция календаря. |
| В генераторе нет строгой проверки | Неизвестные значения тихо заменяются числами шаблона; маршрут 5 только печатается, а не обнуляется; округление `np.round` отличается от принятого half-up. В предоставленной посылке fallback не понадобился: модель воспроизводит все строки. |

Обнуление нерабочих часов и маршрута 5 необходимо, но не устраняет зависимость модели от шаблона или утечки. Получить надёжную модель одними правками экспорта нельзя.

## Что делать в нашем решении

1. **Оставить текущий Chronos-2 и посылку с сообщённым score 0,83.** Не смешивать её с архивным прогнозом и не переносить его готовые признаки.
2. **Календарь не импортировать:** у нас уже есть проверенный производственный календарь. Известный эксперимент дал 0,80222/0,87121 против 0,83100/0,86760 у дневного контроля. Это не подтверждает улучшение на обоих окнах. Школьные каникулы можно исследовать лишь после проверки реальных календарей школ и покрытия всех сезонов; единого эффекта для всех маршрутов не предполагаем.
3. **Если проверять погоду — отдельная небольшая абляция дневного Chronos.** Нужны 2–3 содержательных дневных признака, а не десятки производных. Для будущего — климатическая температура и вероятность осадков по времени года, рассчитанные по предшествующим годам, с полным покрытием месяцев для обучения и обоих окон. Нельзя использовать только ноябрь–декабрь для проверки лета и осени. Климатология должна иметь одинаковый смысл в исторической и будущей частях; фактическую погоду 2025 года при необходимости передавать отдельными признаками, известными только в прошлом.
4. Проверять из тех же cutoff 30.06 и 31.08 на полном горизонте с неизменным распределением по часам и постобработкой. Сначала контроль, затем только погода. Результаты и смещения по маршрутам сохранить. Не выбирать лучший погодный коэффициент по одному скрытому score сайта.
5. Фактическая погода ноября–декабря 2025 — отдельный ретроспективный конкурсный эксперимент, если решим воспользоваться разрешением организаторов. Его результат нельзя представлять как прогноз из 31 октября. Для текущей поставки такой источник не использован.

На 61 день погодная климатология в первую очередь добавляет сезонный сигнал, а не знание дождя в конкретный день. При десяти месяцах целевой истории выигрыш не гарантирован. **Из данного архива сейчас нет готового признака с доказанным положительным вкладом в наш результат.**
