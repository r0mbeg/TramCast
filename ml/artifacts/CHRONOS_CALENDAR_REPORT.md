# Календарь для Chronos-2: эксперимент на Zhores

Выполнено 26.09.2026, job **8476914**, резервация `HPC-2966`, узел `gn28`, **одна A100 / восемь CPU**. Задание завершилось успешно (`COMPLETED`, `0:0`), выделенные ресурсы освобождены. Результаты выгружены и независимо проверены локально.

**Решение:** сохранить текущий дневной Chronos-2 с прежним распределением по часам. Календарные признаки улучшили осень и праздничные дни дополнительного окна, но ухудшили лето. Изменение только часовых долей немного улучшило среднее двух основных окон, однако тоже ухудшило лето: заранее выбранное условие улучшения обоих окон не выполнено.

## Фиксированная постановка

Проверены четыре конфигурации, заданные до расчёта метрик:

| Код | Признаки в Chronos | Распределение дневной суммы |
| --- | --- | --- |
| `cov0_shares0` | Без дополнительных признаков — прежний контроль | Маршрут × обычный день недели × час |
| `cov1_shares0` | Календарные признаки | Прежние доли |
| `cov0_shares1` | Без дополнительных признаков | Маршрут × тип дня × час |
| `cov1_shares1` | Календарные признаки | Доли по типу дня |

Изменения проверены как схема 2×2, чтобы отделить эффект прогноза дневного объёма от эффекта его распределения внутри дня. Модель остаётся zero-shot, без дообучения и без cross-learning между маршрутами. Девять дневных рядов; маршрут 5 восстанавливается нулями.

В модель переданы четыре заранее известных признака для прошлого и всего будущего горизонта: синус и косинус дня недели, индикатор федерального праздника, рабочий/нерабочий день по пятидневному производственному календарю с учётом переносов. Фактические будущие посадки и погода не передаются. Передача этих четырёх признаков проверялась одним пакетом: отдельный вклад каждого признака в этом опыте не измерен.

Для новых долей использованы существующие типы дня проекта: семь обычных дней недели, праздник, перенесённый выходной, рабочий выходной. Доли — нормированные исторические объёмы по часам. Если у точного типа меньше трёх дней или нет положительного объёма, используется общий профиль соответствующего рабочего/нерабочего дня. Порог три дня взят из существующего календарного эксперимента, не подбирался по новым результатам. Праздники разных сезонов объединены; это ограничение короткой истории.

Производственный календарь — признак спроса, а не расписание трамваев. Исходные часы работы, полная сетка, маски наблюдений, допущение об отсутствующих событиях и правила округления сохранены.

Основные окна прежние: cutoff 30.06 → июль–август (62 дня), cutoff 31.08 → сентябрь–октябрь (61 день). До запуска добавлено диагностическое окно cutoff 30.04 → май–июнь (61 день), поскольку в двух основных окнах нет федеральных праздников и переносов. Оно не входит в среднее основных окон и не является новым независимым скрытым тестом.

## Основные результаты

WAPE-score вычислен на окончательных целых почасовых прогнозах полной сетки. Выше — лучше.

| Конфигурация | Июль–август | Сентябрь–октябрь | Среднее двух окон | Глобальный score объединённых окон |
| --- | ---: | ---: | ---: | ---: |
| Текущий Chronos | **0,830995** | 0,867597 | 0,849296 | 0,850889 |
| Только календарные признаки | 0,802221 | 0,871214 | 0,836717 | 0,839720 |
| Только доли по типу дня | 0,829634 | 0,869432 | **0,849533** | **0,851265** |
| Оба изменения | 0,800520 | **0,873080** | 0,836800 | 0,839958 |

Контрольный прогноз **побитно совпал по целочисленным значениям** с предыдущим опытом на обоих основных окнах. Смена окружения или адаптера не объясняет изменения.

Календарные признаки при прежних долях снизили летний score на 0,028775 и подняли осенний на 0,003617. Они усилили летнее завышение суммарного объёма: смещение выросло с +482 888 до +1 175 338 посадок. Осенняя недооценка уменьшилась с −737 404 до −619 849. Это наблюдение об эффекте данного набора признаков; единственная причина ошибки не установлена.

Доли по типу дня при прежнем дневном прогнозе дали −0,001361 летом и +0,001835 осенью. Прирост среднего — всего **0,000237**, глобальная абсолютная ошибка уменьшилась на 8 806 посадок из 3 492 794 (около 0,25%). Статистическая устойчивость этого малого выигрыша не установлена. По условию улучшения обоих окон текущую конфигурацию не заменяем. Дневная сумма до округления сохраняется; небольшие изменения суммарного целочисленного прогноза вызваны распределением округлений между часами.

## Май–июнь: отдельная диагностика праздников

Во всём дополнительном окне:

| Конфигурация | WAPE-score |
| --- | ---: |
| Текущий Chronos | 0,820350 |
| Только календарные признаки | 0,826698 |
| Только доли по типу дня | 0,819898 |
| Оба изменения | 0,828466 |

Специальные дни — 1, 2, 8, 9 мая и 12, 13 июня: три федеральных праздника и три перенесённых выходных. Их шесть, остальные дни окна — 55 обычных календарных дней, включая обычные выходные.

| Подвыборка | Текущий Chronos | Только признаки | Только новые доли | Оба изменения |
| --- | ---: | ---: | ---: | ---: |
| Шесть специальных дней: score | 0,000000 | 0,376554 | 0,000000 | 0,428304 |
| Шесть специальных дней: абсолютная ошибка | 798 051 | 427 751 | 789 262 | 392 245 |
| Остальные 55 дней: score | 0,882573 | 0,855177 | 0,881281 | 0,853783 |

Нулевой score здесь означает срабатывание ограничения `max(0, 1 − WAPE)`: ошибка превышает сумму факта, а не нулевые посадки или одинаковые прогнозы. Поэтому для этой подвыборки показана также абсолютная ошибка. Сумма факта шести дней — 686 108 посадок.

Календарь почти вдвое снизил ошибку специальных дней, но ухудшил обычные дни. Даже с обоими изменениями суммарный прогноз специальных дней всё ещё завышен на 369 511 посадок. Полностью проблема праздников не решена. Автоматически включать календарную модель только на праздники по этому единственному результату пока нельзя: это новая гипотеза, выбранная после анализа, которую нужно проверить отдельно, без назначения победителей по известным ответам.

## Ресурсы и воспроизведение

- Slurm: **24 секунды**, одна NVIDIA A100-SXM4-80GB, восемь CPU с привязкой к ядрам, запрошено 32 ГБ RAM. Очередь пользователя после завершения пуста.
- Измеренный участок эксперимента после импорта библиотек: **6,40 секунды**, загрузка локальной модели 0,42 секунды. Пик RAM процесса **1,19 GiB**.
- Шесть вызовов прогнозирования (два набора входов × три окна), суммарно около 0,80 секунды. Первый включал прогрев CUDA. Пик выделенных тензоров PyTorch на GPU — **0,482 GiB**; память CUDA/драйвера сюда целиком не входит.
- Веса, окружение и параметры сохранены от предыдущего опыта: `amazon/chronos-2`, revision `29ec3766d36d6f73f0696f85560a422f50e8498c`, seed 42, batch 32, context 512, медиана 0,5, float32, cross-learning выключен. Версии записаны в `run.json`; новые зависимости не устанавливались.
- Указанные секунды — единичные замеры, не оценка API и не устойчивый benchmark скорости.
