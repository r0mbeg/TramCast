## Запуск

Проверено на Python 3.12; зависимости для подготовки и baseline зафиксированы в `requirements.txt`.

```sh
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m tests.test_pipeline
python pipeline.py prepare
python pipeline.py evaluate
```

Исходные `dataset/train.csv`, `dataset/test.csv` и `dataset/labels/*.csv` необходимо положить локально: они исключены из Git. Скрипт находит их относительно корня проекта и не изменяет. Подготовка читает сырые CSV порциями по 250 000 строк; повторная оценка использует уже сохранённую таблицу.

## Правила расчёта

- Цель — число успешных валидаций (`validation_result == 1`) на маршрут за календарный час.
- Обе части сырых данных объединяются по времени события: сентябрьский хвост `train.csv` включается в сентябрь, ноябрьский хвост `test.csv` исключается. Идентификатор `tran_no` не уникален; произвольная дедупликация не выполняется. Кандидаты на дубли между файлами проверяются на границе по пяти полям, а итоговые агрегаты сверяются со всеми исходными labels.
- Рабочее время: `[00:00, 01:00)` и `[05:30, 24:00)`. В 05-м часу учитывается только вторая половина часа. Время трактуется как московское местное без сдвига; timezone отсутствует в исходных строках.
- Маршрут 5 и часы 01–04 имеют нулевой прогноз. Все 10 маршрутов и 24 часа остаются в сетке.
- Пропущенные наблюдения пока приняты за ноль, но сохранены маски наличия исходной разметки, успешных рабочих событий и любых рабочих событий (включая отказы). Это не восстановление спроса и не доказательство отсутствия движения.
- Профиль baseline: `маршрут × день недели × час`, среднее или медиана за 4, 8, 12 недель либо всю доступную историю (`weeks=0`). Прогноз округляется по `floor(max(0, x) + 0.5)`.
- Окна проверки: история по 30 июня → июль–август; по 31 августа → сентябрь–октябрь. Каждый прогноз строится сразу на два месяца. Данные после границы не участвуют в профиле. Случайности нет, seed не требуется.
- Основная метрика — WAPE-score по очищенной полной сетке. Дополнительно тот же прогноз сравнивается с исходными labels: это другая цель. При нулевой сумме фактов score не определён, абсолютная ошибка сохраняется.

## Первая ML-модель

После подготовки и оценки baseline:

```sh
python -m tests.test_model
python model.py
```

Одна фиксированная модель градиентного бустинга проверяется на тех же двух окнах. Используются календарь и исторические профили, рассчитанные только до точки прогноза. Валидационные факты не участвуют в построении признаков. Код: `model.py`; метрика и постобработка переиспользуются из `pipeline.py`.

Результат: 0,83063 летом и 0,72216 осенью, среднее 0,77640 против 0,82079 у опорного baseline. Эта конфигурация не заменяет baseline. [Разбор, ограничения и артефакты](artifacts/ML_REPORT.md).

Контрольный эксперимент без месяца и абсолютных дней года:

```sh
python model.py --no-absolute-calendar
```

Результат: 0,77384 летом и 0,79454 осенью, среднее 0,78419. Baseline остаётся лучше в среднем и на обоих окнах этой новой конфигурации. Исходные артефакты не перезаписываются. [Отчёт эксперимента](artifacts/ABLATION_REPORT.md).

Поправка к среднему историческому профилю с заранее заданным ограничением ±20%:

```sh
python model.py --residual-correction
```

Результат: 0,71931 летом и 0,81657 осенью, среднее 0,76794. Вариант не заменяет baseline. [Постановка и результаты](artifacts/RESIDUAL_REPORT.md).

Диагностика обучающих переходов и направления ошибок: `python diagnose.py`. Она не обучает модель и не меняет прогнозы. Обнаружены неверные суммарные направления поправки летом и осенью при наличии лишь 4/6 исторических точек обучения. [Подробности и таблицы](artifacts/DIAGNOSTIC_REPORT.md).

Проверка влияния первой точки: `python model.py --residual-correction --exclude-january-origin`. Исключается только обучающий блок точки 31 января, исторические события сохраняются. Score: 0,74287 летом, 0,80982 осенью; baseline остаётся лучше. [Отчёт](artifacts/NO_JANUARY_REPORT.md).

## Повторение последней полной недели

Проверка: `python -m tests.test_pipeline`, затем `python pipeline.py repeat-week`.
Повторяется последняя завершённая календарная неделя (понедельник–воскресенье) по маршруту, дню недели и часу на весь горизонт без обновления истории. Источники: 23–29 июня и 25–31 августа. Это не скользящие последние семь дней.

Score: 0,80642 летом, 0,82324 осенью; среднее 0,81483 против 0,82079 у среднего всей истории. Опорный baseline сохраняется. Результаты, детализация и прогнозы — `artifacts/repeat_week_*.csv`, параметры и ресурсы — `artifacts/repeat-week_run.json`. [Отчёт](artifacts/REPEAT_WEEK_REPORT.md).

## Chronos-2 на Zhores

Первый zero-shot эксперимент выполнен на одной A100 и восьми CPU в резервации `HPC-2966`, job `8476911`. Дневные суммы с распределением по историческому часовому профилю дали score **0,83100 летом / 0,86760 осенью**, среднее **0,84930**. Это выше `mean_all` на обоих окнах. Отдельные дневные ряды для каждого часа дали 0,83938 / 0,84612 и ухудшили осень относительно baseline.

Код — `experiments/chronos_experiment.py`, локальная проверка без загрузки весов — `python -m tests.test_chronos_experiment`. Кластерный запуск из подготовленного каталога: `sbatch --parsable jobs/zhores_chronos.sbatch`; скрипт использует существующий Python/PyTorch Zhores, отдельный venv и фиксированную ревизию весов. Подробные условия воспроизведения, ограничения и ресурсы — в [отчёте](artifacts/CHRONOS_ZHORES_REPORT.md). Все прогнозы, метрики, версии и журналы находятся в `artifacts/chronos_zhores/`.

Это ретроспективная оценка современных весов с ограничением входной истории по cutoff, без внешних факторов и дообучения. Осенний выигрыш неоднороден по маршрутам/месяцам; скрытый период не оценён, финальный submission этим запуском не создавался.

## Производственный календарь

Календарь также проверен как вход Chronos-2 и отдельно как правило распределения дневного прогноза по часам: [отчёт Zhores](artifacts/CHRONOS_CALENDAR_REPORT.md). Признаки дали 0,80222 / 0,87121 против 0,83100 / 0,86760 у текущего Chronos; улучшение осени не компенсировало ухудшение лета. Только новые часовые доли дали 0,82963 / 0,86943, но также не улучшили оба окна. Текущий Chronos сохранён. Дополнительное окно май–июнь показало пользу признаков на праздниках и ухудшение обычных дней. Код `experiments/chronos_calendar_experiment.py`, проверка `python -m tests.test_chronos_calendar_experiment`, запуск `jobs/zhores_chronos_calendar.sbatch`; артефакты в `artifacts/chronos_calendar_zhores/`.

```sh
python -m tests.test_calendar_experiment
python -m experiments.calendar_experiment
```

Контрольный эксперимент сохраняет среднее всей истории, но выделяет праздники и переносы в отдельные типы дня. Для группы с менее чем тремя историческими днями используется общий профиль рабочего/нерабочего дня. Федеральный календарь 2025 года и источники сохранены локально; сетевые обращения при запуске не нужны. Используются существующие `hourly_clean.csv` и `baseline_metrics.csv`.

Score: **0,73895 летом, 0,87756 осенью**, среднее **0,80825** против **0,82079** у baseline. Осень улучшилась, лето и среднее ухудшились; baseline остаётся опорным. В июле–октябре нет федеральных праздников/переносов, поэтому проверено влияние их отделения в обучающей истории, а не качество будущих праздничных дней. Результаты и прогнозы — `artifacts/calendar_*.csv`, параметры и источники — `calendar_run.json` и `calendar_sources.json` в той же папке. [Отчёт](artifacts/CALENDAR_REPORT.md).
