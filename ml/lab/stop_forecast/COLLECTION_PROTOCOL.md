# Самостоятельный сбор: измерения отдельно от восстановления

Версия L20260927-v1. Цель — получить независимые наблюдения для проверки
привязки успешных валидаций к остановкам. Период исходной задачи — 2025;
пользователь разрешил отдельный [современный пилот N-v1](MODERN_PILOT.md).
Новый сбор не восстанавливает фактическое движение прошлого года.

## Проверенные возможности онлайн-источников

27.09.2026 проверен доступный без ключа GET
`https://moscowtransport.app/api/stop_v2/<stop_uuid>`.
Способ получения найден в [клиенте автора для Home Assistant](https://github.com/egmen/moscow_transport),
полученный ответ исследован непосредственно. Он содержит остановку,
координаты, маршруты и `externalForecast`:
`time`, `byTelemetry`, `tmId`, `routePathId`.
`byTelemetry=1` не превращает ожидаемое прибытие в состоявшееся посещение.
`tmId` сохраняется как непрозрачный ключ источника, его равенство бортовому
номеру/ID вагона не подтверждено. В ответе нет счётчиков успешных оплат.

Проверка сборщика на автобусной остановке «Клуб “Творческий городок”»
вернула 6 ETA: 2 по телеметрии, 4 по расписанию. Это техническая проверка
канала, **не пилот №12** и не датасет посадок. Сохранены исходный ответ,
время начала/конца запроса, HTTP Date, SHA256 и нормализованные строки в
`dataset/external/stop_evidence_20260927/capture-001/`.

Попытка использовать исходный ID 3707 из книги в `stop_v2` дала HTTP 404.
QR-запрос к `https://api.moscowapp.mos.ru/v8.2/qr-stop/3707/stop`
с координатами остановки дал HTTP 500. Совпадение внутренних ID разных
систем не установлено. Нужен настоящий UUID остановочного табло, полученный
из его публичной ссылки, с проверкой координат, направления и номера маршрута.
Угадывание ID и массовый перебор не выполняются.

Публичный код текущей страницы остановки подтверждает использование
`stop_v2` и `qr-stop`, но не объясняет связь с ключами нашей книги.
Проверен [другой открытый клиент](https://github.com/zavorateam/moscow-transport-mcp):
он также использует эти ответы и справочник data.mos.ru №752.
Его сторонние ключи доступа не используются, чужой код не запускается.
[Карточка официального справочника](https://data.mos.ru/opendata/752)
через web не открылась. Прочие результаты поиска:
[Bustime](https://api.bustime.ru/) описывает формат обмена координатами,
но не предоставляет здесь архив №12 за 2025;
[ru-api](https://ru-api.ru/docs/moscow_transport) относится к проверке
штрафов по VIN и для задачи не подходит.

## Что можно считать надёжным датасетом

Три разных слоя сохраняются раздельно:

1. **Измерения источника:** исходные AFC, фактический GPS, журнал открывания
   дверей или ручные посещения с временем и происхождением. Отдельно храним
   опубликованные ETA: это наблюдение *прогноза источника*, не движения.
2. **Восстановленная привязка:** вероятности остановки, неоднозначности,
   версия алгоритма, неопределённость часов/геопозиции. Не эталон теста.
3. **Независимый контроль:** посещения или связанные оператором события,
   которые не использовались для настройки и назначения меток.

Два приложения могут получать одну телеметрию и не быть независимыми.
Исчезновение прогноза, ETA=0, исчезновение значка с карты и отсутствие
ответа API не доказывают прибытие, отмену рейса или нулевые посадки.
Видимый вход человека не доказывает успешную валидацию.

## Практический путь самостоятельного пилота

Если допустим новый период, начать с короткого инструментального обследования:
один маршрут, оба направления, часы пик/межпик и будние/выходные дни.
Это проверка метода, не достаточный объём для оценки 61-дневного прогноза.

- Наблюдатель в вагоне записывает GNSS-трек с исходным временем, точностью и
  пропусками, отдельно отмечает фактические открытия/закрытия дверей и
  остановочные позиции. Номер вагона, дата, направление и факт смены маршрута
  относятся к поездке. Геозона сама по себе не считается открытием дверей.
- В тех же поездках необходимы успешные валидации с временем и ID устройства
  либо проверенный остановочный счётчик оператора. Если их нет, получится
  надёжный датасет *движения*, но целевой датасет успешных оплат не получится.
  Полный ручной подсчёт входящих можно собирать отдельно как другую цель.
- Независимую часть посещений проверяет второй наблюдатель или другой
  измерительный канал. Контроль делится по целым поездкам/вагоно-дням до
  подбора параметров. Повторная разметка той же моделью не независимый контроль.
- Измеряются задержка оплаты после входа, сдвиги часов, пропуски GNSS и
  регистрации. Для пересекающихся временных окон остановок сохраняется
  неоднозначность. Неполный охват дверей/устройств обозначается явно.
- После проверки метода сбор продолжается на достаточном временном покрытии
  для обучения и отдельного 61-дневного теста без поступления новых фактов.
  Короткая поездка или одна неделя такой тест не заменяют.

Дистанционно агент может собрать доступные открытые ответы и обработать
измерения; физически проехать маршрут и получить закрытые журналы валидаторов
без источника он не может. Текущий код не создаёт эти недостающие измерения.

Для строгого 2025 нужен существующий независимый архив этого периода:
фактические треки/посещения плюс связь с AFC. Данные справочника, POI и
нынешние GPS могут уточнить модель, но не стать исторической контрольной целью.
Существующие поля/баланс и формат будущих наблюдений — [SCHEMA.md](SCHEMA.md).

## Реализованный минимальный сборщик

Используется стандартная библиотека Python; установка сервиса не требуется.
Один вызов — один последовательный проход по явно указанным UUID (до 20),
таймаут 25 секунд, без фонового процесса и автоматического расписания.

```sh
.venv/bin/python ml/lab/stop_forecast/test_stop_evidence.py
.venv/bin/python ml/lab/stop_forecast/collect_stop_evidence.py \
  --stop-id 99a2734d-84ed-4361-8cc2-5cb3e4e778c5 \
  --out dataset/external/stop_evidence_new/capture-001
```

UUID в примере — проверенная автобусная остановка, не №12.
Каталог выхода должен быть новым. Ошибки запросов сохраняются в
`requests.json`, а команда завершается с ошибкой при неполном проходе.
Пустой список прогнозов не создаёт нулевых посадок. Ответ с неизвестной
схемой или признаками некорректных значений не нормализуется молча.

`eta_observations.json` содержит `telemetry_eta`/`schedule_eta`;
`actual_arrival_time` и `observed_boardings` всегда null,
`usable_as_stop_truth=false`. Время снимка — время получения, не время
измерения GPS; свежесть источника независимо не подтверждена. Неизменённые
ответы лежат в `raw/`, manifest фиксирует SHA256 кода и каждого выхода.
Лицензия распространения ответов не установлена; сбор локальный, без публикации.

Длительный сбор пока не запущен: сначала нужен целевой UUID, подходящий
период и способ независимого контроля. Технически работающий ETA-канал
сам по себе этих требований не закрывает.
