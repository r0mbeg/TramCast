# CatBoost, LightGBM и XGBoost: фиксированное сравнение

26.09.2026 выполнены **12 обучений: 3 алгоритма × 2 набора признаков × 2 временных окна**. Ни одна новая конфигурация не превзошла `mean_all` по среднему окон. Лучшим ранее проверенным кандидатом остаётся Chronos-2 с дневным прогнозом и распределением по часам. Это ограниченный эксперимент с сильными табличными алгоритмами, не доказательство превосходства одной библиотеки вообще и не исчерпывающий рейтинг SOTA.

Chronos в рамках этой задачи заново не запускался: использованы сохранённые результаты Zhores, проверены хеш истории, факты по ключам и повторно рассчитаны метрики. Подробности и ограничения современных предобученных весов — [CHRONOS_ZHORES_REPORT.md](CHRONOS_ZHORES_REPORT.md).

## Что меняли и что сохраняли

Переиспользованы `model.features`, `model.training_examples`, метрика/сетка/постобработка из `pipeline.py` и расчёт детализации из `chronos_experiment.evaluate`. Последний импорт не загружает PyTorch и не запускает Chronos.

**Полный набор:** маршрут, час, день недели, месяц, день года, горизонт, день года точки прогноза, среднее профиля всей истории, среднее и медиана профиля последних 28 дней. Профили имеют ключ `маршрут × день недели × час`.

**Без абсолютного календаря:** удалены только `month`, `day_of_year`, `origin_day_of_year`. День недели, час и горизонт сохранены. Новые внешние данные, производственный календарь, обогащение признаков и восстановление пропусков одновременно со сменой алгоритма не добавлялись.

Все шесть конфигураций объявлены до расчёта. Для каждой — 500 деревьев, learning rate 0,05, абсолютная ошибка, seed 42 и 4 потока CPU. Ранняя остановка и подбор параметров по проверочным окнам отсутствуют.

| Алгоритм | Параметры сверх общих |
| --- | --- |
| CatBoost 1.2.10 | `MAE`, depth=6, l2_leaf_reg=5; route/weekday — категориальные |
| LightGBM 4.7.0 | `regression_l1`, num_leaves=31, min_child_samples=50, reg_lambda=5; deterministic/force_col_wise; route/weekday — категории |
| XGBoost 3.4.1 | `reg:absoluteerror`, max_depth=6, min_child_weight=50, reg_lambda=5; hist, enable_categorical; route/weekday — категории |

Это фиксированные стартовые конфигурации с одинаковыми признаками и функцией потерь, но не эквивалентная ёмкость или одинаковая регуляризация трёх разных алгоритмов. Источники параметров: [CatBoost](https://catboost.ai/docs/en/references/training-parameters/common), [LightGBM](https://lightgbm.readthedocs.io/en/stable/Parameters.html), [XGBoost](https://xgboost.readthedocs.io/en/stable/parameter.html). Параметры каждого сохранённого экземпляра записаны в `run.json`.

Точки обучения прежние: каждые 28 дней с 31 января, только полные доступные 62-дневные цели. Для летней проверки — 4 точки / 44 640 строк, для осенней — 6 / 66 960. Перекрывающиеся цели не дают столько же независимых примеров смены режима. Не меняли схему обучения, чтобы отделить смену алгоритма от других гипотез.

Валидация: история по 30.06 → 62 дня июля–августа; по 31.08 → 61 день сентября–октября. Каждый профиль ограничен собственной исторической точкой, фактические лаги внутри будущего горизонта не подставляются. Маршрут 5 исключён из обучения, в прогнозе только нули; часы 01–04 также нули. Пропуски остаются нулями по прежнему допущению. Округление `floor(max(0,p)+0.5)`.

## Интерпретация

Все три модели с полным календарём превосходят baseline летом, но сильно проигрывают осенью. Их осенний прогноз занижен суммарно на 2,70–2,86 млн посадок. Удаление абсолютного календаря сокращает осеннюю недооценку, но ухудшает лето; обе метрики этих вариантов ниже baseline.

Это повторяет наблюдения для HGB: при данной схеме примеров и признаках простая замена бустинга не устранила ошибку переноса на другой сезон. Нельзя заключить, что CatBoost или LightGBM в принципе непригодны. Следующая отдельная гипотеза для табличной модели — изменить представление/признаки или плотность исторических точек, а не смешивать десятки параметров с оценкой на тех же окнах. Денежные ресурсы и новые GPU для этого сравнения не выделялись.

Модели и параметры не продвигаются в итоговый прогноз. Файлы прежних опытов и submission не изменены. Chronos остаётся лучшим локальным кандидатом, `mean_all` — опорным контролем.

## Воспроизведение

Проверено в отдельном `.venv-boost`, созданном из Python 3.12 с `--system-site-packages`; основное `.venv` не обновлялось. Основные численные зависимости совпадают с `requirements.txt`, версии бустингов закреплены в `requirements-boost.txt`. Для чистого окружения:

```sh
python3.12 -m venv .venv-boost
.venv-boost/bin/python -m pip install -r requirements-boost.txt
.venv-boost/bin/python test_pipeline.py
.venv-boost/bin/python test_model.py
.venv-boost/bin/python test_boost_experiment.py
.venv-boost/bin/python boost_experiment.py
```

Команды выполнять из корня репозитория. Нужны `artifacts/hourly_clean.csv` и `baseline_metrics.csv`. Установка пакетов требует сети; сам эксперимент локален. Полный список видимых пакетов фактического окружения — `boost_environment.txt`; он включает унаследованные пакеты и не является минимальным requirements.

Артефакты находятся в `artifacts/boost_comparison/`:

- `metrics.csv`, `summary.csv`, `pooled_metrics.csv`: все конфигурации, оба окна, объединённая метрика.
- `breakdown.csv`: ошибки по маршрутам, месяцам, часам и группам горизонта 1–7 / 8–28 / 29–62.
- `predictions.csv`: 206 640 строк — шесть кандидатов и baseline на двух окнах, с фактами и ключами.
- Двенадцать `.pkl`: модели каждого окна, загружаемые с теми же версиями библиотек. Загружать только доверенные pickle.
- `run.json`: признаки, параметры, обучающие точки, хеши входа и кода, версии, постобработка, время и память.
- `verification.json`: независимая повторная проверка сохранённых прогнозов по исходной очищенной истории.

Три набора проверок прошли. Проверены все шесть путей модели, постоянное кодирование категорий train/inference, изоляция от будущих фактов, сохранение/загрузка моделей, полная сетка, неотрицательные целые и обязательные нули. CSV перечитан и сверен с исходной таблицей; затем независимо пересчитаны метрики по всем 206 640 строкам и сверены хеши. Baseline точно совпал с прежними результатами.

Полный запуск: **58,98 с**, пик RAM процесса **633,45 MiB**, локальный macOS arm64, Python 3.12.14. Обучение, два прогноза (включая проверку сохранённой модели) и сохранение одного кандидата занимали 1,17–7,47 с. Это не чистый benchmark обучения или latency API. Пик памяти относится ко всему процессу, не к отдельной модели. Версии: numpy 2.3.5, pandas 2.2.3, scikit-learn 1.9.1, scipy 1.18.1, threadpoolctl 3.7.0.
