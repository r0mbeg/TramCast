Дата: 26.09.2026. Это план будущей работы, а не отчёт о выполненных экспериментах. Основание: AGENTS.md, существующий пайплайн и отчёты, исследование `artifacts/LITERATURE_REVIEW.md`.

**Область работы:** только модель, признаки, временная оценка и пакетный прогноз. Интеграция с backend в этот план не входит.

**Рекомендация:** сначала получить воспроизводимое сравнение календарного baseline и двух представлений Chronos-2, затем экспорт лучшего допустимого прогноза. Начать на текущем Mac; при медленном инференсе использовать одну GPU на несколько часов. Расширение списка архитектур — после результатов первого набора.

## 2. Основной этап: 16–24 рабочих часа

| Порядок | Реализация | Проверяемый результат | Трудозатраты |
| --- | --- | --- | --- |
| 1 | Переиспользовать метрику и постобработку в общей оценке кандидатов; сохранять прогнозы, параметры, время и память | Существующий baseline воспроизводится; будущие факты не меняют прогноз из фиксированного cutoff | 2–3 ч |
| 2 | Добавить известный заранее производственный календарь: рабочий/выходной/праздничный день, перенесённые дни; проверить календарный профиль отдельно | Сравнение с тем же baseline на обоих окнах; календарные признаки не смешаны с поздними новостями | 3–4 ч |
| 3 | Chronos-2 без дообучения: девять дневных рядов суммарных посадок, затем историческое распределение по часам | Полный почасовой прогноз на 61/62 дня, оценённый общей почасовой метрикой | 4–6 ч |
| 4 | Chronos-2 без дообучения: 180 дневных рядов `маршрут × рабочий час` | Отдельная проверка влияния представления данных, без распределения дневной суммы | 3–5 ч |
| 5 | Сравнить ошибки, выбрать конфигурацию, обучить/подготовить на январе–октябре, сохранить артефакты и экспорт | Проверенный `submission.csv`, отчёт с ограничениями, воспроизводимые инструкции | 4–6 ч |

### Конкретные решения для реализации

**Оценка.** Сохранить два существующих окна: обучение по 30.06 → июль–август, 62 дня; обучение по 31.08 → сентябрь–октябрь, 61 день. В каждом случае модель видит только историю до cutoff. Настройку при необходимости проводить на более ранних временных окнах; уже многократно использованный сентябрь–октябрь не объявлять независимым тестом.

Для каждой конфигурации сохранять глобальный WAPE-score каждого окна, среднее двух окон с соответствующей подписью, ошибки по маршрутам/месяцам/горизонтам и суммарное смещение. Среднее двух score не называть глобальным score объединённых периодов. Сравнивать одинаковые окончательно округлённые почасовые прогнозы.

**Календарь.** Сначала заменить группировку «обычный день недели» на осмысленный тип дня там, где календарь указывает перенос. Для редкой группы заранее установить возврат к более общему профилю. Не подбирать вручную поправки по ошибкам будущего периода. Источник производственного календаря 2025 года опубликован до всех основных cutoff; сохранить источник и дату доступности. Изолировать влияние календаря от смены модели.

**Chronos-2, дневные суммы.** Девять рядов по маршрутам, маршрут 5 исключён из моделирования. Начать с медианного прогноза. Долю каждого рабочего часа считать только по истории соответствующего cutoff: неотрицательные доли, сумма 1, возврат к общему профилю для редких типов дня. Умножить дневной прогноз на доли, восстановить полную сетку и применить общую постобработку. Оценивать почасовой WAPE: улучшение дневных сумм само по себе не является победой. Для контроля отдельно прогнать простую дневную сезонную модель через такое же распределение по часам.

**Chronos-2, отдельные часы.** Девять маршрутов × двадцать рабочих часов = 180 рядов с шагом в сутки. Час 05 сохраняет смысл получасового интервала. Маршрут 5 и часы 01–04 восстанавливаются нулями. Начать с явно зафиксированного независимого режима рядов; совместное использование информации между рядами проверять отдельной конфигурацией. 180 рядов не считать 180 независимыми транспортными системами.

Такое представление даёт горизонт 61/62 шага. У Chronos-2 заявлен максимальный горизонт 1024 шага, тогда как наш прямой почасовой горизонт составляет 1464/1488 часов. Поэтому дневное представление — конкретная адаптация к задаче, а не произвольное уменьшение детализации ответа. Поддержка CPU/GPU описана в [официальной карточке Chronos-2](https://huggingface.co/amazon/chronos-2); совместимость и скорость Apple MPS в проекте ещё не проверены.

**Выбор.** Первое условие замены baseline — выигрыш на обоих окнах, а не только более красивое среднее. При противоположных результатах сохранить baseline основным и описать компромисс; не выбирать допустимое ухудшение задним числом. Если ошибки кандидата дополняют ошибки baseline, отдельно проверить заранее заданный ансамбль 50/50. При малом выигрыше проверить устойчивость по временным блокам; для обучаемых сетей — также по нескольким seed.

**Экспорт.** Обучение/профили только по 31.10.2025, прогноз 01.11–31.12. Присоединение к шаблону по ключам. Проверка после повторного чтения файла: UTF-8, `;`, схема `route;date;hour;prediction`, 14 640 уникальных ключей, целые неотрицательные значения, отсутствие NaN/inf, все 1464 строки маршрута 5 равны нулю, часы 01–04 равны нулю. Округление везде `floor(max(0, prediction) + 0.5)`. Сохранить происхождение прогноза и дату среза истории.

## 3. Два режима внешних данных

**A — прогноз из фиксированной точки.** Использовать только информацию, опубликованную не позже cutoff. Для событий хранить как минимум маршрут, начало/конец действия, дату публикации, источник и статус «план/подтверждённый факт/неизвестно». Дата события не заменяет дату публикации. Неизвестный конец ограничений не превращать в известное восстановление движения.

**B — конкурс с ретроспективными факторами: ещё 6–10 часов на первый ограниченный набор.** Сначала собрать найденные официальные сообщения об изменениях движения маршрутов 7 и 50, затем отдельно проверить фактическую погоду. Фиксировать A/B у каждой конфигурации и каждого экспортированного результата. Сравнение проводить с той же моделью без добавленного фактора. Поздняя новость может объяснять ошибку, но без проверенного механизма поправки не становится улучшением модели.

Каталог источников уже есть в исследовании: [Московский транспорт](https://transport.mos.ru/mostrans/all_news/125272), [календарь переносов Правительства РФ](https://government.ru/docs/all/155500/), [историческая погода Open-Meteo](https://open-meteo.com/en/docs/historical-weather-api). Сохранять конкретные использованные документы и покрытие, а не только ссылку на сайт. Сбор полного архива всех изменений в эту оценку 6–10 часов не входит.

Фактическая погода будущих 61 суток допустима только в B. Архив прогноза погоды, выпущенного до cutoff, обычно покрывает лишь часть горизонта: остальную часть нельзя незаметно заполнить будущими фактами. Ноябрь–декабрь не имеет доступной целевой разметки, поэтому качество B на этом периоде не заявлять до оценки платформой.

Современные веса, выпущенные после 2025 года, разрешены пользователем. Их опыты обозначать как ретроспективную проверку метода с ограничением входных данных по cutoff, а не как доказательство возможности развернуть именно эти веса в августе 2025 года. Отдельно фиксировать версию весов, лицензию и известные сведения о предобучении.

| 2 | Сохраняется гипотеза о недостатке обучающих примеров | Более плотные исторические точки обучения для существующего HGB; новые полные цели только там, где они уже доступны | 4–8 ч |

LightGBM проверять как отдельное изменение после постановки и признаков, не одновременно с ними. Более плотные origin увеличивают число обучающих примеров, но не добавляют независимых годовых циклов. Пропуски в валидационной цели не заменять восстановленными значениями. TimesFM-3 оставить необязательным исследовательским кандидатом; перед использованием проверить условия лицензии весов.

Итого: **2–3 рабочих дня** на основной ML-набор и submission; **22–34 рабочих часа (примерно 3–5 рабочих дней) суммарно** с первым набором ретроспективных внешних факторов B, без существенных проблем зависимостей. Резервные архитектуры и полный архив событий увеличивают срок отдельно. Если актуален указанный в PDF дедлайн 27 сентября, его нужно подтвердить на платформе: весь этот объём в оставшийся срок не закладывать. При жёстком суточном лимите сначала обеспечить экспорт baseline, затем календарную проверку и один вариант Chronos, сохранив рабочую сдаваемую версию.

## 6. Минимальные изменения в репозитории и приёмка

Переиспользовать `pipeline.py` для сетки, метрики и постобработки, `model.py` — для существующей табличной модели. Для Chronos достаточно одного отдельного модуля; внешний календарь/события — небольшие производные таблицы с источниками. Метрики и параметры — CSV/JSON рядом с текущими артефактами. Тяжёлые экспериментальные зависимости держать отдельно от рабочего окружения baseline; фиксировать совместимые версии после проверки установки.

Дополнить существующие запускаемые проверки: изменение фактов после cutoff не меняет прогноз A; доли часов корректны; оба представления сохраняют ключи; доступность события определяется публикацией; нули, округление и экспорт соблюдают контракт. Не создавать отдельную платформу экспериментов.

Работа этапа считается законченной, когда другой разработчик воспроизводит оценку и экспорт по проверенным инструкциям, видит параметры/версии/границу истории, получает артефакты и реальные замеры ресурсов. Улучшение качества считается доказанным только на наших временных окнах с указанными ограничениями. Если кандидаты проиграли, сдаваемым остаётся baseline; отрицательные результаты сохраняются и определяют следующую гипотезу.

В рамках составления этого плана модели не запускались, облачные ресурсы не создавались, исходные данные и реализация не менялись.
