# Развитие ML без потери воспроизводимости

Актуальное решение: исследования продолжаются в `lab/`, основной рецепт сервиса — 030. Добавлены вызов TabPFN по требованию, локальный постоянный кэш и ручной выпуск нового поколения. Конкурсный период — ноябрь–декабрь 2025. Целевая возможность — календарный год с отдельной проверкой применимости.

## Что уже работает

Добавлена [автоматическая офлайн-подготовка](PREPARATION.md) обновлённой истории и следующих 61 суток: новая очистка, родительские модели и пакет входов 030. Она требует покрывающих внешних снимков, не оценивает качество автоматически и не переключает сервис. Перенос месяца проверен синтетически; новые реальные периоды требуют своей проверки качества.

Сервис считает финальную TabPFN-поправку из подготовленных признаков и родительского прогноза 029. Подготовка этих входов остаётся офлайн. Один процесс закреплён за одной версией; первичный кэш опубликованных результатов — Go/PostgreSQL, вторичный кэш вычислений — локальный SQLite. Ручной пересчёт создаёт новый конфиг, его запуск и регистрация в Go выполняются явно. gRPC-контракт и лимит 1464 часа сохранены. Frontend пока использует демо-данные.

## Модель выбирается для выпуска прогноза

Рекомендация: автоматически применять заранее утверждённый рецепт по горизонту при создании версии прогноза. Диспетчер выбирает период и смотрит результат; выбор алгоритма не нужен для обычного просмотра. Сравнение моделей можно добавить позднее как отдельные версии, если оно потребуется пользователям.

Горизонт — расстояние от даты выпуска до конца прогнозируемого интервала. Масштаб просмотра (часы/дни/месяцы) на выбор модели не влияет. Переключение вида не меняет ранее опубликованные часы. Если для годового рецепта нужны разные модели для ближней и дальней части, это один зафиксированный составной рецепт с границами сегментов и правилами согласования. Вначале достаточно одного рецепта; реестр классов, плагины и фабрики сейчас не нужны.

Модель становится кандидатом для горизонта по заранее закреплённой временной проверке, с сезонным baseline и разбивкой по маршрутам, суммам, смещению и удалённости. Frozen и регулярное обновление оцениваются отдельно. Разные модели на разные горизонты — возможность, а не требование назначить победителей при отсутствии доказательств.

## Внешние данные: снимок до расчёта

Рекомендуемый поток следующего этапа:

`дата выпуска + горизонт → получение источников → неизменяемый снимок → расчёт → проверенный пакет → публикация Go`

Получение в реальном времени означает обновление входов перед новым выпуском, а не при каждом просмотре и не повторное скачивание при каждом retry RPC. Все маршруты одной версии используют один снимок. Его идентификатор включает содержимое внешних входов вместе с версией истории. Не подменять данные под существующим `dataset_version`.

Приоритеты источников:

| Источник | Зачем и при каких условиях |
|---|---|
| Календарь | Известные выходные и праздники; фиксировать источник и версию, отдельно проверить эффект на ошибках праздников |
| Объявления о движении | Проверка показала полезность; сохранять время публикации и действия, маршрут и исходное сообщение; начинать с проверяемого снимка без автоматической интерпретации произвольного текста |
| Прогноз погоды | Подключать только после сравнения с контролем; сохранять время выпуска прогноза и его фактический горизонт, не заменять прогноз будущей фактической погодой |
| Свежие валидации и исправность регистрации | Нужны для перехода к актуальным датам и регулярному пересчёту; публичная погода не заменяет свежую историю спроса |

Для каждого источника до реализации выбрать поставщика, условия использования, доступность и формат; задать таймаут, допустимый возраст снимка, предел повторов и способ проверки. Ключи держать в окружении. Проверять дату, часовой пояс, полноту, диапазоны и принадлежность маршрутам. При недоступности обязательного источника не публиковать прогноз. Последний пригодный снимок или резервный рецепт допустимы только по заранее описанному правилу с отражением в метаданных. Ошибка источника не превращается в нулевой спрос.

Для 2025 различать доступное на дату выпуска и разрешённый конкурсный ретроспективный режим. Сегодняшний ответ API не становится историческим прогнозом погоды. Сохранённые фактические архивы можно применять в ретроспективном исследовании, явно отмечая режим.

## Этапы и условия перехода

1. **Интеграция рецепта 030.** Подключить Go к текущему gRPC и frontend к API прогнозов отдельной задачей. Проверить очередь, повтор, отмену, несовпадение версий, отсутствие частичной публикации и суммы в UI. Условие завершения — один маршрут проходит весь путь, ошибки и нули различаются.
2. **Подготовка новых входных пакетов вне RPC.** Выделить воспроизводимую команду из цепочки 030: новая история, исходные прогнозы/учителя и внешние снимки → признаки и родительский прогноз → проверенный рецепт для runtime. Сейчас поставлен один подготовленный снимок 2025. Полная пересборка родительской цепочки и обучение/подбор в RPC не выполняются. Проверить происхождение каждого компонента и отсутствие будущих целевых значений. Связать ручной выпуск поколения с административным действием Go, не изменяя опубликованные версии.
3. **Один внешний источник.** Выбрать источник по доступности и проверенной пользе; начать с календаря или объявлений о движении. Сначала сохранить и проверить снимок, затем сравнить рецепт с контролем. Проверить отказ, просроченный кеш и повторное использование того же снимка. Подключать источник к опубликованной модели только по результатам проверки.
4. **Несколько рецептов и расчёт до года.** До изменений согласовать контракт с Go: как закрепляется рецепт и снимок, как задаётся годовой интервал, как выбирается версия. Текущий PredictRequest не содержит ID желаемой модели — нельзя молча переключать её по длине запроса. Выбрать явную передачу версии либо отдельный процесс с закреплённым пакетом, когда появится второй реальный рецепт. Затем обновить ограничения Go/Python, таймауты, транспортные пределы и UI; проверить год целиком, включая високосный, точную сетку и нагрузку. Существующие версии оставить воспроизводимыми.
5. **Оперативное обновление.** После появления свежей истории и наблюдений о её полноте выпускать новые версии по расписанию. Не изменять начатые задания. Сравнивать качество, смещение, покрытие источников, длительность и отказы с предыдущей версией; откат — выбор прежнего неизменяемого пакета.

Каждый этап — отдельный проверяемый результат. Backend/frontend меняются согласованно с их разработчиками, а не внутри перемещения ML-файлов.

## Особенности года

Год определяется календарными границами в Europe/Moscow и может содержать 366 дней. При почасовой публикации нужны все часы; суточные и месячные значения складываются из них после единственного half-up округления. Прогноз погоды используется только в пределах доступного горизонта; дальнейшие погодные предположения — отдельный сценарий или климатология с собственной версией, не «погода на год».

Десять месяцев истории не подтверждают годовую точность. До дополнительных полных годовых циклов и отдельного будущего периода результат за пределами проверенного горизонта обозначается сценарием с допущениями. Не получать год простым повтором пакета 002 и не приписывать ему score двухмесячного теста. Ограничение 1464 часа сейчас не расширено: снять его можно только на этапе согласованной реализации и проверок, а не косметической сменой константы.
