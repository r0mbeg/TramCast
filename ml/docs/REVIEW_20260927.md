# Сверка ревью коллеги с текущим кодом

27 сентября 2026. Основа проверки — локальный коммит `7e932a0` и объединение
с `origin/master` (`40e2adf`). Исходный отзыв `TramCast_ML_review.md` проверял

## Что подтверждено

| Замечание | Состояние текущей реализации |
| --- | --- |
| 1. Остановочная точность не установлена | Верно. Манифест профилей содержит `stop_wape=null`, `stop_mae=null`, покрытие подтверждённых наблюдений 0. Загрузчик отвергает неподдержанные заявления о точности. Баланс и совпадение с эталонным сценарием проверяют реализацию распределения, а не его точность на остановках. |
| 2. Постоянные профили 17/25/26/28/50 | Подтверждено загрузкой точных Fraction-весов: по одному уникальному вектору на маршрут. Для 1/7/11/12 в текущем пакете соответственно 19/24/27/26 уникальных векторов. Наличие разных контекстов не означает наблюдаемые остановочные цели. |
| 3. Нет экспозиции обслуживания | Верно. `PredictStops` выбирает веса по номеру, часу и `weekday() >= 5`; расписание, число посещений, праздничный календарь и фактические рейсы не участвуют. Допустимость посадки из справочника не заменяет наличие рейса в конкретный час. |
| 4. Ретроспективные внешние данные | Верно. Builder проверяет покрытие, checksum, `regime`, URL и дату получения погоды, но не гарантирует доступность каждого значения на дату выпуска прогноза. CPU-дистилляция также использует ретроспективный погодный сценарий. Конкурсное разрешение внешних данных не доказывает качество будущего эксплуатационного прогноза. |
| 5. Независимое преимущество сложной цепочки | Ограничение остаётся. Сохранённые метрики и пользовательские закрытые scores не являются новой независимой проверкой в этой работе. Повторно использованный сентябрь–октябрь нельзя объявлять нетронутым holdout. |
| 6. Отказы параллельным запросам | Воспроизведено: четыре одновременных полных `PredictStops` №12 дали один OK и три `UNAVAILABLE`. Общий semaphore ограничивает сборку ответов после получения прогноза и используется обоими RPC; это не блокировка GPU. |
| 7. Healthcheck не доказывает готовность модели | Верно. Compose проверяет только №5 за фиксированный час ноября 2025. В recipe-режиме он обходит compute/cache; отсутствие stop-пакета не блокирует маршрутный RPC. Go worker из master тоже использует №5 как проверку доступности и версий, а не доказательство прогретого расчёта. |
| 8. Ограниченный перенос периода | Верно. Публичный runtime CPU получает фиксированные признаки ноября–декабря; прежний builder пересобирает семейство 030 на 61 день при оговорённой истории. Исследовательский CLI с выбором даты не делает публичный gRPC универсальным. Период stop-пакета проверяется отдельно. |
| 9. SQLite и Windows | Незакрытое соединение конструктора подтверждено: после выхода из `with sqlite3.connect(...)` оно продолжает принимать SQL. `get()` закрывает собственное соединение в `finally`; проблема не относится ко всем путям. Fixtures с `write_text`, чтение дочернего stdout без явной UTF-8 и соединения в тестах сохранились. Windows в этой сверке не запускалась. |
| 10. Пропуски и неопределённость | Методологически верно. Маска наблюдения не доказывает полноту регистрации, восстановленные значения не заменяют факты, разброс сценариев не является откалиброванным доверительным интервалом. Новых доказательств полноты или остановочной точности не получено. |

## Что изменилось после снимка коллеги

- Основной локальный режим — CPU CatBoost. GPU 030 выбирается явно;
  работающий удалённый GPU-сервис этим изменением не переключён.
  Сообщённые пользователем закрытые scores CPU 0.88362 и GPU 0.88543
  записаны в [инструкции поставки](HANDOFF.md); здесь они независимо не проверялись.
- Утверждение о сохранении суточной суммы 029 относится к
  [TabPFN-корректору](../runtime/model_030.py), где это явно заложено.
  [CPU-модель](../runtime/model_cpu.py) прогнозирует почасовые значения
  через собственную опорную величину и не обязана сохранять суточную сумму 029.
- Из master пришли Go gRPC-клиент, регистрация версий, очередь и worker.
  HTTP API прогнозов и подключение пользовательского расчёта в UI ещё отсутствуют.
  Go-интеграция остановочного метода остаётся отдельной работой.
- `.gitattributes` из master сохраняет байты рецептов/пакетов и LF исходников
  runtime. Это защищает checkout, но не исправляет создание временных CSV
  через `write_text()` в Windows-тестах.
- Новые OT/elastic-опыты сохранены с отрицательным результатом:
  географическое преимущество не подтверждено. Они не устраняют замечания 1–3.
  [Отчёт elastic](../lab/stop_forecast/ELASTIC_REPORT.md).

## Проверено запуском на текущем Mac

- Общие runtime-проверки маршрутов 002/030, клиента, кэша, отмены,
  версий и тестового вычислителя прошли. Это не запуск GPU TabPFN.
- Отдельный остановочный тест с полным `stop_estimates.csv.gz` подтвердил
  все **884 256** целых значений. Максимальный ответ — **178 976 байт**.
- Повторная проверка параллельных запросов: единственный успешный ответ
  примерно **0,74 с**, остальные получили `UNAVAILABLE` за **0,043–0,107 с**.
  Это один локальный опыт с replay, не нагрузочный benchmark CPU/GPU.
- Реальная CPU-модель ранее в этой же сессии прошла эталонную проверку
  **14 640 часов**, gRPC, остановочных сумм, повторного использования кэша,
  смены поколения и целостности. Холодный дочерний расчёт около **0,99 с**;
  новая оценка прогнозной точности при этом не выполнялась.
- Семь тестов новых optimal transport/elastic модулей прошли;
  они проверяют алгоритмы, а не географическую точность Москвы.

Полную пересборку из raw, новое обучение, GPU-запуск, Windows и новое
развёртывание на сервере эта сверка не включает.

## Практический приоритет

1. Закрыть SQLite-соединения и сделать временные файлы/дочерний вывод
   переносимыми. Это небольшие исправления с конкретными воспроизводящими тестами.
2. Пересмотреть общий semaphore сборки ответов после измерений памяти и задержек.
   Уже есть четыре RPC-потока и предел восьми RPC: отдельная новая очередь
   или кэш готовых ответов пока не обоснованы. SQLite-блокировку холодного
   вычисления сохранять независимо от параллельной выдачи.
3. Разделить проверку доступности и готовность нужной модели/stop-пакета.
   Проверка должна учитывать текущие версии и период. Простая замена №5 на
   ненулевой маршрут с прежним коротким тайм-аутом может повторно отменять
   холодный GPU-расчёт и не является достаточным решением.
4. Плановую экспозицию включать только из проверенного источника с покрытием
   дат и направлений; до этого сохранять явный сценарный статус. Получение
   закрытых выгрузок не является условием продолжения согласованного MVP.
5. Следующее сравнение моделей заранее фиксировать и проводить на одинаковых
   входах и масках, отличая конкурсную ретроспективу от доступных на дату
   прогноза данных. Измерять эксплуатацию на выбранном хосте; RTX 3070
   больше не является обязательным условием проверки основного CPU-режима.
