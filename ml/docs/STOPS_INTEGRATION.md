# Остановочные оценки: подключение Python к Go

## Что реализовано и кто за что отвечает

Python-сервис поддерживает новый unary RPC
`/tramcast.forecast.v1.ForecastService/PredictStops`. Он получает маршрутный
прогноз тем же путём, что `Predict`: реальный вычислитель выбранного рецепта
либо явно включённый replay, общий SQLite-кэш, затем распределение по
зафиксированным остановочным профилям. Это не чтение готовых почасовых
остановочных оценок из лаборатории.

Рабочий код — `ml/runtime/stops.py` и `service.py`. Компактные входы —
`ml/bundles/stops-network-v1/`: каталог позиций, 40 профилей на маршрут
и manifest. Нужны только стандартная библиотека Python и уже существующие
gRPC/Protobuf-зависимости. `lab`, pandas, NumPy, scipy, исходные оплаты,
архивы метро и справочники подготовки для остановочного расчёта не нужны.
Для вычисления самого маршрута на GPU сохраняются обычные зависимости 030.

Go отвечает за очередь, ожидаемые версии, проверку всего ответа, сопоставление
позиций, транзакционное сохранение и публикацию через HTTP. Пользовательский
HTTP-запрос не должен ждать холодный GPU-расчёт: по-прежнему возвращается job ID.
Python не обращается к PostgreSQL и не публикует результат в приложении.

В репозитории обновлены общий `.proto`, генерация Python/Go, Python runtime и Docker.
**Модель распределения математически обоснована и готова в Python;
интеграция с frontend не завершена.** Остановочное хранилище, HTTP API
и обработчик ответа предстоит реализовать в backend.
Предыдущий `Predict`, его сообщения и номера полей сохранены.

## Семантика результата

Название для пользователя: **«Расчётное распределение посадок»**.
Подпись: «Оценка по маршрутному прогнозу и предположениям модели;
точность по отдельным остановкам не проверена».

Поддержаны 1, 5, 7, 11, 12, 17, 25, 26, 28, 50; профильный пакет ограничен
`[2025-11-01T00:00:00+03:00, 2026-01-01T00:00:00+03:00)`. Это 604 позиции,
20 направленных шаблонов, 884 256 значений полного выпуска всех маршрутов.
Один запрос — один маршрут, от 1 до 1 464 часов внутри периода. Для фонового
выпуска Go запрашивает полный горизонт выбранной версии; срезы нужны для
проверки/диагностики, а просмотр готовых данных идёт из БД.

Это **сценарные оценки успешных валидаций**, не остановочные наблюдения,
число людей в вагоне или заполненность. Остановочные WAPE/MAE отсутствуют,
маршрутный score на остановки не переносится. География поздняя и условно
применяется ко всему горизонту; независимых остановочных наблюдений нет.

Prior смешивает равные веса и близость к архивным входам метро. Исходные
доли B/F есть у 1/7/11/12; у 17/25/26/28/50 доли географические и постоянны
по часам. Это допускается для согласованной сценарной функции и отражено
в [пакете исследования](../lab/stop_forecast/NETWORK_PACKAGE.md).
На рабочем запросе prior не подбирается и модель не обучается: применяются
готовые профили `p`. Целый маршрутный итог распределяется largest remainder
с точной рациональной арифметикой. Нельзя округлять результат повторно.

## Запуск и первая проверка

Из корня репозитория. Для интеграции без GPU:

```sh
docker compose -f ml/compose.yaml --profile replay up -d --build --wait
docker compose -f ml/compose.yaml --profile replay exec ml-replay \
  python service.py --bundle /app/ml/bundles/030/forecast_bundle.json --describe
docker compose -f ml/compose.yaml --profile replay exec ml-replay \
  python client.py --stops --route 12 \
  --from 2025-11-01T00:00:00+03:00 --to 2026-01-01T00:00:00+03:00 \
  --timeout 30 --output /tmp/stops12.json
```

`--describe` сохраняет прежние маршрутные поля верхнего уровня и добавляет
`stop_forecast`. JSON ответа клиента записывается **в контейнер**, его можно
забрать через `docker compose -f ml/compose.yaml cp ml-replay:/tmp/stops12.json ./stops12.json`.
JSON использует Protobuf JSON: int64 представлены строками, enum — именами,
timestamps — RFC3339 UTC. Это сериализация; gRPC Go получает обычные int64.

Для рабочего GPU-режима установка/запуск остаются из [HANDOFF](HANDOFF.md).
После запуска заменить `ml-replay` на `ml-gpu`; для описания версий использовать
`python service.py --describe`, без `--bundle`. Для холодного запроса задать
`--timeout 930`. При смене replay на GPU маршрутные и составные версии изменятся.
Это нужно зарегистрировать в Go, а не подменять числа под старой версией.

gRPC доступен по `127.0.0.1:50051` хоста; порт меняется через `ML_PORT`.
Если Go работает в другой контейнерной сети/на другом хосте, адрес и доступ
настраиваются отдельно; внутри Go-контейнера localhost не является ML-хостом.
Транспорт пока insecure, предназначен для внутренней сети. Публичную
аутентификацию/HTTP по-прежнему обеспечивает backend.

Финальная поставка запускается на CPU по [RUN.md](../../RUN.md).
Остановочные профили и runtime входят в CPU-образ.

Пакет остановок включён в обе Docker-цели: `serving` и `inference`.
По умолчанию используется `../bundles/stops-network-v1/allocation_bundle.json`
относительно runtime. Для собственного процесса доступны `--stop-bundle`
или `ML_STOP_BUNDLE`; внешний пакет нужно смонтировать read-only и явно
передать путь процессу. Горячей перезагрузки нет.

Существующий Compose healthcheck проверяет **маршрутный** RPC. Для готовности
остановочной функции проверить `stop_forecast.available=true` и выполнить
`client.py --stops --route 5` на один допустимый час: это не запускает GPU.
`available=true` означает загруженный пакет; дополнительно проверить его
период относительно выбранного маршрутного горизонта. Нельзя применять
профили ноября–декабря к следующему горизонту без нового пакета.

## Контракт и пример вызова Go

Сгенерированный Go-контракт уже входит в репозиторий. При изменении `.proto`:

```sh
make proto-generate-go
```

Требуются существующие `protoc`, `protoc-gen-go`, `protoc-gen-go-grpc`.
Старый Go-клиент продолжит вызывать `Predict`. Для `PredictStops` нужна
перегенерация; старый Python-сервер вернёт `UNIMPLEMENTED` на новый метод.
Пакет остаётся `tramcast.forecast.v1`, поскольку изменение добавочное.

Пример вызова из фонового обработчика (после создания gRPC-клиента):

```go
func fetchStops(ctx context.Context, client forecastv1.ForecastServiceClient,
    route int32, from, to time.Time,
) (*forecastv1.PredictStopsResponse, error) {
    ctx, cancel := context.WithTimeout(ctx, 930*time.Second)
    defer cancel()
    return client.PredictStops(ctx, &forecastv1.PredictRequest{
        RouteNumber: route,
        ForecastFrom: timestamppb.New(from),
        ForecastTo: timestamppb.New(to),
    }, grpc.MaxCallRecvMsgSize(4<<20))
}
```

Импорты: `context`, `time`, `google.golang.org/grpc`,
`google.golang.org/protobuf/types/known/timestamppb`,
`forecastv1 "github.com/r0mbeg/TramCast/backend/internal/gen/tramcast/forecast/v1"`.
Этот фрагмент только получает ответ: **до записи требуется валидация ниже**.
Каналу нужен адрес ML-сервиса и прежние транспортные настройки Go-клиента.
Один запрос получает оба направления; нельзя вызывать расчёт отдельно для
каждого направления и присваивать каждому полный маршрутный итог.

## Версии: что закрепить в задании

| Поле PredictStopsResponse | Значение |
|---|---|
| model_version | Составная идентичность фактической маршрутной модели и остановочного алгоритма |
| dataset_version | Составная идентичность маршрутных данных и остановочного пакета |
| route_model_version, route_dataset_version | Точно те ID, которые возвращает Predict при том же комплекте |
| allocation_model_version | Исходная модель долей и SHA256 рабочего кода остановочного расчёта |
| allocation_dataset_version | SHA256 manifest профилей, включая контрольные суммы и происхождение |
| network_version | SHA256 файла позиций остановок |
| allocation_package_version | ID исходного исследовательского выпуска для аудита |
| estimate_status | Всегда scenario_estimate_unvalidated для текущей реализации |
| geography_status | Ограничение актуальности схем, из профилей |

При регистрации остановочной версии сохранить ID из **`stop_forecast`**
в `--describe`, а не маршрутные ID верхнего уровня. Также закрепить период,
исходные маршрутные ID, network_version и сценарный статус в контексте задания.
Ответ с несовпадающей ожидаемой версией отклоняется целиком.
RPC не выбирает старую версию по ID: для неё нужен процесс с тем же комплектом.
При обновлении кода распределения составной model ID меняется автоматически;
старые сохранённые результаты остаются самостоятельной версией.

В существующей схеме `forecast_versions` предусмотрена одна активная версия
без разделения видов прогноза. Для одновременных маршрутных и остановочных
версий backend должен **явно расширить модель хранения/активации новой миграцией**,
не записывать остановочную версию поверх активного маршрутного выпуска.
Точное устройство новых таблиц остаётся задачей разработчика Go; изменения
существующей применённой миграции недопустимы.

## Каталог позиций и почасовые массивы

`occurrences` передаётся один раз. Порядок: направление, строковый pattern_key,
числовой stop_sequence, строковый source_stop_id. Маршрут задан запросом.

| Поле позиции | Как использовать |
|---|---|
| occurrence_id | Уникальный локальный ключ пакета, не разбирать формат |
| source_route_id | Источник маршрута из книги либо `osm:relation/<route_master>` |
| pattern_key | Шаблон книги либо `osm:relation/<route>` |
| direction_id | 0 или 1, в соответствии с каталогом приложения |
| stop_sequence | Порядковое вхождение, начинается с 1 в этом пакете |
| source_stop_id | Источник остановки книги либо `osm:node/<node>` |
| stop_name | Подпись для диагностики, не ключ сопоставления |
| boarding_allowed | optional bool; presence обязательно, false для OSM exit-only |
| boarding_role | assumed_unverified / stop / stop_entry_only / stop_exit_only |

`hours` — точная возрастающая сетка запрошенных часов:

- `hour_start`: присутствующий Timestamp, nanos=0;
- `route_boardings`: присутствующий optional int64, маршрутный итог;
- `estimated_boardings`: плотный массив int64 **той же длины, что occurrences**;
  элемент i относится к позиции i, включая явные нули;
- `status`: `SCENARIO`, `NONWORKING_ZERO` либо `ROUTE5_FALLBACK` с префиксом
  `STOP_HOUR_STATUS_`; `UNSPECIFIED` недопустим.

Для №5 fallback имеет приоритет даже ночью. У остальных маршрутов часы 1–4
нулевые с `NONWORKING_ZERO`; часы 0 и 5–23 — `SCENARIO`, даже если итог равен
нулю. В рабочий час нули отдельных exit-only позиций определяются через
`boarding_allowed=false`. Остальной ноль может быть результатом округления;
он не доказывает отсутствие спроса. Сервис не возвращает дробные ожидания:
интерфейс и агрегаты используют готовые целые оценки.

## Обязательная проверка ответа в Go

Использовать всю проверку до начала публикации, как в
`ml/runtime/client.py::validate_stop_response`, и дополнить сравнением
ожидаемых версий/каталога приложения:

1. Сравнить все ожидаемые версии, сценарный статус и период задания.
2. Убедиться, что есть полный ожидаемый каталог; occurrence_id и составные
   ключи уникальны, порядок канонический. Повторный source_stop_id допустим
   на другой позиции. Проверить оба направления и непрерывные stop_sequence.
3. В Go проверить `BoardingAllowed != nil` и `RouteBoardings != nil`:
   `Get...()` без проверки presence скрывает разницу между отсутствием и нулём.
4. Проверить точную часовую сетку, `Timestamp.CheckValid()`, nanos=0,
   длину каждого массива, все значения >=0, статусы и правила нулей.
5. Проверить сумму массива относительно route_boardings **без переполнения**:
   перед `sum += value` требовать `value <= routeBoardings-sum`, начиная с sum=0.
   После всех элементов требовать равенство. Python уже проверяет int64;
   Go всё равно валидирует внешнюю границу самостоятельно.
6. Если маршрутный прогноз уже сохранён, сравнивать только с **теми же**
   route_model_version/route_dataset_version. При этих ID значения должны
   совпасть по каждому часу; при разных ID публикацию под старой версией отклонить.

Для стандартного выпуска число позиций: 1→44, 5→32, 7→89, 11→85, 12→97,
17→52, 25→41, 26→51, 28→30, 50→83. Привязывать эти ожидания к network_version,
не считать вечными константами для будущих пакетов.

## Сопоставление и хранение

Найти маршрут по номеру и сверить `routes.source_route_id` с source_route_id.
Найти остановку по `stops.source_stop_id`. Сопоставить позицию с
`routes_stops` по `(route_id, pattern_key, stop_sequence)`, затем проверить
direction_id и stop_id. Это реальные поля действующего каталога. Не использовать
название/координаты и не превращать source_stop_id в числовой PostgreSQL ID.

Ключ остановочного значения должен сохранять версию, маршрут, шаблон,
позицию и час. Одного `(stop_id, date, hour)` недостаточно: он смешает направления,
маршруты и повторные прохождения. Текущая `validation_predictions` хранит
маршрутные значения и не подходит для этих строк без отдельного расширения.

Если каталог приложения не сопоставил часть позиций, не удалять их массу
и не перенормировать остальные оценки. Либо остановить публикацию как ошибку
сопоставления, либо явно сохранить несопоставленные позиции/сумму и показать
частичное покрытие. Для каждого часа должно выполняться:

`route_boardings = mapped_estimates + unassigned_estimates`.

Рекомендуемый порядок обработчика: взять аренду задания → вызвать RPC →
проверить ответ и сопоставление → в одной транзакции сохранить значения,
остаток/покрытие и завершить задание под проверкой актуальности аренды/попытки.
Частичные ответы, другой набор версий и результат просроченного работника
не публикуются. Сутки/недели складываются из уже сохранённых целых часов.
Агрегация по физической остановке допустима отдельным представлением после
сохранения исходных позиций.

## Ошибки, кэш и отмена

| gRPC status | Причина и действие Go |
|---|---|
| INVALID_ARGUMENT | Неполный/нецелый час, неверный интервал/номер; исправить запрос |
| NOT_FOUND | Неизвестный маршрут; не подменять нулём |
| FAILED_PRECONDITION | Пакет/профили повреждены или период не поддержан; проверить deployment и версии |
| UNAVAILABLE | Занят построитель ответа, ошибка хранилища или лимит расчёта; ограниченный retry с backoff |
| RESOURCE_EXHAUSTED | Транспортная конкуренция или ответ >4 MiB; уменьшить нагрузку/проверить контракт |
| CANCELLED / DEADLINE_EXCEEDED | Прекратить попытку, не публиковать частичный результат |
| UNIMPLEMENTED | Старый Python-сервис; обновить образ, не маскировать маршрутным ответом |

Четыре RPC-потока, максимум восемь одновременных RPC; один построитель ответа
общий для обоих методов. Вход ≤64 KiB, выход ≤4 MiB. Максимальный измеренный
ответ полного текущего выпуска — 178 976 байт. Холодный маршрутный расчёт
по-прежнему ограничен конфигом 030, а остановочное распределение выполняется
на CPU после него. Кэш хранит полный маршрутный результат, профили — в памяти;
отдельного SQLite-кэша остановочных строк нет.

Повтор `PredictStops` и последующий `Predict` используют тот же маршрутный
кэш без повторного вызова модели. №5 не запускает её вообще. Негодный
профиль/его период проверяется **до** вызова вычислителя. Повреждённый
остановочный пакет делает недоступным только PredictStops; Predict продолжает
работать. Детали ошибки остаются в серверном логе.

Проверка отмены выполняется до вычисления и между часами распределения.
При отмене во время модели действуют прежние завершение дочернего процесса
и откат незавершённого кэша. Если полный маршрут уже посчитан и отменён лишь
остановочный ответ, корректный маршрутный кэш может остаться; незавершённый
остановочный результат не сохраняется и не отправляется как успешный.

## Обновление профилей и воспроизведение

ML готовит новый офлайн-выпуск и экспортирует только данные для сервиса:

```sh
.venv/bin/python ml/preparation/export_stops.py \
  --source ml/lab/stop_forecast/releases/network-entropy-v1 \
  --out /tmp/tramcast-stop-serving-new
```

Каталог назначения должен отсутствовать. Экспорт проверяет хеши исходных
файлов и целостность профилей. В пакет не копируются почасовые результаты,
служебные XLSX или raw. Исторический выпуск и рабочий пакет не перезаписывать:
создать новый каталог, получить новые ID, согласовать их с Go и перезапустить
сервис с новым путём. Расширение периода требует отдельно подготовленных
профилей и проверенной поддержки географии; смена даты запроса не обновляет их.

Обычные проверки не требуют GPU, БД, Docker или lab:

```sh
make test-ml-service PYTHON="$PWD/.venv/bin/python"
```

Дополнительная проверка каждого числа по сохранённому лабораторному эталону:

```sh
STOP_REFERENCE_FILE="$PWD/ml/lab/stop_forecast/releases/network-entropy-v1/stop_estimates.csv.gz" \
  make test-ml-service PYTHON="$PWD/.venv/bin/python"
```

Пройдены все 884 256 значений, баланс, позиции/нули, проверки повреждённых
профилей и векторов, разные версии, общий кэш после перезапуска, отмена,
int64-округление, CLI. Смена маршрутного результата проверена считаемым
тестовым вычислителем: это проверка соединения компонентов, не новый запуск
